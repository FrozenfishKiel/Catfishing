# 《钓鱼规则-整合稿》三个重构需求讨论意见

属主：李前臻（需求提出与裁决）；评估：Codex
状态：讨论稿，2026-09-08；只提出结构与接口方案，未修改整合稿或其他文件。
出处：[指定整合稿](../2026-09-06-钓鱼规则整合/钓鱼规则-整合稿.md)、[09-07 裁决记录](../2026-09-06-钓鱼规则整合/2026-09-07裁决记录.md)、该目录材料 60—65，以及 [GDD 系统分册的出处与阅读规则](../2026-09-05-codex独立评审/材料/06_GDD%20系统分册.md)。

本文的节号均指指定整合稿，不指源文档《钓鱼全流程 9.3》。材料 60—65 是 09-06 本地快照；猫册与动作表现集参考 09-05 材料。涉及后续变化，以指定整合稿与晚间 N1—N10 裁决为准，不用旧快照反推现行规则。下文接口字段名均为建议，不表示已有程序接口。

## 一、总判断

**三个需求值得一起做，但不能按字面机械执行。**

| 需求 | 判断 | 我反对的做法 |
|---|---|---|
| 机制开头加形象化描述 | 支持按机制群加一句读者能想象的动作或结果 | 每个三级标题都强加一句；用比喻重写判定条件 |
| 先讲钓鱼，多人独立附篇 | 支持“基础规则＋多人扩展”，主文按一竿流程组织 | 把所有出现“多人”的句子搬走；把主文命名为独立“单人模式” |
| 钓鱼文档自成体系 | 支持机制闭环、接口明确、外部数据单独维护 | 承诺外部机制怎么改都不牵连钓鱼；复制所有鱼表、道具表来实现自给自足 |

**建议顺序：先定职责与接口（需求 3），再拆分并重排（需求 2），最后加引导句（需求 1）。** 首要问题是规则归属混杂，其次是阅读顺序；加一句话无法弥补必须跨页找关键判定的结构问题。

“全部裁决完成”不等于“全部实现规格完备”。整合稿仍明示鱼饵权重矩阵、基础池、运动求解细节、换人闭环等缺口。本次重构必须保留这些缺口的状态和责任，不能靠改写把它们变成已定规则。

## 二、需求 1：按机制群加引导句，不按标题逐个铺

### 2.1 粒度与摆放

以“读者需要建立一个新的因果认识”为粒度。一个机制群只加一句，放在标题后、出处注记与公式前；同群下的数据定义、边界、验算、术语表不再加。现有首句已经直观的，直接精简或替换，不另叠一层。

例如窝点建立、投放与补窝可以共用入口；咬钩计时、抽鱼扣减、衰减、聚鱼窗口各有不同因果，应各有入口。搏斗一章不能只给总导语：响应奖励、力量与装备检查、体力消耗、线长交换、失败出口要分别说清。只有字段表的 §4.2、数据流总览 §2.8、术语速查 §1.2，不因是三级标题就配一句。

建议主文约 14—16 句，多人附篇约 4—6 句，总计 18—22 句。候选落点为准备、窝点投补、计时、抽扣、衰减、聚鱼、渔网、抛竿、提竿、强度检查、搏斗消耗、收放线、失败、收鱼及昼夜边界；相邻且首句已够清楚的合并。多人侧覆盖合力移动、辅助、换人、抢收与贡献。

### 2.2 三个风格样例

| 机制 | 建议开头 | 这句话的边界 |
|---|---|---|
| 窝点投放与存量 | **一把窝料往这片水里添一批鱼。** | 建立“存量是鱼”的画面；三分量、整数、扣点、衰减取整仍只在正式规则处定义 |
| 搏斗消耗 | **猫顶住鱼的游动会消耗搏斗体力。** | 符合 N1 的抵抗做功；不把鱼猫距离不变写成免费，也不恢复 N9 已否定的“鱼歇免费” |
| 收放线 | **放线用线长换取更少的搏斗消耗。** | 表达 N7 的资源交换；不承诺放线必回体、不省略线尽后的强制对抗，也不覆盖腿部消耗 |

风格要像在描述眼前的动作，少用“银行、印钞机、命条”等跨体系比喻。尤其不能把“形象化”变成“鱼闹收费、鱼歇免费”这种记忆鲜明但已经错误的口号。词语“休息”若保留作演出名，须避免让读者误认为鱼意图速度归零。

### 2.3 与受控冗余的关系及篇幅

库规明确允许一句结论与标注快照的数字冗余，但规定“判定条件、公式、清单成员只在唯一出处写”，且“冗余结论句不得含从句”。因此引导句应是一个简单结论，不含“当……且……时……”等条件，不塞阈值、例外、公式或完整结果枚举。上面的三句符合这个方向；右栏解释属于本次评估，不应一起塞进每节开头。

引导句不承担验收定义。若一句话只有附带三个例外才正确，应缩窄这句话的主语或适用对象；不能以“只是比喻”为由保留误导表述。多人附篇对基础规则最多给这种结论句和直达链接，不复写公式。

指定整合稿实测有 **48 个三级小节、约 27,810 个非空白字符**（包含 Markdown、表格、公式，不是纯汉字字数）。按 18—22 句、每句约 20—30 字，正文新增约 **360—660 字**，连同标记与必要过渡预留 **500—750 字，约为原稿 2%—3%**。这是引导句的毛增量；替换现有首句、拆走第 6 章等带来的净缩减另算，不混在一起报“增长”。若逐个三级标题都加，约增加 960—1,440 字，还会多出 48 个阅读停顿，不划算。

主要风险是把结论简化成错误机制，以及让重复导语遮住规则。反对理由成立于“每节一条”的机械版本，不成立于按认知难点少量增补的版本。

## 三、需求 2：基础规则留共享语义，多人附篇只持扩展

### 3.1 四处指定边界的裁定

判断依据不是句中有没有“多人”，而是它决定了资源、对象和事务的什么基本性质。还必须留出第三类“局级编排”，不能硬塞进基础钓鱼或多人合作二选一。

| 当前位置 | 裁定与最终去向 | 原因与必须保住的口径 |
| §2.1 共享窝存量 | **全部基础语义留主文。** 同时保留 §2.2 多次投料累加、§2.3 每漂独立计时 | 窝是服务器持有的世界资源，不是某个玩家的私有副本。人数为一时仍使用同一个模型；几何归属、创建序、边界包含关系也不能外移 |
| §2.4 同窝多漂判序 | **留主文。** 抽鱼和扣库存的事务与判序写在一起 | 漂主当前饵选鱼、抽中即扣、基础池不扣、后续不回滚共同保证库存不透支。多人到点例用于验证基础语义；不能移走后只剩“随机出鱼” |
| §5.4 多人抢抄 | **拆句不拆事务。** 抢抄的热闹、竞争示例、合作分工进附篇；资格、所有猫可收、实物唯一归属、时间戳与席位序、失败硬直留主文 | “所有猫均可收”也是访问资格，不只是体验文案；删掉会暗示仅钓手可收。同 tick 的“收鱼→苏醒→落水”即使一人也适用，必须留下 |
| §6.3 按人数定任务 | **从钓鱼移交 62《局与进程》，不进多人附篇。** | 清晨人数快照决定当日目标，属于天循环和经济压力。一天一人也有任务；当天进退不重算是局级规则，不是合力能力。钓鱼不需要用每日任务数来运行 |

§2.4 可以引用主文同一处服务器判序约定；§5.4 已裁的时间戳并列按席位序应保留为公共约定。但不要把它推广成“所有事件只按先到先得”：不同事件已有不同优先序，换人并列、献祭与搬鱼同刻等仍有未定边界。

| §9.4 | **持竿者的位置落水、取等不落水、体力出口优先、放线不判位置落水回迁主文。** 辅助手不落水、归零弹出及是否退出合力留附篇；放线回复率缺口回挂主文资源接口 |
| §9.5 | **上钩者与实物持有人分离、两层图鉴的事件时点回迁主文输出接口。** 合力贡献资格、换人贡献与多人展示进附篇；图鉴消费归图鉴册 |

因此，第 8、9 章整体应拆，但不能原封不动剪走。基础规则目前借住其中；先回迁公共部分，再搬扩展部分。

### 3.3 引用方向与统一计算

**规则依赖单向：多人附篇 → 基础钓鱼规则。导航允许双向。** 主文首页可列“多人扩展见附篇”的链接，这不构成机制依赖；主文任何一条基础判定都不能以“具体条件见多人”才能成立。附篇必须直达对应机制或接口，不能先跳主文目录再跳别册。

统一模型建议由主文持有 `F_total`（本次对抗有效力量）和 `K_pos`（参与者消耗倍率）等扩展输入：无辅助时，`F_total` 取持竿猫当前力量、`K_pos=1`。主文持有瞬断、碾压、鱼体力扣减和猫体力消耗公式，以及“有效力量变化时重新检查”的入口。附篇只给总力量如何由主辅组成、各角色传入什么倍率、加入退出和换人如何触发入口。**不能在附篇再抄一套消耗公式，也不能让主文只剩抽象变量而没有一人运行的默认值。**

### 3.4 主文与附篇建议目录

主文建议仍称《钓鱼规则》，页首声明“适用于单人及多人共同使用的基础机制”。先给一竿流程，术语就近解释，完整速查移末尾。

| 新章 | 内容与旧稿来源 |
|---|---|
| 1. 一竿流程与准备 | 一屏流程：备装→可选打窝→抛竿→等待／试探→真咬／提竿→搏斗→收鱼／失败；旧 §2.7、§3.1 的钓鱼侧准备条件 |
| 2. 打窝、等待与抽鱼 | 旧第 1、2 章的有效规则，含独立浮漂计时、抽扣事务、基础池、渔网与死水 |
| 3. 抛竿与提竿 | 旧第 3 章、§4.1；落点、换饵、扣饵与道具闸门 |
| 4. 搏斗与退出 | 旧 §4.2—4.7，回迁 §9.4 基础落水，统一力量／消耗／线长模型 |
| 5. 收鱼与归属 | 旧第 5 章，含叼鱼态、抄取／翻肚／拾取、服务器判序及捕获事件 |
| 6. 外部接口与生命周期 | 输入数据、行为输出接口、渔获交接、入夜／强制中断／翻天／局结束；旧第 6 章只保留钓鱼侧责任 |
| 7. 信息与反馈 | 旧第 7 章及 §4.5、§5.6 的信号需求；素材细节不重复成动作清单 |
| 文末附录 | 术语与参数定位、裁决出处索引、集中缺口及对应验收点 |

多人附篇建议按“范围与基础引用→合力钓鱼的加入、力量、退出、换人→抢收、贡献、求助与展示→合力移动→多人缺口”组织。先接主文的搏斗流程，再讲合力移动，避免当前读者先学移动合力才找到搭手钓鱼。

主要风险是拆完出现循环引用、两个公式版本，或者把所有猫可抢鱼改成钓手专属。反对理由是多人本来就是本作核心，拆分可能削弱体验整体感；解决办法是首页保留多人入口和一段合作体验概览，不用保留实现规则的交叉依赖来维持整体感。

## 四、需求 3：去掉文档强耦合，保留必要语义接口

### 4.1 “自成体系”的验收定义

主文应能独立回答：一竿怎么开始、如何抽扣、怎么搏斗、成功或失败怎么结账、外部中断来了怎么办。读者只带接口数据，就能运行一人基础流程；无需阅读其他分册的叙述才能补齐状态转移。

鱼种、配方、装备参数和动画资产仍由各自唯一出处提供。其增删、调值或文案重排不应要求改写钓鱼算法。**字段单位、状态含义、交易时点、鱼行为能力边界改变，仍必须联审。** 完全没有这种牵连不合理：比如把鱼意图改为可随时归零，会直接破坏 N9；换一个“行为服务”的名字也隔离不了这个语义冲突。

区分三种引用：出处引用用于溯源，可保留在附录；规范引用意味着不读外页就不知道机制，须内收或接口化；数据引用指向唯一配置表，应保留。材料 10／20／30、50、70 主要属于出处链，不应继续成为现行正文阅读的前置步骤。已有表格的数值权威不因重构转移。

### 4.4 接口至少要写到什么程度
