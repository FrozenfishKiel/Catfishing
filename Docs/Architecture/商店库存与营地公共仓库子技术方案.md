# 商店库存与营地公共仓库子技术方案

文档状态：摊位库存组件实现同步版，等待 UE 编译与 PIE 验证。

更新时间：2026-08-28

适用范围：商店出售表、商店随机刷新、购买结算、购买物发放到营地公共仓库、玩家从营地公共仓库取用到个人装备库存。

不覆盖范围：最终价格数值、最终刷新时机、正式 WBP 视觉排版、尚未落正式装备定义的道具资产。

## 已确认口径

- 商店本身按一个“库存型 Model”理解：它有当前可售条目、库存数量、刷新版本和交易记录。
- 商店仍走 MVC：View 只展示和发起 EntryId；Controller 转发购买意图；Model/Service 读取表并完成权威校验。
- 商店出售内容必须来自表。购买时也以当前表生成出来的商店库存为权威，UI 不能提交价格、数量或物品定义。
- 商店会随机刷新，但现在不确定由谁、何时触发。实现时只预留服务端刷新接口或函数，不绑定每日、开局、打开商店或营地阶段。
- 初级鱼竿、初级鱼饵、初级鱼漂每次刷新都必须出现。
- 固定商品之外的商品进入随机池，用一个单独结构数组保存；刷新时从随机池抽取若干条导入当前商店库存。
- 购买成功后，商品全部进入团队库存/公共装备库。本文把这个概念落成“营地公共仓库”，不再额外拆出两个名字。
- 营地公共仓库本质是一个库存对象，但需要单独设计为 Actor 类，因为它是玩家公共取用、商店发货和营地交互的核心入口。
- 物品进入库存时继续复用“按物品定义决定怎么添加”的口径：能堆叠的按堆叠规则进格子；不能堆叠或存在独立状态的按实例/单格处理。

## 当前源码事实

- 个人装备库存当前主要在 `UCatEquipmentComponent`，槽位数据是 `FCatRunInventorySlot`：`DefinitionId + Quantity`。它已经有同定义优先堆叠、空槽补位、栈上限和容量检查。
- `UCatEquipmentDefinition` 是装备/消耗品运行时定义。`Kind`、`bRunConsumable`、`MaxStackSize` 等字段能判断鱼竿、鱼漂、鱼饵、窝料等该如何入库存。
- `UCatItemsService` 当前主要是真鱼/鱼箱容器服务。虽然类型里有 Equipment/Consumable 枚举，但实际转移非鱼对象时仍是 `PolicyUndecided`，不能把它直接当公共装备仓库使用。
- 当前商店表挂在 `ACatShopKioskActor` 自带的 `UCatShopInventoryComponent` 上；源码仍保留组件内联固定/随机数组和 `UCatShopCatalogDefinition` 资产入口，但这些属于旧口径，后续重构应迁移到策划维护的 DataTable。
- `UCatShopEconomySettings` 只保留团队公款、经济开关和售鱼估价策略，不再保存任何商店出售表或免费领取白名单。
- 当前购买链路由 `UCatShopOrderCoordinator` 在扣款前预检营地公共仓库，再把购买物发到 `ACatCampInventoryActor`，不再直发购买者个人 `UCatEquipmentComponent`。
- 当前发货目标不再挂在商店摊位上：PageController 只记住来源摊位作为距离证明，服务器下单时全图检测 `ACatCampHubActor`，并让营地通过 `ResolvePublicInventoryForShopOrder()` 返回自己的公共仓库。
- 当前 UI 仍只发 EntryId。`UCatShopModel` 从当前公开货架过滤随机商品，`UCatShopWidget` 必须通过 `ShopButtons` 容器按 `ViewState.Entries` 动态生成当前货架按钮；商品按钮只有这一条正式生成路径。
- 当前营地公共仓库交互的根页面不复用默认背包页；`ACatCampInventoryActor.InventoryViewClass` 应指向独立的 `/Game/UI/Inventory/WBP_CatCampInventory`，父类为 `UCatCampInventoryWidget`。这只决定打开哪个组合页面，不代表 C++ 要裁掉玩家随身库存；页面内部可以嵌入背包子 WBP，共享同一份完整库存投影，并用库存页自己的 SlotSource 过滤拆出玩家背包区和公共仓库区。

## 最终数据表形态

不要继续把商店商品散在 `DefaultGame.ini` 的 `CatalogEntries` 里，也不要继续让 `UCatShopInventoryComponent` 的 C++ 默认数组或 `UCatShopCatalogDefinition` 资产承担正式商品表。最终商店商品应来自策划维护的 `UDataTable`：

`UDataTable` with `FCatShopCatalogTableRow : FTableRowBase`

建议资产路径：

`/Game/Catfishing/Data/Shop/DT_ShopCatalog_Default`

选择 DataTable 的原因是：商店商品规模会持续扩展，新增商品、改价、改分类、改排序、上下架和随机权重都应由策划配表完成。程序只维护行结构、加载校验、运行转换和交易裁决，不逐个维护商品。若刷新规则需要独立配置，可以另设轻量规则表或摊位配置；商品行本身仍统一来自 DataTable。

### 出售条目结构

`FCatShopCatalogTableRow` 是“真正能卖什么”的基础结构。固定商品和随机候选都在同一张表中表达。

```cpp
USTRUCT(BlueprintType)
struct FCatShopCatalogTableRow : public FTableRowBase
{
	GENERATED_BODY()

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	FName EntryId = NAME_None;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	ECatShopEntryKind EntryKind = ECatShopEntryKind::Unknown;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	FName DisplayCategoryId = NAME_None;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	FName DefinitionId = NAME_None;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	int32 UnitPrice = -1;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	int32 PurchaseQuantity = 1;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	int32 InitialStock = 0;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	bool bUnlimitedStock = false;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	bool bEnabled = true;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	FName RequiredShopUnlockId = NAME_None;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	FName RefreshPoolId = NAME_None;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	int32 RefreshWeight = 0;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	int32 MinRefreshedStockOverride = -1;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	int32 MaxRefreshedStockOverride = -1;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	FText DisplayNameOverride;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	FText DescriptionOverride;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	TSoftObjectPtr<UTexture2D> IconOverride;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	int32 SortOrder = 0;
};
```

字段口径：

| 字段 | 用途 | 规则 |
| --- | --- | --- |
| `EntryId` | 售卖条目 ID，UI 和交易只传它 | 整张表内唯一 |
| `EntryKind` | 展示和旧账本类别提示 | 运行目录不允许 Unknown；真正入库方式仍由物品定义和目标库存裁决 |
| `DisplayCategoryId` | 商品页分类 | 不等于 `EntryKind`；“全部”由 UI 虚拟生成 |
| `DefinitionId` | 购买后要加入库存的物品定义 | 必须能在 `UCatEquipmentSettings` 找到 runtime-ready 定义 |
| `UnitPrice` | 单次购买价格 | `-1` 表示未配置，运行时 fail closed；`0` 表示免费 |
| `PurchaseQuantity` | 单次购买给多少个 | 默认 1，鱼饵/窝料可配置为多份 |
| `InitialStock` | 刷新后本条库存 | 有限库存使用；无限库存可为 0 |
| `bUnlimitedStock` | 是否不限量 | 初级保底物品通常为 true |
| `bEnabled` | 是否进入运行货架候选 | false 时保留配置但不参与刷新和展示候选 |
| `RequiredShopUnlockId` | 商店解锁条件 | 当前没有可信解锁事实源，必须留空；非空条目不上架也不能购买 |
| `RefreshPoolId` | 随机池 ID | 为空表示固定货架或按摊位规则直接上架；非空表示进入对应随机候选池 |
| `RefreshWeight` | 随机抽取权重 | 随机候选必须大于 0；固定货架可为 0 |
| `MinRefreshedStockOverride` | 随机库存下限 | `-1` 表示使用 `InitialStock` |
| `MaxRefreshedStockOverride` | 随机库存上限 | `-1` 表示使用 `InitialStock`；小于下限时配置无效 |
| `DisplayNameOverride` | 商店展示名覆盖 | 留空时使用物品定义的显示名 |
| `DescriptionOverride` | 商店描述覆盖 | 留空时使用物品定义描述 |
| `IconOverride` | 商店图标覆盖 | 留空时使用物品定义图标 |
| `SortOrder` | 展示排序 | 固定商品可排前，随机商品排后 |

### 刷新规则结构

固定货架和随机候选都由 DataTable 行表达。一次刷新从同一张表中筛出 `bEnabled=true` 的行：没有随机池 ID 的行直接进入当前货架，有随机池 ID 的行按池和权重抽取后进入当前货架。每个摊位抽哪个池、每个池抽几条，可以由摊位配置或轻量刷新规则表提供；触发时机仍不写进商品表。

摊位库存组件进入 World 或被显式刷新时，会从 DataTable 生成当前商店库存快照。这个快照继续使用 `FCatShopStockSnapshot`，并额外携带 `ShopInventoryId`，避免多个摊位使用同名 EntryId 时串货。

## 刷新设计

预留服务端函数：

```cpp
bool RefreshShopInventoryFromCatalog(UCatShopInventoryComponent* ShopInventory,
    const FGuid& RequestId, const FCatShopRefreshRequest& Request);
```

刷新流程：

1. 读取来源 `UCatShopInventoryComponent` 上配置的正式商店 DataTable；未配置或加载失败时关闭本摊位目录，不回退到旧 C++ 默认商品。
2. 校验 DataTable 行：`EntryId` 唯一、`DefinitionId` 有效、价格已配置、数量大于 0、库存配置合法、展示分类可读、随机池字段自洽。
3. 把固定上架行写入当前商店库存。
4. 按 `RefreshPoolId` 分组随机候选，并按 `RefreshWeight` 不放回抽取摊位规则要求的数量。
5. 被抽中的随机商品写入当前商店库存；如果配置了随机库存区间，则在区间内生成本次库存，否则使用 `InitialStock`。
6. 重建当前商店库存并发布新的商店快照给 GameState/UI；旧 `ShopCatalog`、`FixedSaleEntries`、`RandomSaleEntries` 和 C++ 默认数组不再参与正式刷新。

暂不决定谁调用刷新。后续 Run、营地、GM、测试命令或运营工具都可以调用这个函数，但不能把触发时机写死在 Catalog 读取里。

## 购买与发货流程

目标链路：

```text
Shop UI -> Shop PageController -> PlayerController Server RPC（携带来源商店摊位作距离证明）
-> PlayerController 全图检测 ACatCampHubActor
-> ACatCampHubActor 判断并返回可用公共仓库
-> UCatShopOrderCoordinator
-> UCatShopEconomyService 验证价格/库存/钱包
-> ACatCampInventoryActor 接收商品
-> Shop Ledger 确认交付
```

关键规则：

- UI 只提交 `EntryId`。
- 发货目标由服务器全图检测营地获得；商店摊位只用于确认玩家仍在摊位交互范围内，不配置营地引用。
- 营地通过 `ACatCampHubActor::ResolvePublicInventoryForShopOrder()` 判断自己当前是否能接收商店发货；没有营地或营地缺公共仓库时，购买在扣款前失败并返回错误。
- 价格、数量、DefinitionId、库存都从当前商店库存快照读，不接受客户端参数。
- 付款前先检查营地公共仓库是否能接收这批物品；仓库满或定义无效时，不扣钱、不扣商店库存。
- 交易成功后扣团队钱包、扣商店库存，再把物品加入营地公共仓库。
- 加入仓库时不看商店条目的 `Kind` 来决定发货方式，而是读取 `UCatEquipmentDefinition`：消耗品走可堆叠数量，鱼竿/鱼漂/抄网等走单件/实例口径。
- 交易记录继续保留 EntryId、DefinitionId、价格、数量、库存版本、钱包版本和发货状态，方便幂等和追查。

## 营地公共仓库设计

新增 Actor：

`ACatCampInventoryActor`

建议目录：

`Source/Catfishing/Camp/`

职责：

- 作为营地公共仓库的世界对象和服务端权威入口。
- 保存公共库存槽位、库存版本和必要的复制快照。
- 接收商店购买后的发货。
- 提供玩家从公共仓库取到个人装备库存的服务端接口。

不建议直接把 `UCatEquipmentComponent` 挂到营地上。原因是它不仅是库存，还承担个人装备栏、自动选中、鱼竿耐久和玩家当前装备语义。营地仓库只需要公共库存，不应该继承玩家个人装备状态。

首版直接把公共库存 Model 收进 `ACatCampInventoryActor`，不再额外拆 `UCatCampInventoryComponent`。它复用 `FCatRunInventorySlot` 的槽位形态和 `UCatEquipmentDefinition` 的栈规则，但 API 面向公共仓库：

```cpp
ECatDomainCommandError ValidateAddItemFromAuthority(FGuid RequestId, int64 ExpectedRevision, FName DefinitionId, int32 Quantity) const;
FCatDomainCommandResult AddItemFromAuthority(FGuid RequestId, int64 ExpectedRevision, FName DefinitionId, int32 Quantity);
ECatDomainCommandError ValidateWithdrawToEquipment(FGuid RequestId, int32 SourceSlotIndex, int32 Quantity, UCatEquipmentComponent* TargetEquipment) const;
FCatDomainCommandResult WithdrawToEquipmentFromAuthority(FGuid RequestId, int64 ExpectedCampRevision, int32 SourceSlotIndex, int32 Quantity, UCatEquipmentComponent* TargetEquipment, int64 ExpectedEquipmentRevision);
```

营地对商店只暴露一个小接口：

```cpp
ACatCampInventoryActor* ResolvePublicInventoryForShopOrder() const;
```

这个接口只回答“本营地现在有没有可用公共仓库”，不负责扣款、不负责写入商品。真正入库仍由 `ACatCampInventoryActor` 的正式入库接口完成。

取用流程：

```text
玩家在营地交互 -> PlayerController Server RPC
-> 校验玩家是否能访问该营地仓库
-> 校验仓库槽位和数量
-> 校验玩家个人 UCatEquipmentComponent 是否能接收
-> 仓库扣减
-> 个人装备库存增加
-> 双方递增版本并复制快照
```

## MVC 落点

商店：

| 层 | 现有/目标类 | 职责 |
| --- | --- | --- |
| Model | `UCatShopInventoryComponent`、`UCatShopEconomyService`、`UCatShopModel` | 摊位组件生成并持有货架库存；服务维护钱包和交易快照；Model 只读两者 |
| View | `UCatShopWidget` / `WBP_CatShop` | 展示条目、价格、库存、是否可买 |
| Controller | `UCatShopPageController`、PlayerController RPC、`UCatShopOrderCoordinator` | 把 EntryId 意图转成服务端购买流程 |

营地公共仓库：

| 层 | 目标类 | 职责 |
| --- | --- | --- |
| Model | `ACatCampInventoryActor` | 保存公共库存和版本 |
| View | `WBP_CatCampInventory` / `UCatCampInventoryWidget` | 作为营地自己的组合库存页面，读取完整库存投影；子库存页可设置 `InventoryObject` 或 `CampInventoryObject` 过滤，分别展示玩家随身库存区和公共仓库区 |
| Controller | PlayerController RPC / 仓库 PageController | 处理从公共仓库取到个人装备库存 |

## 最小实现顺序

1. 新增商店 Catalog 数据结构，并让 `UCatShopInventoryComponent` 成为摊位自己的出售表和运行货架库存。
2. 改造商店服务加载逻辑：服务只注册摊位库存组件并聚合公开快照，不再从全局 Settings 生成当前商店库存。
3. 新增 `ACatCampInventoryActor`，先支持 `DefinitionId + Quantity` 的入库、堆叠、容量、复制快照。
4. 改造 `UCatShopOrderCoordinator`：购买成功后发货到营地公共仓库，而不是玩家个人装备库存。
5. 新增公共仓库到个人装备库存的取用接口。
6. 更新 UI Model 展示：固定商品永远出现，随机商品按当前商店库存快照展示。
7. 后续验收关注：表校验、刷新结果、固定商品保底、随机池抽取、购买按表扣款、仓库满不扣款、购买入公共仓库、玩家取用入个人库存。本轮按最新指令不写测试代码。

## 需要避免的错误方向

- 不把价格、库存或购买数量放进 UI。
- 不让客户端传 DefinitionId、价格或数量。
- 不继续让商店购买直接发到个人装备库存。
- 不把 `UCatItemsService` 当前鱼箱容器硬当公共装备仓库。
- 不为了“未来万能物品系统”新增大而全的通用物品框架。
- 不把商店出售表和装备定义混成一张表；装备定义描述物品是什么，商店出售表描述它怎样卖。
- 不在刷新触发时机没裁定前写死每日刷新、开店刷新或 Run 开始刷新。

## 待裁但不阻塞结构的问题

- 每个随机商品的正式价格、单次购买数量和刷新库存。
- 一次刷新抽几个随机商品。
- 虫虫窝料是固定付费常驻，还是只进入随机池。
- 商店刷新到底由营地阶段、天数、Run 开始、手动测试命令还是运营入口触发。
- 后续如果鱼竿、鱼漂出现耐久、词条、改造等实例差异，营地仓库需要从 `DefinitionId + Quantity` 升级为带 `ObjectInstanceId` 的实例槽位；首版不预先引入这层复杂度。

## 验证计划

- 静态配置验证：Catalog 中所有 EntryId 唯一，所有 DefinitionId runtime-ready，固定商品包含 `StarterRodT1`、`BugBait`、`FeatherFloat`。
- 刷新验证：任意刷新结果都包含固定商品；随机商品数量符合规则；禁用或权重为 0 的商品不会出现。
- 购买验证：UI 只传 EntryId；服务端按 Catalog 价格、数量和库存结算；余额不足、库存不足、仓库满都不会扣款。
- 发货验证：购买成功后公共仓库增加对应物品，玩家个人装备库存不直接增加。
- 取用验证：玩家从公共仓库取用后，公共仓库扣减，个人装备库存增加，并遵守个人库存容量和堆叠规则。

### 本轮商店营地检测人工验收

阅读导航：

- 交互打开入口先看 `Source/Catfishing/UI/Shop/CatShopInteractionComponent.cpp` 的 `OpenShopForPlayer`，重点确认打开页面只需要来源摊位和 WBP，不检查营地。
- 购买发货入口从 `Source/Catfishing/Framework/Game/CatGameplayTypes.cpp` 的 `SubmitShopOrder` 开始看：来源摊位只做距离证明，公共仓库由当前 World 中的 `ACatCampHubActor::ResolvePublicInventoryForShopOrder()` 提供。
- 公共仓库页面接线先看 `Source/Catfishing/Camp/CatCampInventoryActor.h/.cpp`，重点确认 `InventoryViewClass` 走营地自己的根页面类；资产侧要补齐 `/Game/UI/Inventory/WBP_CatCampInventory`，父类是 `UCatCampInventoryWidget`。如果页面里嵌入玩家背包子 WBP，它由父页自动接收同一份 ViewState，不需要额外打开默认背包；背包区把过滤设为 `InventoryObject`，公共仓库区把过滤设为 `CampInventoryObject`。

手工步骤：

1. 在测试关卡中只放商店摊位，不放营地或不给营地配置公共仓库，进入 PIE 后靠近摊位按 `E`。预期：商店 UI 可以打开并显示可购买条目。
2. 在没有可用营地公共仓库的情况下尝试购买或免费领取任一条目。预期：UI 显示“没有可用营地公共仓库，未扣款”；团队货币不扣减，商店库存不扣减，公共仓库不新增物品，玩家个人装备库存也不新增物品。
3. 在同一关卡放置有效 `ACatCampHubActor`，并让该营地配置可接收物品的 `PublicInventory`，重新进入 PIE 后打开商店并购买同一条目。预期：购买成功后按 Catalog 扣款和扣商店库存，购买物进入该营地 `PublicInventory` 对应的公共仓库，玩家个人装备库存不直接增加。
4. 直接与 `ACatCampInventoryActor` 交互打开公共仓库。预期：页面类来自 `ACatCampInventoryActor.InventoryViewClass`，实际打开的是独立根页面 `WBP_CatCampInventory`，不是把默认 `WBP_CatInventory` 当根页面。
5. 在公共仓库页里观察格子内容并选中一格。预期：页面能同时拿到 `InventoryObject` 随身库存格和 `CampInventoryObject` 公共仓库格；如果 WBP 做了两个区域，背包区域不应为空，公共仓库区域也不应混用玩家格。
6. 对公共仓库里一个有物品的格子执行右键取用。预期：客户端只提交取用请求，服务器复核后把物品转入玩家个人装备库存；取用成功时公共仓库扣减、玩家个人装备库存增加，失败时两边都不应出现本地提前改格。
