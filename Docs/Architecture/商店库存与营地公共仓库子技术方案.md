# 商店库存与营地公共仓库子技术方案

文档状态：摊位库存组件实现同步版；本轮 UE 编译检查已通过，PIE 未验证。

更新时间：2026-08-28

适用范围：商店出售表、商店随机刷新、购买结算、购买物发放到营地公共仓库、玩家从营地公共仓库取用到个人随身库存。

不覆盖范围：最终价格数值、最终刷新时机、正式 WBP 视觉排版、尚未落正式装备定义的道具资产。

## 已确认口径

- 商店本身按一个“库存型 Model”理解：它有当前可售条目、库存数量、刷新版本和交易记录。
- 商店仍走 MVC：View 只展示和发起 EntryId；Controller 转发购买意图；Model/Service 读取表并完成权威校验。
- 商店出售内容必须来自表。购买时也以当前表生成出来的商店库存为权威，UI 不能提交价格、数量或物品定义。
- 商店会随机刷新，但现在不确定由谁、何时触发。正式入口是服务端刷新接口，不绑定每日、开局、打开商店或营地阶段。
- 初级鱼竿、初级鱼饵、初级鱼漂每次刷新都必须出现。
- 固定商品之外的商品进入随机池，用一个单独结构数组保存；刷新时从随机池抽取若干条导入当前商店库存。
- 购买成功后，商品全部进入营地公共仓库，公共物品归属只使用这个仓库入口。
- 营地公共仓库本质是一个库存对象，但需要单独设计为 Actor 类，因为它是玩家公共取用、商店发货和营地交互的核心入口。
- 物品进入库存时继续复用“按物品定义决定怎么添加”的口径：能堆叠的按堆叠规则进格子；不能堆叠或存在独立状态的按实例/单格处理。

## 当前源码事实

- 个人随身库存事实当前由 `UCatInventoryComponent` 承载，槽位数据是 `FCatInventoryEntry`：每格保存正式物品实例和堆叠数量。`UCatEquipmentComponent` 只保留钓鱼选择读模型；鱼竿耐久、鱼重量和来源等专属运行状态始终由 entry 中的实例持有，UI、Save 与 Fishing 都从实例读取需要的领域数据。
- `UCatEquipmentDefinition` 是装备/消耗品运行时定义。它保留通用身份、钓具槽和部署配置；入口通过对应 Fragment 读取鱼竿耐久/线长、鱼饵咬钩倍率、浮漂射程、抄网范围或窝料影响，判断物品能否进入对应流程。
- `UCatFishContainerService` 当前只是真鱼/鱼箱容器服务。正式道具实例、随身背包和营地公共仓库都由 `Inventory/` 承载，不能把鱼容器服务当公共装备仓库使用。
- 当前商店表由 `ACatShopKioskActor` 自带的 `UCatShopInventoryComponent` 读取策划维护的 `DT_ShopCatalog_Default` DataTable；商品只从 DataTable 进入运行货架。
- `UCatShopEconomySettings` 只保留团队公款、经济开关和售鱼估价策略；商店出售表和免费领取白名单不归它保存。
- 当前购买链路由 `UCatShopTradeController` 在扣款前预检营地公共仓库，再把购买物发到 `ACatCampInventoryActor`；个人 `UCatEquipmentComponent` 不是发货目标。
- 当前发货目标由营地提供：PageController 只记住来源摊位作为距离证明，服务器下单时全图检测 `ACatCampHubActor`，并让营地通过 `ResolvePublicInventoryForShopOrder()` 返回自己的公共仓库。
- 当前 UI 仍只发 EntryId。`UCatShopModel` 从当前公开货架过滤随机商品，`UCatShopWidget` 必须通过 `ShopButtons` 容器按 `ViewState.Entries` 动态生成当前货架按钮；商品按钮只有这一条正式生成路径。
- 当前营地公共仓库交互的根页面不复用默认背包页；`ACatCampInventoryActor.InventoryViewClass` 应指向独立的 `/Game/UI/Inventory/WBP_CatCampInventory`，父类为 `UCatCampInventoryWidget`。这只决定打开哪个组合页面，不代表 C++ 要裁掉玩家随身库存；页面内部可以嵌入普通背包子 WBP 和营地页，分别读取同一份 ViewState 的 `InventorySlots` 与 `CampInventorySlots`。

## 最终数据表形态

商店商品不写入配置或 C++ 默认表；正式商品来自策划维护的 `UDataTable`：

`UDataTable` with `FCatShopCatalogTableRow : FTableRowBase`

资产路径：

`/Game/Catfishing/Data/Shop/DT_ShopCatalog_Default`

选择 DataTable 的原因是：商店商品规模会持续扩展，添加商品、改价、改分类、改排序、上下架和随机权重都应由策划配表完成。程序只维护行结构、加载校验、运行转换和交易裁决，不逐个维护商品。若刷新规则需要独立配置，可以另设轻量规则表或摊位配置；商品行本身仍统一来自 DataTable。

### 出售条目结构

`FCatShopCatalogTableRow` 是“真正能卖什么”的基础结构。固定商品和随机候选都在同一张表中表达。

```cpp
USTRUCT(BlueprintType)
struct FCatShopCatalogTableRow : public FTableRowBase
{
	GENERATED_BODY()

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	FName EntryId = NAME_None;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	FName DisplayCategoryId = NAME_None;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	FName DefinitionId = NAME_None;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	int32 UnitPrice = -1;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	int32 PurchaseQuantity = 1;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	int32 InitialStock = 0;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	bool bUnlimitedStock = false;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	bool bEnabled = true;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	FName RequiredShopUnlockId = NAME_None;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	FName RefreshPoolId = NAME_None;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	int32 RefreshWeight = 0;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	int32 MinRefreshedStockOverride = -1;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	int32 MaxRefreshedStockOverride = -1;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	FText DisplayNameOverride;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	FText DescriptionOverride;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	TSoftObjectPtr<UTexture2D> IconOverride;

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	int32 SortOrder = 0;
};
```

字段口径：

| 字段 | 用途 | 规则 |
| --- | --- | --- |
| `EntryId` | 售卖条目 ID，UI 和交易只传它 | 整张表内唯一 |
| `DisplayCategoryId` | 商品页分类 | 不写成 C++ enum；“全部”由 UI 虚拟生成 |
| `DefinitionId` | 购买后要加入库存的物品定义 | 必须能在 `UCatInventorySettings` 找到 runtime-ready 定义 |
| `UnitPrice` | 单次购买价格 | `-1` 表示未配置，运行时 fail closed；`0` 表示免费 |
| `PurchaseQuantity` | 单次购买给多少个 | 默认 1，鱼饵/窝料可配置为多份 |
| `InitialStock` | 刷新后本条库存 | 有限库存使用；无限库存可为 0 |
| `bUnlimitedStock` | 是否不限量 | 初级保底物品通常为 true |
| `bEnabled` | 是否进入运行货架候选 | false 时保留配置但不参与刷新和展示候选 |
| `RequiredShopUnlockId` | 商店解锁条件 | 当前没有可信解锁事实源，必须留空；非空条目不上架也不能购买 |
| `RefreshPoolId` | 随机池 ID | 为空表示固定货架或按摊位规则直接上架；非空表示进入对应随机候选池 |
| `RefreshWeight` | 随机抽取权重 | 随机候选必须大于 0；固定货架可为 0 |
| `MinRefreshedStockOverride` | 随机库存下限 | `-1` 表示使用 `InitialStock` |
| `MaxRefreshedStockOverride` | 随机库存上限 | `-1` 表示使用 `InitialStock`；小于下限时配置无效 |
| `DisplayNameOverride` | 商店展示名覆盖 | 留空时使用物品定义的显示名 |
| `DescriptionOverride` | 商店描述覆盖 | 留空时使用物品定义描述 |
| `IconOverride` | 商店图标覆盖 | 留空时使用物品定义图标 |
| `SortOrder` | 展示排序 | 固定商品可排前，随机商品排后 |

### 刷新规则结构

固定货架和随机候选都由 DataTable 行表达。一次刷新从同一张表中筛出 `bEnabled=true` 的行：没有随机池 ID 的行直接进入当前货架，有随机池 ID 的行按池和权重抽取后进入当前货架。每个摊位抽哪个池、每个池抽几条，可以由摊位配置或轻量刷新规则表提供；触发时机仍不写进商品表。

摊位库存组件进入 World 或被显式刷新时，会从 DataTable 生成当前商店库存快照。这个快照继续使用 `FCatShopStockSnapshot`，并额外携带 `ShopInventoryId`，避免多个摊位使用同名 EntryId 时串货。

### 不进入运行表

- `FlashingBait`、`SoundBait`、`GiantLureBait`：资产存在，但飞书当前口径里“假饵/特殊饵”仍偏演示或未完整落地，不应默认进商店。
- 逗猫棒竿/T3：策划表有概念，但当前未核到对应正式装备资产。
- 抄网、鱼护、小鱼干、爪爪套、湿毛器、渔网/捞捞网等：策划总表里出现过，但当前不是完整可售装备定义，不能直接放进运行商店表。
- 应急线组：不进商店。
- 幸运四叶草、恶作剧假鱼、响响筒：当前更像钓鱼意外或表现道具，不按普通商店商品处理。

## 刷新设计

服务端刷新接口：

```cpp
bool RefreshShopInventoryFromCatalog(UCatShopInventoryComponent* ShopInventory,
    const FGuid& RequestId, const FCatShopRefreshRequest& Request);
```

刷新流程：

1. 读取来源 `UCatShopInventoryComponent` 上配置的正式商店 DataTable；未配置或加载失败时关闭本摊位目录。
2. 校验 DataTable 行：`EntryId` 唯一、`DefinitionId` 有效、价格已配置、数量大于 0、库存配置合法、展示分类可读、随机池字段自洽。
3. 把固定上架行写入当前商店库存。
4. 按 `RefreshPoolId` 分组随机候选，并按 `RefreshWeight` 不放回抽取摊位规则要求的数量。
5. 被抽中的随机商品写入当前商店库存；如果配置了随机库存区间，则在区间内生成本次库存，否则使用 `InitialStock`。
6. 重建当前商店库存并发布新的商店快照给 GameState/UI；刷新只消费正式 DataTable 生成的目录项。

刷新入口由 Run、营地、GM、测试命令或运营工具按各自生命周期调用；Catalog 读取只提供商品定义，不承担刷新时机。

## 购买与发货流程

目标链路：

```text
Shop UI -> Shop PageController -> PlayerController Server RPC（携带来源商店摊位作距离证明）
-> PlayerController 全图检测 ACatCampHubActor
-> ACatCampHubActor 判断并返回可用公共仓库
-> UCatShopTradeController
-> UCatShopEconomyService 验证价格/库存/钱包
-> ACatCampInventoryActor 接收商品
-> Shop Ledger 确认交付
```

关键规则：

- UI 只提交 `EntryId`。
- 发货目标由服务器全图检测营地获得；商店摊位只用于确认玩家仍在摊位交互范围内，不配置营地引用。
- 营地通过 `ACatCampHubActor::ResolvePublicInventoryForShopOrder()` 判断自己当前是否能接收商店发货；没有营地或营地缺公共仓库时，购买在扣款前失败并返回错误。
- 价格、数量、DefinitionId、库存都从当前商店库存快照读，不接受客户端参数。
- 付款前先检查营地公共仓库是否能接收这批物品；仓库满或定义无效时，不扣钱、不扣商店库存。
- 交易成功后扣团队钱包、扣商店库存，再把物品加入营地公共仓库。
- 加入仓库时读取库存定义自身的堆叠/实例语义；数量型消耗物走可堆叠数量，工具、装备和部署型物品走单件实例口径。
- 交易记录继续保留 EntryId、DefinitionId、价格、数量、钱包版本和发货状态，方便幂等和追查。

## 营地公共仓库设计

现有 Actor：

`ACatCampInventoryActor`

源码目录：

`Source/Catfishing/Camp/`

职责：

- 作为营地公共仓库的世界对象和服务端权威入口。
- 作为正式 `UCatInventoryComponent` 的空间宿主，由组件保存公共库存槽位和复制观察面。
- 接收商店购买后的发货。
- 参与通用库存移动命令；玩家随身背包和公共仓库之间只走正式库存移动接口。

营地不挂 `UCatEquipmentComponent`。这个组件承担个人装备栏、自动选中、鱼竿耐久和玩家当前装备语义；营地仓库只需要公共库存，不能继承玩家个人装备状态。

当前正式版本直接把公共库存宿主收在 `ACatCampInventoryActor`，库存状态只由它持有的正式 `UCatInventoryComponent` 管理。商店发货面向公共仓库，玩家整理和背包/仓库移动统一面向正式库存组件：

```cpp
UCatInventoryComponent* GetInventoryComponent() const;
bool RestoreInventorySlotsFromAuthority(const TArray<FCatInventoryEntry>& RestoredSlots, FText& OutFailure);
bool ExportInventorySlotsFromAuthority(TArray<FCatInventoryEntry>& OutSlots, FText& OutFailure) const;
```

营地对商店只暴露一个小接口：

```cpp
ACatCampInventoryActor* ResolvePublicInventoryForShopOrder() const;
```

这个接口只回答“本营地现在有没有可用公共仓库”，不负责扣款、不负责写入商品。真正入库由公共仓库上的正式 `UCatInventoryComponent` 完成。

背包/仓库移动流程：

```text
玩家在营地交互打开仓库页
-> UI 只提交源宿主、目标宿主和两侧槽位
-> PlayerController Server RPC
-> UCatInventoryStatics 校验玩家、可达性和两个正式 InventoryComponent
-> Source UCatInventoryComponent 按同一套堆叠/交换规则提交
-> 如果玩家随身库存参与移动，Equipment 刷新只读投影和钓鱼选择
-> 双方正式库存标记变更条目并复制
```

## MVC 落点

商店：

| 层 | 现有/目标类 | 职责 |
| --- | --- | --- |
| Model | `UCatShopInventoryComponent`、`UCatShopEconomyService`、`UCatShopModel` | 摊位组件生成并持有货架库存；服务维护钱包和交易快照；Model 只读两者 |
| View | `UCatShopWidget` / `WBP_CatShop` | 展示条目、价格、库存、是否可买 |
| Controller | `UCatShopPageController`、PlayerController RPC、`UCatShopTradeController` | 把 EntryId 意图转成服务端购买流程 |

营地公共仓库：

| 层 | 目标类 | 职责 |
| --- | --- | --- |
| Model | `ACatCampInventoryActor` + `UCatInventoryComponent` | Actor 提供世界交互宿主，正式库存组件保存公共库存条目 |
| View | `WBP_CatCampInventory` / `UCatCampInventoryWidget` | 作为营地自己的组合库存页面，读取完整库存投影；普通背包子页读取 `InventorySlots`，营地页读取 `CampInventorySlots`，两者都用宿主与槽位提交命令 |
| Controller | PlayerController RPC / 仓库 PageController / `UCatInventoryStatics` | 把拖拽、整理和右键移动都提交为同一类库存移动意图，并在玩家随身库存参与时刷新钓具选择摘要 |

## 当前运行入口

1. `UCatShopInventoryComponent` 是摊位自己的出售表和运行货架库存入口。
2. `UCatShopEconomyService` 注册摊位库存组件并聚合公开快照。
3. `ACatCampInventoryActor` 持有正式 `UCatInventoryComponent`，负责公共仓库入库、堆叠、容量和复制观察。
4. `UCatShopTradeController` 在购买成功后发货到营地公共仓库。
5. 通用库存移动命令覆盖公共仓库内部整理、个人背包内部整理、公共仓库和个人背包之间移动。
6. UI Model 展示固定商品和随机商品时只读取当前商店库存快照。
7. 验收关注：表校验、刷新结果、固定商品保底、随机池抽取、购买按表扣款、仓库满不扣款、购买入公共仓库、通用库存移动、移动后保存和重启读档。验证时必须确认公共仓库和随身库存都来自正式 `UCatInventoryComponent`。

## 需要避免的错误方向

- 不把价格、库存或购买数量放进 UI。
- 不让客户端传 DefinitionId、价格或数量。
- 不继续让商店购买直接发到个人随身库存。
- 不把 `UCatFishContainerService` 当前鱼箱容器硬当公共装备仓库。
- 通用物品框架不属于本链路边界。
- 不把商店出售表和装备定义混成一张表；装备定义描述物品是什么，商店出售表描述它怎样卖。
- 不在刷新触发时机没裁定前写死每日刷新、开店刷新或 Run 开始刷新。

## 待裁但不阻塞结构的问题

- 每个随机商品的正式价格、单次购买数量和刷新库存。
- 一次刷新抽几个随机商品。
- 虫虫窝料是固定付费常驻，还是只进入随机池。
- 商店刷新到底由营地阶段、天数、Run 开始、手动测试命令还是运营入口触发。
- 后续如果鱼竿、鱼漂出现更多耐久、词条或改造差异，在对应 Inventory Item Instance 子类保存运行状态，并以新增定义 Fragment 表达静态能力；营地仓库始终保留同一实例身份。

## 验证计划

- 静态配置验证：Catalog 中所有 EntryId 唯一，所有 DefinitionId runtime-ready，固定商品包含 `StarterRodT1`、`BugBait`、`FeatherFloat`。
- 刷新验证：任意刷新结果都包含固定商品；随机商品数量符合规则；禁用或权重为 0 的商品不会出现。
- 购买验证：UI 只传 EntryId；服务端按 Catalog 价格、数量和库存结算；余额不足、库存不足、仓库满都不会扣款。
- 发货验证：购买成功后公共仓库增加对应物品，玩家个人随身库存不直接增加。
- 移动验证：玩家从公共仓库移动物品到个人随身库存后，公共仓库和个人随身库存的正式组件都按同一套容量、堆叠和交换规则变化；已离开随身库存的钓具选择必须被清理或切换到仍在随身库存的合法实例。
- 保存验证：公共仓库和随身库存互相移动后立即保存，保存导出必须从 `ACatCampInventoryActor::ExportInventorySlotsFromAuthority` 与玩家正式库存读取事实；重启游戏进程后读取同一存档，物品所在库存和装备选择不能回到先前快照或悬空实例。

### 本轮商店营地检测人工验收

阅读导航：

- 交互打开入口先看 `Source/Catfishing/UI/Shop/CatShopInteractionComponent.cpp` 的 `OpenShopForPlayer`，重点确认打开页面只需要来源摊位和 WBP，不检查营地。
- 购买发货入口从 `Source/Catfishing/Framework/Game/CatfishingPlayerController.cpp` 的 `SubmitShopCart` 开始看：来源摊位只做距离证明，公共仓库由当前 World 中的 `ACatCampHubActor::ResolvePublicInventoryForShopOrder()` 提供。
- 公共仓库页面接线先看 `Source/Catfishing/Camp/CatCampInventoryActor.h/.cpp`，重点确认 `InventoryViewClass` 走营地自己的根页面类；资产侧要补齐 `/Game/UI/Inventory/WBP_CatCampInventory`，父类是 `UCatCampInventoryWidget`。如果页面里嵌入玩家背包子 WBP，它由父页自动接收同一份 ViewState，不需要额外打开默认背包；普通背包子页读取 `InventorySlots`，营地页读取 `CampInventorySlots`，每个格以库存宿主与宿主内槽位定位。
- 背包/公共仓库移动入口先看 `Source/Catfishing/UI/Inventory/CatInventoryPageController.cpp` 的移动提交，再看 `Source/Catfishing/Framework/Game/CatfishingPlayerController.cpp` 的 `ServerMoveInventoryItemBetweenHosts`、`Source/Catfishing/Inventory/CatInventoryStatics.cpp` 的 `MoveItemBetweenInventoryHostsFromAuthority` 和 `Source/Catfishing/Inventory/CatInventoryComponent.cpp` 的 `MoveItemToInventoryFromAuthority`；它们只应把源宿主、目标宿主和两侧槽位交给服务器复核。
- 保存导出入口先看 `Source/Catfishing/Save/CatSaveSubsystem.cpp` 写入 `CampInventory` 的路径，再看 `Source/Catfishing/Camp/CatCampInventoryActor.cpp` 的 `ExportInventorySlotsFromAuthority`、`RestoreInventorySlotsFromAuthority`；营地库存只导出正式组件槽位。

手工步骤：

1. 在测试关卡中只放商店摊位，不放营地或不给营地配置公共仓库，进入 PIE 后靠近摊位按 `E`。预期：商店 UI 可以打开并显示可购买条目。
2. 在没有可用营地公共仓库的情况下尝试购买或免费领取任一条目。预期：UI 显示“没有可用营地公共仓库，未扣款”；团队货币不扣减，商店库存不扣减，公共仓库不增加物品，玩家个人随身库存也不增加物品。
3. 在同一关卡放置有效 `ACatCampHubActor`，并让该营地配置可接收物品的 `PublicInventory`，重新进入 PIE 后打开商店并购买同一条目。预期：购买成功后按 Catalog 扣款和扣商店库存，购买物进入该营地 `PublicInventory` 对应的公共仓库，玩家个人随身库存不直接增加。
4. 直接与 `ACatCampInventoryActor` 交互打开公共仓库。预期：页面类来自 `ACatCampInventoryActor.InventoryViewClass`，实际打开的是独立根页面 `WBP_CatCampInventory`，不是把默认 `WBP_CatInventory` 当根页面。
5. 在公共仓库页里观察格子内容并选中一格。预期：页面能同时拿到 `InventorySlots` 随身库存格和 `CampInventorySlots` 公共仓库格；如果 WBP 做了两个区域，背包区域不应为空，公共仓库区域也不应混用玩家格。
6. 对公共仓库里一个有物品的格子执行右键移动。预期：客户端只提交源宿主、目标宿主和两侧槽位；服务器复核后把物品转入玩家个人随身库存。成功时公共仓库和玩家个人随身库存一起变化，失败时两边都不应出现本地提前改格。
7. 把当前已经被 Equipment 选中的鱼饵、鱼漂、鱼竿或抄网从随身库存移动到公共仓库后，立刻通过局内菜单点保存。预期：保存成功；不能再出现“装备选择没有指向同一份库存中的正确实例”这类失败。若随身库存里还有同类合法实例，Equipment 选择应切到该实例；没有同类实例时应清空对应选择。
8. 结束 PIE 或重启游戏进程后读取同一存档。预期：刚才移动到公共仓库的物品仍在公共仓库，移动到随身库存的物品仍在随身库存；公共仓库内容来自正式库存组件导出的存档，不应回到营地快照或只保留 UI 曾显示过的状态。
