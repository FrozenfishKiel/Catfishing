## 核心结论

属性集不是“把所有数字放到一个类里”。GAS AttributeSet 的底层价值是让一组稳定领域事实进入 `GameplayEffect` 聚合、捕获、修改、复制、预测和回调体系：属性有 Base / Current，有 Modifier 聚合，有 GE 生命周期，有 Attribute capture，有 `PreAttributeChange`、`PreAttributeBaseChange`、`PostGameplayEffectExecute` 这些统一约束点。它适合保存“会被 GE 改、会被计算捕获、需要被网络同步为玩法事实”的数值，不适合保存事务 ID、状态机枚举、实例数组、空间场、账本和高频模拟中间量。

Catfishing 应套用 Lyra 的结构思想，而不是照抄字段：

```text
ACatCharacter
  -> Character ASC
  -> UCatSurvivalAttributeSet
  -> 猫身体属性、身体 GE、动作 Ability、身体 GameplayTag

ACatfishingGameState
  -> Run ASC
  -> UCatRunAttributeSet
  -> UCatRunModifierAttributeSet
  -> 全队共享最终额度属性、局内来源倍率、献祭数值计算

ACatfishingGameModeBase / UCatSacrificeCoordinator
  -> Run / Items 事务协议、StateTree 事件、幂等、Revision、补偿

ACatFishingSession
  -> 固定步长会话模拟、鱼体力、线长、张力、线耐久、会话结算
```

第一刀应该从献祭额度开刀：新增 GameState Run ASC、`UCatRunAttributeSet` 和 `UCatRunModifierAttributeSet`；最终集只放 `QuotaTarget`、`QuotaProgress`，来源集只放 `QuotaTargetMultiplier`、`DailyPressure`、`SacrificeEfficiency`。外部献祭入口、Items 预留与提交、Run 预检、Revision 幂等和 StateTree 达标事件仍保留在现有 Coordinator / GameMode 协议里。GAS 接管“数值怎么算和怎么写”，不接管“这条命令是否有资格提交”。

## 设计目标

1. 属性分域：身体属性归 Character ASC，局内公共额度归 GameState Run ASC，高频 FishingSession 状态、Items/Shop 事务和 Environment/Social 空间协议不混进角色属性集。
2. 计算收口：能被 GE 捕获和修饰的数值统一通过 AttributeSet、GameplayEffect、ExecutionCalculation 或必要的 MMC 计算；不再在 UI、Session、Component、GameMode 各自手写同一公式。
3. 行为不漂移：首轮迁移默认倍率全部为 1，沿用当前 `UCatRunSettings::QuotaTarget`、鱼实例冻结贡献和当前可超额语义，保证重构后游戏仍能按现有规则进行。
4. 事务不降级：`RequestId`、`ExpectedRevision`、`ExpectedRunRevision`、Items 预留、Items 不可逆提交、Run 达标事件继续由原领域拥有，不能因为引入 AttributeSet 破坏并发和补偿协议。
5. 可继续扩展：后续成长 Buff、天气压力、祭坛加成、鱼饵/窝料影响可以通过 GE 修改相关 Attribute 或 SetByCaller 输入，不需要再绕到多个服务里补公式。

## 属性系统治理范式

本次要建立的不是“更多 AttributeSet”，而是一套数值治理模块。AttributeSet 只负责保存适合 GAS 聚合的运行时事实；同一模块还必须规定原始输入来自哪里、最终公式在哪里、其他系统怎么读、谁可以写，以及旧写口什么时候删。否则只是把一部分字段搬家，数值仍会继续乱算。

统一范式分四层：

| 层级 | 职责 | 可以保存什么 | 不可以做什么 |
| --- | --- | --- | --- |
| 内容与配置输入层 | 保存设计师配置、DataAsset、Settings、实例冻结值 | 鱼定义、装备定义、RunSettings、ConditionSettings、已捕获鱼冻结贡献 | 不保存“已被 Buff/环境/倍率修饰后的最终值”。 |
| Attribute 事实层 | 保存会被 GE 改、会被捕获、需要复制的运行时数值 | `Poison`、`FishingStrength`、`FightStamina`、`MaxFightStamina`、`QuotaTarget`、`QuotaProgress`、`QuotaTargetMultiplier`、`DailyPressure`、`SacrificeEfficiency` | 不保存数组、账本、事务 ID、阶段枚举、空间目标、高频模拟中间量。 |
| 计算层 | 集中最终公式、clamp、取整、倍率组合和溢出策略 | ExecCalc、MMC、AttributeSet 回调、必要的纯 C++ 公式 helper | 不允许 UI、GameMode、Session、Component 再复制一份最终公式。 |
| 投影与接入层 | 给非 GAS 模块提供稳定只读快照和少量命令入口 | `FCatRunPublicState`、Fishing 派生快照、Condition/Growth/UI 只读 View | 不暴露可随意写属性的旁路，不让调用方直接拼 GE 细节。 |

实现时用以下硬规则约束后续模块：

- 每个玩法数值必须登记唯一所有者：Character ASC、Run ASC、某个领域 Aggregate、DataAsset/Settings 或派生快照，不能没有归属。
- 局内可变、会被 Buff/Debuff/环境/难度/活动修饰、需要服务器权威复制的连续数值，优先进入 AttributeSet 或由 AttributeSet 派生快照统一输出。
- DataAsset 和 Settings 只提供原始输入。任何“最终战斗力”“最终献祭贡献”“最终目标额度”“最终效率倍率”都不能直接从资产值临时相乘得出。
- 非 GAS 模块可以拥有事务和生命周期，但不能拥有最终数值公式。它们要么提交原始输入给属性系统，要么读取属性系统投影后的快照。
- AttributeSet 不提供任意 setter。服务器写入必须通过初始化边界、GameplayEffect、ExecutionCalculation 或明确的 Attribute Owner 方法；客户端和 UI 只能读投影。
- 重构完成后，旧的直接写口必须删除或改成调用统一入口，不能长期保留“新 GAS 口径”和“旧手写口径”两套结果。

反扩展硬约束：

- 不因为“属性系统应该完整”而新建空 AttributeSet、空 Component、空 Subsystem、空 Manager、空 Registry 或只转发一行调用的 helper。
- 不新增运行时“全局数值注册中心”。本文的数值登记表是实现前和审查时使用的归属清单；只有当代码需要稳定 tag、属性访问或日志枚举时，才把必要常量落到代码里。
- 不把单调用点公式提前抽公共文件。先放在 ExecCalc `.cpp` 私有 namespace 或 Owner 私有方法中；出现第二个真实调用点，且复制公式会造成行为风险时，再提升为公共 helper。
- 不为未来玩法预留接口。没有现成调用方、没有当前公式、没有验证路径的字段和方法不进代码，只保留在未决问题或后续路线里。
- 不为了“所有模块都接入”把事务、空间场、高频模拟、展示参数硬塞进 AttributeSet。接入属性系统的意思是使用统一数值读写口径，不是把所有数据结构变成 GAS 字段。
- 每个新增类型、方法、快照和写口都必须通过删除测试：删掉它以后，如果复杂度没有回到多个调用方或多个公式里，它就不该存在。

首轮对外接口应尽量小，避免把所有模块都绑死在 GAS 类型上：

| 接口类型 | 建议形态 | 调用方 | 作用 |
| --- | --- | --- | --- |
| Run 数值快照 | `FCatRunAttributeSnapshot` 或 GameState 只读 getter | GameMode、HUD、UI、Debug | 读取目标、当前进度、倍率、压力和效率的权威投影。 |
| Character 数值快照 | ASC / Character 提供只读构建方法 | Fishing、Condition、HUD、Debug | 读取身体属性，避免模块直接到处拿 AttributeSet 指针后各自组合。 |
| Fishing 派生快照 | `FCatFishingDerivedStatsSnapshot` | FishingService、FishingSession | 一次性冻结角色、装备、鱼定义、鱼性格、环境和窝料输入，生成模拟配置。 |
| Run 写入命令 | GameMode/Run Owner 的少量方法 | SacrificeCoordinator、StateTree | 开始新一天、提交已通过事务检查的献祭贡献。 |
| Character 写入命令 | ASC 现有方法收口后保留 | Condition、Growth、Fishing | 施加中毒、恢复、体力消耗、成长 Buff，不暴露直接加减属性。 |

这些接口的目的不是隐藏 GAS，也不是增加包装层，而是让其他模块只依赖“我要一个权威数值”或“我要提交一个已裁定的数值输入”，不用知道本轮到底是 AttributeSet、ExecCalc、MMC 还是 Meta Attribute 在工作。每个接口都必须有实际调用方和删除收益；没有实际调用方时，只写在方案里，不落代码。

## 其他模块接入与影响边界

这次重构一定会改其他模块代码。合理边界不是“不影响别人”，而是“影响方式统一、可搜索、可删除旧口径”。下面是各模块必须改到的方向：

| 模块 | 必须接入属性系统的部分 | 仍由模块自己拥有的部分 | 禁止保留的旧口径 |
| --- | --- | --- | --- |
| Run / GameMode | `QuotaTarget`、`QuotaProgress` 的最终计算和投影，以及 `QuotaTargetMultiplier`、`DailyPressure`、`SacrificeEfficiency` 的来源捕获 | Phase、Deadline、Revision、StateTree 事件、幂等终态 | 在 GameMode 中手写 `QuotaProgress + Contribution` 或自行组合目标倍率。 |
| Sacrifice / Items | 提交鱼实例冻结贡献给 Run 写口，读取 Run 结果 | 预留、提交、补偿、库存 Revision、`RequestId` | 献祭点回查鱼定义、临时计算效率、绕过 Run ASC 改额度。 |
| UI / HUD | 只读 `RunPublicState` 或数值快照 | 页面状态、按钮可用性、展示格式 | UI 构造命令时漏传 `ExpectedRunRevision`，或自己预估最终贡献当作权威结果。 |
| Character / AbilitySystem | 身体属性、Meta Attribute、初始化和 GE 写口 | Character 生命周期、输入、BodyAction gate | 在 ASC 包装方法里重复 clamp，或在 Character 初始化外随意 `SetNumericAttributeBase`。 |
| Condition | 通过 Character 写口施加中毒/恢复，按属性快照做倒地裁决 | 湿身、倒地状态、恢复模式、草药距离 | 保存第二份 Poison 或在 Condition 中直接改 AttributeSet 值。 |
| Growth | 选择 Buff 后施加 GE，成长带来的数值变化进入 Character/Run 属性 | 经验槽、待选次数、选择流程 | 在 Growth Snapshot 中保存“成长后的力量/效率”供 Fishing 或 Run 旁路读取。 |
| FishingService / FishingSession | 通过统一派生快照读取角色属性、装备表现、鱼/环境输入 | 高频模拟状态、鱼运动、线长、张力、会话结算 | Session 内直接散读 ASC、Settings、Equipment 后手写最终力量和体力组合。 |
| FishCatalog | 从派生快照读取最终参与者能力，继续负责候选过滤和权重 | 鱼表、挑战比、随机选择、时段/天气过滤 | 自己重新计算一套角色总战力，或把每条鱼候选变成 Attribute。 |
| Equipment / Items | 装备定义作为原始输入进入派生快照，Buff 后最终表现从属性系统输出 | 库存、耐久、破损、数量、容器事务 | 装备系统保存第二份最终钓力、最终线长、最终咬钩倍率。 |
| Environment / Chum | 天气、事件、窝料如果影响目标、效率、咬钩或挑战，应施加 GE 或进入派生快照 | 天气枚举、时段、空间场、自然事件、采样向量 | 在 Environment 中直接改 Run DTO 数值，或让 FishSelection 和 Run 各写一份压力公式。 |
| Social | 未来数值 Buff/Debuff 通过 GameplayTag/GE 进入对应属性或派生快照 | 偷鱼、保护牌、求助、距离和冷却裁决 | 把保护/惩罚效果写成目标模块的临时乘法分支。 |
| ShopEconomy | 未来折扣、通胀、卖鱼倍率可成为 Economy/Run 属性输入 | 钱包余额、库存、价格表、交易账本 | 把可叠加经济倍率散落在购买、售卖、UI 预览三个入口。 |

因此，“影响其他模块”的控制方式是：

- 只改数值读写闭包内的调用路径，不顺手重构事务、UI 样式、资产结构或无关状态机。
- 每一阶段先保留行为等价的默认值，再删除旧直接写口；不能只新增新口而留下旧口继续可用。
- 对每个模块提供一个明确迁移点：读最终值走快照，写数值变化走 Owner 命令，原始内容值仍从原模块取。
- 交付时用源码搜索证明旧公式和旧写口已经不存在，或明确列出因蓝图/资产风险暂留的入口。

## 当前属性与玩法数值分类

| 最终归属 | 当前数值或事实 | 当前来源 | 重构口径 |
| --- | --- | --- | --- |
| Character ASC / `UCatSurvivalAttributeSet` | `Poison`、`FishingStrength`、`FightStamina` | 现有 AttributeSet | 保留在 Character ASC，补齐约束、Meta Attribute 和统一 GE 写口。 |
| Character ASC 新增上限 | `MaxFightStamina` | `UCatAbilitySettings`、`UCatCharacterDefinition::FightStaminaMaximum`、搏斗配置中的 `CatStaminaMaximum` | 加入身体属性集，作为 `FightStamina` 的上限和初始化基线；首轮默认等于现有配置。 |
| Character Meta Attribute | `IncomingPoison`、`IncomingPoisonRecovery`、`IncomingFightStaminaDelta` | 当前分散在 ASC 包装方法和 GE SetByCaller | 非复制，仅用于 Instant GE 输入；在 `PostGameplayEffectExecute` 转成真实属性并清零。 |
| Run ASC / `UCatRunAttributeSet` | `QuotaTarget`、`QuotaProgress` | 当前 `FCatRunPublicState` 与 `UCatRunSettings` | 新增 GameState Run ASC 后成为最终额度真相；首轮保持旧行为。 |
| Run ASC / `UCatRunModifierAttributeSet` | `QuotaTargetMultiplier`、`DailyPressure`、`SacrificeEfficiency` | 默认 1，未来由 Run/Environment/祭坛/成长等 GE 写入 | 作为额度公式来源属性被 ExecCalc 捕获；不保存最终目标、进度、阶段或环境枚举。 |
| Run 公开投影 | `FCatRunPublicState.QuotaTarget`、`QuotaProgress`、`Revision`、`Phase`、`Environment`、`EndReason` | GameMode 写、GameState 复制 | 继续是 UI/客户端只读 DTO；额度字段切换后只从 Run AttributeSet 投影，不再自己计算。 |
| Run 配置输入 | `DayLengthSeconds`、`QuotaTarget`、`PlayerScalingPolicy`、`FinalDayIndex`、`SuccessSettlementPolicy` | `UCatRunSettings` | 保持 Settings；`QuotaTarget` 作为 `BaseQuotaTarget` 输入 Run GE。`DayLengthSeconds` 与阶段策略不是 Attribute。 |
| 献祭鱼实例冻结值 | `FCatFishInstance.SacrificeContribution`、`WeightKilograms`、`FishDefinitionId` | 捕获提交时从鱼定义冻结到实例 | 献祭 ExecCalc 只读冻结贡献，不回查 `UCatFishDefinition`，防止资产改值影响已捕获鱼。 |
| 献祭事务上下文 | `RequestId`、`ExpectedRevision`、`ExpectedRunRevision`、`StableNetId`、`FishInstanceId`、`ContainerId`、`ReservationId` | `FCatSacrificeCommand`、`FCatDomainCommandContext`、Items/Run Result | 保持 Command / Result / 协调器协议，绝不属性化。 |

## Lyra 套用口径

Lyra 给本项目的关键启发是“按事实宿主分 ASC 和 AttributeSet”，不是“所有数值都塞进一个属性集”：

- Lyra PlayerState/Character 持有玩家 ASC 与 Health/Combat 属性。Catfishing 当前决定是 Character-owned ASC，身体属性随局释放，因此首轮不把 ASC 迁到 PlayerState。
- Lyra HealthSet 把 `Health` / `MaxHealth` 当作真实状态，把 `Damage` / `Healing` 当作 Meta Attribute；ExecCalc 输出一次伤害，AttributeSet 再统一改真实生命值。Catfishing 的 `Poison`、`FightStamina` 和 `QuotaProgress` 应采用同一思路：一次输入先进入 Meta 或 ExecCalc，再由 AttributeSet 钳制和落真值。
- Lyra GameState 可以有 ASC，但 Lyra 不把所有比赛分数、助攻历史、UI 快照都放进 AttributeSet。Catfishing 的全队额度是单局公共可计算数值，适合 GameState Run ASC；但 Revision、阶段、Ready、偷鱼协议、购物车、容器数组仍然是领域状态。
- Lyra 的 GameFeature 可以动态授予 AttributeSet。本项目首轮不需要为了未来玩法做动态属性集；先保留固定 Character AttributeSet，并新增固定 Run 最终集和来源集。等成长 Buff、活动玩法或特殊祭坛真的需要动态属性时，再按 AbilitySet / GameFeature 风格扩展。

## 目标结构

### Character ASC

`ACatCharacter` 继续拥有现有 `UCatAbilitySystemComponent` 和 `UCatSurvivalAttributeSet`。首轮不移动 Owner/Avatar，不改输入 Ability；BodyAction 后续已从旧单网关拆成具体 GameplayEvent Ability，本文不再把它作为属性系统改造内容展开。

目标属性：

| 属性 | 类型 | 默认来源 | 写入者 | 读取者 | 约束 |
| --- | --- | --- | --- | --- | --- |
| `Poison` | 真实属性 | `UCatAbilitySettings` / CharacterDefinition | 中毒、吃鱼、草药、休息 GE | Condition、UI、调试 | 下限 0；是否上限需要产品裁定，首轮不新增硬上限。 |
| `FishingStrength` | 真实属性 | `UCatAbilitySettings` / CharacterDefinition | 初始 GE、成长 Buff GE、临时效果 GE | FishingService、FishingSession、鱼选择 | 下限 0；倍率型 Buff 不应直接改 DataAsset。 |
| `FightStamina` | 真实属性 | `MaxFightStamina` 或现有初始配置 | 搏斗消耗/恢复 GE、初始化 GE | FishingSession、HUD、能力 gate | 钳制到 `[0, MaxFightStamina]`。 |
| `MaxFightStamina` | 真实属性 | `FightStaminaMaximum` / `InitialFightStamina` | 初始 GE、成长 Buff GE、临时效果 GE | `FightStamina` clamp、FishingSession | 下限 1。Max 降低时同步钳制当前体力。 |
| `IncomingPoison` | Meta | SetByCaller | 鱼、环境、负面效果 | AttributeSet 内部 | 非复制，执行后清 0。 |
| `IncomingPoisonRecovery` | Meta | SetByCaller | 草药、休息、营地救援 | AttributeSet 内部 | 非复制，执行后清 0。 |
| `IncomingFightStaminaDelta` | Meta | SetByCaller | FishingFightRunner 或 Ability | AttributeSet 内部 | 非复制，执行后清 0。 |

首轮可以保留类名 `UCatSurvivalAttributeSet`，避免蓝图和生成代码引用断裂。等 Run AttributeSet 落稳后，再评估是否把它改名为 `UCatBodyAttributeSet`。若改名，必须配 Redirect、资产引用审计和构建验证，不能顺手改。

### GameState Run ASC

`ACatfishingGameState` 新增一个局内公共 ASC，Owner 和 Avatar 都是 GameState。这个 ASC 不处理输入，不授予角色 Ability，不保存个人物品。它只承载全队共享、需要 GE 计算和复制的 Run 数值，并稳定挂载最终额度集和来源倍率集。

首轮建议直接使用 `UAbilitySystemComponent` 作为 GameState 子对象，不复用 `UCatAbilitySystemComponent`，因为后者已经混入 Character 输入、BodyAction、Poison/FightStamina 便利方法。只有当 Run GE 构造、日志和 Attribute 查询逻辑在 GameMode 中膨胀时，再新增轻量 `UCatRunAbilitySystemComponent`。

`UCatRunAttributeSet` 最终属性：

| 属性 | 默认值 | 含义 | 写入者 | 读取者 | 约束 |
| --- | ---: | --- | --- | --- | --- |
| `QuotaTarget` | `UCatRunSettings::QuotaTarget` | 当天需要达到的献祭额度目标 | `GE_Run_StartDay` | GameMode、GameState 投影、HUD | 整数语义，至少 1。 |
| `QuotaProgress` | 0 | 当天已提交的献祭进度 | `GE_Run_StartDay` 重置，`GE_Run_ApplySacrifice` 增加 | GameMode 达标判定、GameState 投影、HUD | 整数语义，下限 0；首轮保留可超额。 |

`UCatRunModifierAttributeSet` 来源属性：

| 属性 | 默认值 | 含义 | 写入者 | 读取者 | 约束 |
| --- | ---: | --- | --- | --- | --- |
| `QuotaTargetMultiplier` | 1 | 全局目标倍率 | Run 规则、难度、成长或事件 GE | StartDay ExecCalc | 下限 0；首轮保持 1。 |
| `DailyPressure` | 1 | 当天压力系数 | Run/Environment 规则 GE | StartDay ExecCalc、UI | 下限 0；首轮保持 1。 |
| `SacrificeEfficiency` | 1 | 献祭效率倍率 | 祭坛、成长、活动或负面效果 GE | Sacrifice ExecCalc | 下限 0；首轮保持 1。 |

额度是整数语义，但 `FGameplayAttributeData` 底层是 float。实现时应把有效范围限制在 `0 .. 16777215` 内，避免超过 float 精确整数区间；正式业务仍使用 `int32` DTO 投影，所有 GE 输入和输出在边界取整。

`FCatRunPublicState` 继续复制给客户端。切换后它不再是额度计算真相，而是 Run AttributeSet 的公开投影：

```text
Run AttributeSet 真相
  -> GameMode 权威提交后读取属性
  -> 覆盖 FCatRunPublicState.QuotaProgress / QuotaTarget
  -> Revision 递增
  -> GameState 复制 OnRunPublicStateChanged
```

### FishingSession

不新增 FishingSession ASC。理由：

- `FCatFightSimulationState` 是固定步长高频状态，包含鱼体力、线长、张力、线耐久、运动意图、强对抗累计时间；这些每步改变，不适合每 0.05 秒走 GE 和复制。
- 鱼力量、鱼体力、鱼性格、竿强度、鱼饵/窝料影响来自 DataAsset、Settings、Equipment 和 Environment。它们是会话开始或参与者变化时冻结的输入，不是 Character 身体属性。
- Simulator 应保持纯计算核心。它接收 `FCatFightSimulationConfig` 和 `FCatFightSimulationState`，输出下一步状态和结果，不直接读取 ASC、DataAsset、GameState 或 UI。

需要新增的是一个统一的派生快照构建点，而不是新 ASC：

```text
Character ASC + Equipment Snapshot + FishDefinition + FishPersonality + FishingSettings + Environment/Chum/Bait
  -> FCatFishingDerivedStatsSnapshot
  -> FCatFightSimulationConfig / InitialState
  -> FCatFishingFightSimulator
```

## 献祭额度计算方案

### 当前协议必须保留

献祭不是一条简单的 `QuotaProgress += Value`。它跨 Items 和 Run 两个 Aggregate，当前已经有正确的协议骨架：

```text
UI / 祭坛 / BodyAction
  -> FCatSacrificeCommand
  -> UCatSacrificeCoordinator::RequestSacrifice
  -> Items ReserveFish
  -> Run Precheck
  -> Items Commit
  -> Run Apply
  -> GameState 发布结果
```

重构后仍然必须保留这个顺序。尤其是 `Items Commit` 后鱼已经不可逆消失，Run Apply 失败只能补 Run 或返回可审计错误，不能回滚鱼。GAS 只替换 Run Apply 阶段的数值公式和写口，不替换协调器、预检、幂等缓存或补偿规则。

### 已发现的高优先级缺口

UI 构造 `FCatSacrificeCommand` 时疑似只填了容器 `ExpectedRevision`，没有填 `ExpectedRunRevision`；但 `UCatSacrificeCoordinator` 会把 `ExpectedRunRevision` 转成 Run `QuotaCommand.Context.ExpectedRevision` 做预检。重构实现第一阶段必须先修这个缺口：

```text
Inventory UI / 祭坛 UI
  -> 读取 ACatfishingGameState::GetRunPublicState().Revision
  -> 写入 FCatSacrificeCommand.ExpectedRunRevision
  -> 服务端继续严格校验
```

不能为了让旧 UI 路径通过而放宽服务端 Revision 校验。正确修复是让发起端带齐运行事实，服务端仍 fail-closed。

### 公式

首轮行为保持：

```text
QuotaTargetMultiplier = 1
DailyPressure = 1
SacrificeEfficiency = 1
```

每日目标：

```text
EffectiveQuotaTarget =
  ClampInt(
    CeilToInt(BaseQuotaTarget * QuotaTargetMultiplier * DailyPressure),
    1,
    16777215)
```

其中 `BaseQuotaTarget` 来自 `UCatRunSettings::QuotaTarget`。当前 `PlayerScalingPolicy` 只允许 `FixedQuotaTarget`，所以首轮不引入人数缩放。未来若恢复人数缩放，应显式扩展公式：

```text
EffectiveQuotaTarget =
  CeilToInt(BaseQuotaTarget * PlayerScale * QuotaTargetMultiplier * DailyPressure)
```

献祭贡献：

```text
AppliedContribution =
  ClampInt(
    RoundToInt(FrozenSacrificeContribution * SacrificeEfficiency),
    MinContribution,
    16777215)
```

`FrozenSacrificeContribution` 必须来自 `FCatFishInstance.SacrificeContribution`，不能回查鱼定义。`MinContribution` 建议首轮为：

```text
MinContribution = FrozenSacrificeContribution > 0 && SacrificeEfficiency > 0 ? 1 : 0
```

这样效率大于 0 时不会把一条有价值的鱼因为小数舍入成 0；效率等于 0 时允许贡献为 0，用于未来明确的负面规则。若产品不接受“最低 1”，实现前必须单独裁决，不能隐藏在 ExecCalc 里。

进度：

```text
QuotaProgress =
  ClampInt(
    QuotaProgress + AppliedContribution,
    0,
    16777215)
```

首轮保留当前可超额语义，不把 `QuotaProgress` 钳到 `QuotaTarget`。如果未来要展示或结算超额，新增 `QuotaOverflow` 或独立 Result 字段；如果未来要封顶，必须作为产品规则变更单独验证。

这里的 `ClampInt` 只处理 AttributeSet 的数值安全上限，不表达玩法封顶。累计结果超过 `16777215` 时，首轮建议 fail-closed 拒绝本次 Run Apply，并返回结构化错误与日志，而不是静默饱和；静默饱和会让 Items 已提交后的补偿语义变得不可审计。若产品未来真的需要极高额度，应先把公开 DTO 和 GAS 表达改成明确的分段或非 Attribute 账本，而不是突破 float 精确整数区间。

### GE / ExecCalc / MMC 分工

| 计算 | 推荐实现 | 输入 | Capture | 输出 | 不负责 |
| --- | --- | --- | --- | --- | --- |
| 新一天额度目标 | `GE_Run_StartDay` + `UCatRunStartDayExecutionCalculation` | SetByCaller `Cat.Data.Run.BaseQuotaTarget` | `QuotaTargetMultiplier`、`DailyPressure` | Override `QuotaTarget`，Override `QuotaProgress = 0` | 不推进 StateTree，不开关钓鱼，不设置 deadline。 |
| 献祭提交 | `GE_Run_ApplySacrifice` + `UCatRunApplySacrificeExecutionCalculation` | SetByCaller `Cat.Data.Run.Sacrifice.RawContribution` | `SacrificeEfficiency`、当前 `QuotaProgress` 可选 | Additive `QuotaProgress += AppliedContribution` | 不校验鱼、不校验阶段、不处理 Items、不发 StateTree 事件。 |
| 单一标量倍率 | MMC 可选 | DayIndex、人数、天气、难度、Buff | 目标或源属性 | 一个 float magnitude | 不处理多字段覆盖、不做事务结算。 |

ExecutionCalculation 适合本轮主链，因为 StartDay 需要同时设置目标和重置进度，献祭需要 SetByCaller、捕获倍率、取整、审计日志和可超额语义。MMC 只适合“一个可复用标量”，例如未来把每日压力或人数缩放拆成独立可叠加算法时再引入。不要为了“用上 MMC”把简单逻辑拆散成多条难审的 MagnitudeCalculation。

公式应集中在一份纯 C++ 计算函数中，供 ExecCalc、日志、Debug 和未来 UI 预览复用：

```text
CatRunAttributeMath::ComputeQuotaTarget(...)
CatRunAttributeMath::ComputeAppliedSacrificeContribution(...)
```

如果实现时只有 ExecCalc 调用这两个函数，也可以先放在 ExecCalc `.cpp` 的私有 namespace 中；只有第二个调用者出现时再提升为公共 helper。

## 其他系统计算归属

### 中毒与恢复

`Poison` 继续属于 Character ASC。当前 `ApplyPoisonDelta` 在 ASC 包装层里做了非负 clamp，这个约束应迁进 `UCatSurvivalAttributeSet`：

```text
鱼毒性 / 草药 / 休息
  -> GE_ApplyPoison 或 GE_RecoverPoison
  -> IncomingPoison / IncomingPoisonRecovery
  -> PostGameplayEffectExecute
  -> Poison = Max(0, Poison + Delta)
  -> ConditionComponent 按 PoisonDownedThreshold 更新 Downed
```

`PoisonDownedThreshold`、恢复方式、草药距离、`bWet`、`bDowned`、`RecoveryMode` 仍属于 Condition。`Downed` 是状态裁决，不是连续属性；湿身目前只驱动表现，不进入属性系统。

### 吃鱼成长

`EatingExperience` 来自鱼定义，吃鱼提交后进入 Growth。`TotalExperience`、`ExperienceInCurrentSlot`、`PendingChoiceCount` 继续是 Growth Snapshot，不放进 Character AttributeSet。

成长真正影响数值时，正确链路是：

```text
Growth 满槽并完成三选一
  -> 选择一个已裁定 Buff
  -> 施加 GameplayEffect 到 Character ASC
  -> 修改 FishingStrength / MaxFightStamina / SacrificeEfficiency 等真实属性或倍率
```

Growth 不能保存第二份“成长后的力量”，否则 Fishing 会再次出现从 Growth、ASC、Settings 三处读数的混乱。

### 搏斗体力与搏斗资源

猫的 `FightStamina` 和 `MaxFightStamina` 属于 Character ASC。鱼的 `FishStamina`、线长、线耐久、张力和运动意图属于 FishingSession。

当前固定步长 Simulator 可保留，重构点是统一输入来源：

```text
参与者 Character ASC
  -> 读取 FishingStrength / FightStamina / MaxFightStamina
装备快照
  -> 读取鱼竿强度、线长、鱼饵、鱼漂、抄网
鱼定义与鱼性格
  -> 读取 FishStrength / FishFightStamina / Personality multipliers
FishingSettings
  -> 读取消耗、磨损、阈值、速度系数
  -> FCatFishingDerivedStatsSnapshot
  -> FCatFightSimulationConfig
```

首轮不要把每个搏斗 step 改成 ExecCalc。每步 GE 会增加复制和 GameplayEffect 生命周期成本，也会让确定性 Simulator 被 ASC 当前状态、预测窗口和网络时序污染。可以保留现有低频或步进后的 `ApplyFishingStaminaDelta`，但 AttributeSet 必须负责 clamp。

### 鱼种选择

鱼生成仍由鱼目录系统负责。它可以读取 Character ASC 形成 `CombinedFishingStrength` 和 `CombinedFightStamina`，也可以读取 `RunPublicState.Environment`、窝料采样、鱼饵定义和人数，但候选过滤、挑战比、权重随机和最终鱼定义选择不进入 AttributeSet。

挑战度公式继续集中在 `UCatFishCatalogSettings`：

```text
StrengthRatio = FishStrength / CombinedFishingStrength
StaminaRatio = FishFightStamina / CombinedFightStamina
BalancedRatio = HarmonicMean(StrengthRatio, StaminaRatio)
ChallengeRatio = Max(StrengthRatio, BalancedRatio)
```

如果未来成长或祭坛加成影响鱼生成，应以 Character ASC / Run ASC 的属性作为输入，再由鱼目录计算权重，而不是把每条鱼候选变成一个属性集合。

### 装备与道具

装备定义是内容输入，装备实例和库存是事务事实。不要把这些直接变成 Attribute：

- 鱼竿定义的强度、线长、磨损系数是会话配置输入。
- 鱼竿实例 `RodDurability` 是 Equipment Aggregate 的长期局内事实。
- 搏斗配置里的 `RodDurability` 当前实际表达“单场鱼线耐久”，每场从定义重置，并不等于装备实例耐久。
- 鱼饵、窝料、草药数量在库存里，使用时走 Equipment / Items 事务。

后续实现中建议把单场线耐久字段改名为 `MaximumFightLineDurability` 或等价名字，但这会触及源码和可能的资产引用，必须放在实现阶段做引用审计和 Redirect 策略。

### 环境与窝料

Environment 继续发布天气、时段和公共事件，ChumField 继续维护空间场：

```text
RunPublicState.Phase
  -> Environment provider
  -> Weather / TimeOfDay / ActiveEvent
  -> ChumFieldSubsystem 读取自然事件与窝料场
  -> FishSelection 采样 EffectiveChumVector
```

如果天气、自然事件或天数要提高当天压力，不把天气枚举本身属性化，而是由 Run/Environment 在服务器边界施加 GE 修改 `DailyPressure`。也就是说：

```text
RainBloom / DayIndex / Difficulty
  -> GE_SetDailyPressure
  -> RunModifierAttributeSet.DailyPressure
  -> 下次 StartDay 计算 QuotaTarget
```

窝料半径、时长、曲线、位置和采样贡献是空间事实，不适合 AttributeSet。

### 社交

偷鱼、恶作剧、保护牌、手动求助和重连白名单继续由 Social / Run 协议裁决。它们可以在未来给 Character 添加 GameplayTag，例如“处于保护区内”“正在求助窗口”，但半径、冷却、受保护目标、追回协议和 Signal Revision 不进入 AttributeSet。

### 商店经济与容器

团队公款、商品价格、库存、每日进货、售鱼估价、购物车、容器容量和容器 Revision 继续属于 ShopEconomy / Items Aggregate。它们依赖幂等、并发和账本，不应该降格成一个可被 GE 直接加减的 float。

未来只有当产品明确需要“全队折扣倍率”“通胀压力”“卖鱼收益 Buff”这类可被 GE 修饰的规则时，才新增 Economy AttributeSet 或把倍率放入 Run AttributeSet。即使那样，钱包余额和交易账本仍然不能属性化。

## 实施路线

### 阶段 0：方案冻结与写口盘点

目标：冻结本文的属性分类、公式和迁移边界，建立实现前的写口清单。

执行项：

- 搜索所有 `SetNumericAttributeBase`、`ApplyGameplayEffectSpecToSelf`、`QuotaProgress`、`QuotaTarget`、`SacrificeContribution`、`ExpectedRunRevision` 写口。
- 确认 `FCatFishInstance.SacrificeContribution` 是献祭唯一输入。
- 确认当前 `QuotaProgress` 是否允许超额；首轮按“允许超额”保留。
- 确认当前工作区 AbilitySystem 文件移动状态，避免把旧路径删除或新路径重构混在一起。
- 建立“数值登记表”，把每个玩法数值标成 Attribute、Meta Attribute、Settings 输入、DataAsset 输入、Aggregate 状态或派生快照输出。
- 标出每个旧公式的替换入口：Run 写口、Character 写口、Fishing 派生快照、Condition 裁决、Growth Buff、Equipment 输入、Environment GE 或 ShopEconomy 未来扩展。

保护：

- 不改行为，不改资产，不改测试。
- 只输出技术方案和后续实现清单。

### 阶段 0.5：最小统一数值接口骨架

目标：先让其他模块有稳定接入口，再迁移具体公式；避免每个模块直接学习 ASC、GE Spec 和 Attribute capture 细节，同时避免为了“架构完整”提前造一批空壳。

执行项：

- 只在第一个真实调用方迁移时定义对应快照：Run 额度快照、Character 身体属性快照或 Fishing 派生输入快照。没有调用方的快照不先落代码。
- 在 Run Owner 上提供少量写口：开始新一天、提交已通过事务检查的献祭贡献。SacrificeCoordinator 只把冻结贡献和 RequestId 交给 Run，不直接碰 AttributeSet；如果写口只是转发，先内联在现有 Run 方法中。
- 在 Character ASC 或 Character Owner 上收口身体属性写口：中毒、恢复、搏斗体力变化、成长 Buff。Condition、Growth、Fishing 调这些入口，不再各自夹带 clamp 或最终倍率；已有方法能表达语义时优先改深，不另起同义方法。
- 在 Fishing 构建流程中建立一个实际使用的快照构建点，负责把角色属性、装备定义、装备实例、鱼定义、鱼性格、环境、窝料和鱼饵组合成一次冻结输入；不新建只被构造一次又原样转发的中间 DTO。
- 给每个接口写明服务器权威、客户端只读、失败策略和日志字段；GE 构造失败、ASC 缺失或 AttributeSet 缺失必须 fail-closed，不能回退到旧公式。

保护：

- 接口只表达已确认的读写闭包，不为未来未定玩法预留一堆空方法。
- 快照是只读结果，不是新真相；真相仍在 AttributeSet、Aggregate、Settings、DataAsset 或 FishingSession 内。
- 这一步的“骨架”必须伴随真实调用迁移一起出现，不能先提交一堆暂无消费者的文件。

### 阶段 1：修复献祭命令运行版本

目标：先修现有 UI 命令缺口，确保属性化之前献祭协议本身稳定。

执行项：

- `CatInventoryPageController` 或对应祭坛/库存发起端读取 `ACatfishingGameState::GetRunPublicState().Revision`。
- 写入 `FCatSacrificeCommand.ExpectedRunRevision`。
- 保留服务端 `ExpectedRunRevision` 校验，不做兼容放宽。
- 增加 Development 日志，记录 `Event=SacrificeCommandBuilt`、`RunRevision`、`ContainerRevision`、`RequestId`，不要输出敏感身份。

保护：

- 预检仍在 Items 不可逆提交之前。
- 预检失败仍取消预留，不消费鱼。

### 阶段 2：收口 Character AttributeSet

目标：先把已经在 GAS 的身体属性变成真正的 AttributeSet，而不是只有复制字段。

执行项：

- 在 `UCatSurvivalAttributeSet` 增加 `MaxFightStamina` 和必要 Meta Attribute。
- 实现 `PreAttributeBaseChange` / `PreAttributeChange` / `PostGameplayEffectExecute`，统一钳制 `Poison >= 0`、`FishingStrength >= 0`、`MaxFightStamina >= 1`、`FightStamina` 在 `[0, MaxFightStamina]`。
- 把 `ApplyPoisonDelta` 中的 clamp 迁移到 AttributeSet，ASC 方法只负责创建 GE/Spec/SetByCaller。
- 保持 `CatPoisonEffect`、`CatFishingStaminaEffect` 对外入口兼容，避免一次性替换蓝图引用。
- 用初始化 GE 或集中 helper 替代零散 `SetNumericAttributeBase`，若首轮仍保留直接初始化，必须限制在角色初始化边界。

保护：

- 类名暂不改，避免资产断接。
- `ConditionComponent` 仍只做倒地裁决，不直接写属性。
- FishingSession 初始读取值应与当前行为一致。

### 阶段 3：引入 GameState Run ASC 稳定拓扑

目标：建立 Run ASC、最终属性集和来源属性集，让当天额度目标与当前额度先进入 GAS，再投影成旧 UI/StateTree 继续使用的公开 DTO。

执行项：

- `ACatfishingGameState` 实现 `IAbilitySystemInterface` 并提供明确的 Run ASC getter。
- 构造 `RunAbilitySystemComponent`、`UCatRunAttributeSet` 和 `UCatRunModifierAttributeSet`。
- 组件初始化后初始化 ActorInfo，Owner/Avatar 都是 GameState。
- GameMode 新一天开始时应用 Run GE 写入 `QuotaTarget` / `QuotaProgress`，再读取 Attribute 投影到 `RunPublicState`。
- 献祭提交后应用 Run GE 增加 `QuotaProgress`，再读取 Attribute 投影 DTO；如果 Attribute 和 DTO 不一致，输出 `Warning` 并拒绝继续推进。

保护：

- `UCatRunAttributeSet` 是目标和进度的权威数值源；`RunPublicState` 是兼容 UI、StateTree 和复制观察的公开投影。
- UI 和 Debug 仍读 `GetRunPublicState()`，不直接预测或写入 Run Attribute。
- 不新增客户端写口。

### 阶段 4：切换 StartDay 额度目标

目标：新一天开始时由 Run ASC 计算额度目标和重置进度。

执行项：

- 新增 `GE_Run_StartDay` 和 `UCatRunStartDayExecutionCalculation`。
- SetByCaller 写入 `Cat.Data.Run.BaseQuotaTarget`。
- ExecCalc 从 `UCatRunModifierAttributeSet` 捕获 `QuotaTargetMultiplier` 和 `DailyPressure`，输出到 `UCatRunAttributeSet.QuotaTarget`，并覆盖 `UCatRunAttributeSet.QuotaProgress = 0`。
- `EnterRunPhaseFromStateTree(DayActive)` 在原来设置 `QuotaTarget` / `QuotaProgress` 的位置改为应用 GE，再读取 Attribute 投影到 `RunPublicState`。
- `Revision`、deadline、phase、Environment 刷新和 StateTree 事件仍由 GameMode 控制。

保护：

- 默认倍率 1，目标值等于当前固定 `QuotaTarget`。
- 如果 Run ASC 不存在或 GE 构造失败，服务器应 fail-closed 并记录 Error，不悄悄回退到第二套公式。

### 阶段 5：切换献祭额度提交

目标：献祭最终数值由 Run ASC 统一计算，GameMode 不再手写 `QuotaProgress + Contribution`。

执行项：

- 新增 `GE_Run_ApplySacrifice` 和 `UCatRunApplySacrificeExecutionCalculation`。
- Coordinator 仍使用 Items 预留和提交结果中的 `SacrificeContribution`。
- GameMode 预检继续比较 Phase、QuotaOpen、Revision、Contribution、幂等终态。
- Run Apply 阶段创建 GE Spec，SetByCaller 写 `Cat.Data.Run.Sacrifice.RawContribution`。
- ExecCalc 从 `UCatRunModifierAttributeSet` 捕获 `SacrificeEfficiency`，计算 `AppliedContribution`，输出 Additive `UCatRunAttributeSet.QuotaProgress`。
- GameMode 读取 GE 前后 Attribute 值，构造 Result，投影 `RunPublicState`，再判断是否达到目标并发送 `QuotaReached`。
- 旧 `SubmitQuotaContributionInternal` 中直接加法公式删除或内联为调用 Run GE 的唯一入口。

保护：

- Items Commit 后的 Run retry 仍使用同一 RequestId 和冻结贡献。
- 达标事件只发一次，幂等重放只返回首次终态。
- `QuotaProgress` 不封顶，保留当前超额语义。

### 阶段 6：引入可调倍率但默认不改行为

目标：把用户提到的局内公共数值纳入可调结构，但首版不改变游戏结果。

执行项：

- `UCatRunModifierAttributeSet` 中的 `QuotaTargetMultiplier`、`DailyPressure`、`SacrificeEfficiency` 初始值设为 1。
- 只有服务器 Run/Environment/AbilitySet 明确施加 GE 时才修改这些属性。
- 若每日压力由天数驱动，先用固定公式或曲线在 DayActive 之前通过 GE 写入 `DailyPressure`。
- 若献祭效率来自 Buff、祭坛、事件或难度，必须通过 GE 修改 `SacrificeEfficiency`，不要在献祭提交点临时查多个系统。

保护：

- 未配置任何倍率来源时，结果必须与阶段 5 前一致。
- 日压力默认影响目标，不同时影响贡献，避免两个旋钮叠乘导致难度不可控。

### 阶段 7：Fishing 派生快照收口

目标：让钓鱼搏斗的输入集中构建，减少从 Settings、ASC、Equipment、DataAsset 直接散读。

执行项：

- 新增或整理 `FCatFishingDerivedStatsSnapshot`。
- 统一冻结角色属性、装备定义、装备实例、鱼定义、鱼性格、鱼饵、窝料、环境输入。
- Simulator 只接收派生后的 `FCatFightSimulationConfig` 和初始状态。
- 标注并改名“单场线耐久”字段，避免继续和装备实例 `RodDurability` 混淆。
- 删除 Session、HUD、Service 中重复读取体力基线的旁路。

保护：

- 高频模拟仍是纯 C++ struct 运算，不走每步 ExecCalc。
- 中途 Buff 是否影响已开始搏斗必须后续明确；首轮按会话开始冻结。

### 阶段 8：旧入口清理与最小性审查

目标：切换完成后删除直接写口和重复公式，避免新旧双口径长期共存，并让受影响模块真正只通过统一属性系统读写数值。

执行项：

- 搜索并清理 `QuotaProgress` / `QuotaTarget` 直接写入，只保留 AttributeSet 真相到 DTO 投影。
- 搜索并清理 `ApplyPoisonDelta` 包装层 clamp 和手写 stamina clamp。
- 搜索献祭贡献是否还有回查鱼定义的路径。
- 搜索 Fishing、Condition、Growth、Equipment、Environment、Social、ShopEconomy 和 UI 中所有最终数值组合点，把仍属于属性系统的公式迁到 AttributeSet/ExecCalc/MMC/派生快照。
- 对仍保留在原模块的数值，补全“为什么不属性化”的归属说明：事务、内容定义、空间场、账本、高频模拟或展示参数。
- 搜索旧 AbilitySystem 根目录和新子目录的重复头文件，确认工作区移动状态后再处理。
- 对新增 helper、wrapper、subclass 做删减审查：没有第二调用者或明确隔离收益的先内联。

保护：

- 不删除二进制资产和未确认蓝图引用。
- 遇到用户并行改动先汇报和绕开，不擅自 revert。

### 阶段 9：跨模块接入验收

目标：证明其他模块已经能使用这一套属性系统，而不是只证明献祭额度局部可用。

执行项：

- Run 验收：StartDay 和献祭只通过 Run ASC 计算额度；GameMode 没有第二套额度公式。
- Sacrifice / Items 验收：鱼实例冻结贡献仍是唯一输入；事务预留、提交、补偿不被 GAS 接管；Run 只接收已裁定输入。
- UI 验收：HUD 和库存页只读 `RunPublicState` 或快照；命令携带 `ExpectedRunRevision`；UI 预览不当作服务器权威。
- Condition / Growth 验收：Condition 只裁决倒地，Growth 只裁决 Buff 选择，真实数值变化进入 Character/Run 属性。
- Fishing 验收：会话开始或参与者变化时只从统一派生快照构建模拟配置；高频 Simulator 不直连 ASC 或 DataAsset。
- Equipment / Environment / Social / ShopEconomy 验收：这些模块保留自己的事务、空间和经济事实；一旦输出可叠加倍率或最终表现值，必须走 GE 或派生快照。
- 搜索验收：旧直接写口、旧最终公式、旧双口径注释和错误目录归属必须清理；高风险资产引用无法清理时列为显式剩余风险。

保护：

- 验收不要求把所有未来可能出现的数值一次实现成 Attribute，只要求本轮确认过的玩法数值没有无主、双主或旁路公式。
- 对正式蓝图资产、二进制资源和人工未确认行为，只做引用审计和交付说明，不硬删。

上面这些“预计修改”不是要求一次把所有系统大改完，而是表示属性重构会扫描并关闭这些模块里的数值读写闭包：凡是本轮确认属于统一属性系统的最终值，必须迁到快照、GE、ExecCalc、MMC 或 AttributeSet 回调；凡是仍留在原模块的数值，必须能解释为事务、内容定义、空间场、账本、高频模拟或展示参数。

`Catfishing.Build.cs` 当前已有 `GameplayAbilities`、`GameplayTags`、`GameplayTasks` 依赖，新增 AttributeSet / GE / ExecCalc 理论上不需要新模块依赖；实现时仍要以编译结果为准。

## 未决问题

- `SacrificeEfficiency` 小数结果的取整策略需要最终裁决。本文建议 `RoundToInt` 且正贡献最低 1；如果产品需要向下取整或允许低效鱼贡献 0，必须在实现前确定。
- `QuotaProgress` 当前按可超额保留。若未来设计要求封顶、奖励超额或结算溢出，需要新增明确字段或 Result，不应藏在 clamp 中。
- `DailyPressure` 首轮默认 1。它未来由天数、天气、自然事件、人数还是难度曲线驱动，需要单独数值表。
- `MaxFightStamina` 是首轮身体属性集最应该补的上限，但旧字段命名在 Settings、CharacterDefinition 和 Simulator 里不完全一致，实现时要逐个接线，不能只加属性不迁移读取。
- 单场线耐久与装备实例耐久语义冲突需要改名和引用审计；这可能触发资产 Redirect 和蓝图核验。
- Economy 是否需要 AttributeSet 暂不成立。只有当折扣、卖鱼收益、价格倍率被 GE/Ability 修饰时再扩展。
- `UCatSurvivalAttributeSet` 是否改名为 `UCatBodyAttributeSet` 暂缓。首轮保类名优先稳定运行。

## 实现优先级

1. 修复献祭 UI `ExpectedRunRevision`，保证现有协议可靠。
2. 补强 `UCatSurvivalAttributeSet` 的约束和 `MaxFightStamina`。
3. 新增 GameState Run ASC、`UCatRunAttributeSet` 与 `UCatRunModifierAttributeSet`，让额度目标和当前额度先进入 GAS，再投影公开 DTO。
4. StartDay 目标计算切到 Run GE / ExecCalc。
5. Sacrifice Apply 切到 Run GE / ExecCalc。
6. 默认倍率保持 1，确认旧行为不漂移。
7. 收口 Fishing 派生快照，清理旧直接读写路径。

这套顺序的原则是：先修协议，再收身体属性，再把 Run 额度事实迁入稳定属性集。任何阶段发现游戏主链不能正常推进，都应回到上一阶段的单一权威状态，而不是同时保留两套互相写回的数值系统。
