# 局阶段环境与昼夜循环子技术方案

文档状态：环境系统后端架构与接入合同已敲定，代码已接入主链；昼夜表现已接入最小原生场景驱动；不是测试报告或验收报告。

更新时间：2026-09-03

适用范围：`RunEnvironmentSocial` 原子模块内的 Run 阶段、天数、白天时钟、夜晚表达、Environment 快照、天气/自然事件、自然聚鱼入口，以及客户端只读消费合同。

本文解决的问题：把昼夜与环境从“局部功能补丁”收回到项目现有 Run 公共状态链路里，避免后续 Fishing、Camp、Social、Save、UI、表现层各自维护一套白天/夜晚/天气判断。

不覆盖范围：`Wet`/淋湿/抖水、最终美术调光曲线、美术资产、正式关卡灯光摆放、天气概率数值、自然事件频率、最终 WBP 视觉排版、测试源码、测试报告、验收报告，以及 `RunEnvironmentSocial` 模块关闭结论。

## 核心结论

这次返工不是新建一个独立“昼夜系统”。项目已有服务器 RunFlow 和 GameState 公开快照，环境系统必须适配这条主链。

最终口径是：

```text
服务器 GameMode 持有第几天、当前阶段、白天截止、夜晚 ready 和环境快照发布
-> StateTree 只负责阶段拓扑和事件转移，不保存第二份环境事实
-> Environment 只读消费 Run 快照，产出天气、白天鱼情时段、公共环境事件
-> GameState 复制一份 RunPublicState
-> Fishing、HUD、Camp、Social、Save、场景表现都从这份公共状态读取
```

后续玩法不得自行创建第二套昼夜时钟、第二份天数、第二份天气结论或客户端本地阶段推进。需要“现在是白天还是夜晚”的系统，读 `FCatRunPublicState.Phase.Phase`。需要“当前鱼情时段和天气”的系统，读 `FCatRunPublicState.Environment`。需要画面、声音、雾、后处理变化的系统，只能在后续表现层本地派生，不能反写玩法状态。

本次敲定三条硬口径：

1. `ST_RunFlow` 只负责状态机职责：接收事件、选择阶段转移、触发阶段进入 Task；它不保存第二份环境事实，也不承担天气、鱼情、表现或 UI 的业务判断。
2. 环境后端的公共合同先稳定下来：服务器只通过 `RunPublicState` 发布天数、阶段、白天时段、天气和公共事件，所有玩法系统都从这里读。
3. 表现层只做只读消费：昼夜画面可以从 `RunPublicState` 本地派生并驱动 UE 原生灯光、天空光、雾和后处理，但不能反写 Run、Environment、角色状态或客户端本地天数；`Wet`、角色反馈和最终美术资产仍不属于环境后端职责。

本轮收口后的后端范围：

- `ConfiguredWeather` 是现有环境提供者的显式天气输入。它保证联机、钓鱼和 UI 读到同一份天气事实，但不等于天气排期、概率天气或天气转移系统已经完成。
- `ActiveEventId` 是现有环境提供者的显式公共事件输入。它只允许一个公共事件进入 `FCatEnvironmentSnapshot`，不等于六类自然事件表、事件优先级或多事件并发已经完成。
- `Wet`/淋湿/抖水是后续表现或角色反馈层的问题，不属于环境后端收口。Environment 只发布 Rain 这个天气事实，不负责把任何猫改成 Wet。
- 后续若实现“按天/按时段抽天气”和“自然事件表”，应替换或扩展 Environment provider 的内部实现，继续输出同一份 `FCatEnvironmentSnapshot`，不能新增第二套复制状态。

## 当前真实架构

当前主链路已经存在：

```text
ACatfishingGameModeBase
  -> ST_RunFlow 只做阶段状态机
  -> ACatfishingGameModeBase::EnterRunPhaseFromStateTree()
  -> FCatRunPublicState.Phase / Revision
  -> UCatConfiguredEnvironmentProvider::EvaluateEnvironment()
  -> FCatRunPublicState.Environment
  -> ACatfishingGameState::SetRunPublicStateFromAuthority()
  -> OnRep_RunPublicState / OnRunPublicStateChanged
  -> Fishing、HUD、后续表现层和其他玩法只读消费
```

这条链路说明项目不是从零开始。当前方向是对的：GameMode 是权威写者，StateTree 只做阶段状态机，Environment provider 只读消费 Run 快照，GameState 复制组合后的公共状态，客户端不能推进 StateTree。

这已经是环境后端底座的稳定口径。后续还需要补的是运行验证、内容规则和表现适配，不是另起一套架构。

## 全局接入合同

后续任何玩法接环境，只认下面这些入口。

| 使用场景 | 应该读取哪里 | 禁止做法 |
| --- | --- | --- |
| 服务器判断能否钓鱼、能否打窝 | `ACatfishingGameModeBase::CanAcceptFishingCommand()` 或 `FCatRunPublicState.Phase.bFishingAllowed` 的权威结果 | Fishing 自己判断白天/夜晚 |
| 客户端 UI 显示天数、阶段、倒计时 | `ACatfishingGameState::GetRunPublicState()` + `OnRunPublicStateChanged` | HUD 自己缓存天数或轮询猜测 |
| 鱼种选择 | `FCatRunPublicState.Environment.TimeOfDay / Weather` | Fishing 直接调用 Environment provider |
| 夜晚玩法或营地阶段判断 | `FCatRunPublicState.Phase.Phase` | 把 `Night` 塞进 `ECatEnvironmentTimeOfDay` |
| 场景光照、天空、雾、后处理、环境音 | 本地表现层读取 `FCatRunPublicState` 后派生 | 复制 `VisualPhase` 或让表现层写 Run |
| 存档保存当前局进度 | 保存 RunId、DayIndex、Phase、额度、剩余白天秒数等 Run 事实 | 从 HUD 文本或表现参数反推 |
| 商店每日刷新 | 新 `DayActive` 且 `DayIndex` 递增的服务器边界 | 商店 UI 自己按日期刷新 |
| 自然事件/自然聚鱼 | Environment provider 裁决出的 active event | 聚鱼系统自己解释天气事件条件 |

这个表是后续开发的接入规矩。若新玩法发现缺少环境事实，应先判断它是“需要网络一致的玩法事实”还是“只影响本机画面的表现参数”。前者进入 `FCatEnvironmentSnapshot` 或 Run 快照；后者留在本地表现配置，不扩散到网络合同。

## 目标架构

目标架构不是“把所有东西搬进 Environment”，而是让每层只承担自己的稳定职责。

```text
Run Timeline
  持有 RunId、DayIndex、Phase、白天 deadline、夜晚 ready、StateTree 转移

Environment State
  只读消费 Run 快照，生成天气、白天鱼情时段、公共环境事件

Run Public State
  作为唯一复制包，承载 Run + Environment 公开事实，不承载本地表现结论

Gameplay Consumers
  Fishing、Camp、Social、Shop、Save 按公共状态做玩法判断或记录

Presentation Consumers
  HUD、场景氛围、环境音、天气特效只读公共状态并本地表现
```

设计原则：

- `ACatfishingGameModeBase` 继续是服务器 Run 写者，不让 Environment 反向裁决天数或阶段。
- `FCatRunPublicState` 继续是客户端公共状态的唯一复制入口，不新增第二套昼夜复制对象。
- `ECatEnvironmentTimeOfDay` 保持白天鱼情时段语义，不承担夜晚表现。
- 夜晚、失败夜、成功夜的画面语义由本地表现层从 Run Phase 派生，不作为 replicated 字段。
- Environment provider 不持有 GameMode 写指针，不推进 StateTree，不发布自己的网络状态。
- 表现层只读公共状态，不写 Run、Fishing、Social、Items、Profile 或 Save。
- 后续玩法需要接环境时优先扩展公共快照合同，而不是从某个局部系统旁路读取。

## 昼夜生命周期

### DayActive 进入

`ACatfishingGameModeBase::EnterRunPhaseFromStateTree(DayActive)` 是新一天开始的唯一入口。

目标流程：

1. 递增 `DayIndex`。
2. 写入白天开始锚点 `ServerTimeAnchorSeconds` 和 `DeadlineServerTimeSeconds`。
3. 开启 `bFishingAllowed` 与 `bQuotaOpen`。
4. 清空夜晚 ready 集合。
5. 安排三个服务器语义刷新点：Morning 结束、Dusk 开始、白天截止。
6. 递增 `Revision`。
7. 求值 Environment，发布同 Revision 的白天快照。

Morning/Dusk 刷新点只刷新公共快照，不改变天数，不改变 ready，不触发 StateTree 转移。

### 白天时段变化

服务器应根据 `MorningEndFraction` 和 `DuskStartFraction` 安排两个 one-shot timer。

触发时只做：

1. 确认仍是同一个 `RunId`、同一天、`DayActive`，且 deadline 仍有效。
2. 递增 `Revision`。
3. 重新求值 Environment。
4. 写入 GameState。

不需要每秒复制。客户端表现层可以用 `AGameStateBase::GetServerWorldTimeSeconds()` 和公共锚点做本地平滑。

### 额度达成

返工前达标路径在 `SubmitQuotaContributionInternal()` 中先关闭 quota/fishing、清 deadline，再刷新 Environment，随后发送 `QuotaReached`。这会暴露非法中间态。

当前后端定稿做法：

1. 提交额度贡献并记录命令终态。
2. 首次达标时立即关闭新的钓鱼/额度入口，并释放正在钓鱼的操作位。
3. 只停止白天截止和时段刷新 timer，公开 `deadline` 仍保留。
4. 递增 `Revision`，发布一份“仍是 `DayActive`，但 quota/fishing 已关闭且环境仍可求值”的过渡快照。
5. 发送 `QuotaReached` 给 `ST_RunFlow`。
6. 由 StateTree 进入 `NormalNight` 后，夜晚阶段入口统一清 deadline、再次递增 `Revision`、求值并发布夜晚公共状态。

中间不发布“无 deadline 的 DayActive”。

### 白天截止

返工前 `HandleDayDeadlineElapsed()` 也会在仍是 `DayActive` 时清 deadline 并刷新 Environment，再发送 `QuotaFailed`。

当前后端定稿做法：

1. 确认仍是当前 `DayActive` 且额度未达。
2. 关闭新的钓鱼/额度入口并释放操作位。
3. 只停止白天截止和时段刷新 timer，公开 `deadline` 仍保留。
4. 递增 `Revision`，发布一份“仍是 `DayActive`，但 quota/fishing 已关闭且环境仍可求值”的过渡快照。
5. 发送 `QuotaFailed` 给 `ST_RunFlow`。
6. 由 StateTree 进入 `FailureSettlementNight` 后，失败结算夜入口统一清 deadline、再次递增 `Revision`、求值并发布夜晚公共状态。

### 普通夜晚 ready 和翻天

普通夜晚没有倒计时。ready 变化可以递增 Run Revision 并发布 GameState，但不需要为了表现层额外复制夜晚字段。表现层从 `RunPublicState.Phase.Phase == NormalNight` 派生夜晚画面。

全员 ready 后只发送 `AllEligibleReady`。新的 `DayActive` 才递增 `DayIndex`。

## Environment 快照规则

`FCatEnvironmentSnapshot` 是网络同步的环境事实，不是表现参数包。

必须满足：

```text
RunPublicState.Environment.SourceRunRevision == RunPublicState.Revision
```

每次发布新的 `FCatRunPublicState` 前，都要么拿到同 Revision 的 Environment 快照，要么发布同 Revision 的 fail-closed 环境快照：

```text
Weather = Unknown
TimeOfDay = Unknown
bHasActiveEvent = false
ActiveEventId = None
SourceRunRevision = RunPublicState.Revision
```

不要保留旧 Environment 搭配新 Run Revision。这样客户端和未来玩法看到的公共状态不会版本错位。

夜晚阶段下 `TimeOfDay` 可以是 `Unknown`。这不是错误，因为 `TimeOfDay` 只描述白天鱼情时段。需要夜晚语义的消费方读 `Phase.Phase`。

## 表现接入接口

Presentation 在本文里只表示本地“场景氛围消费端”。它不是新的玩法系统，也不是新的网络状态。

人话链路：

```text
Run/Environment 已经决定现在是什么状态
-> 表现层读取这份状态
-> 本地驱动灯光、天空、雾、后处理、环境音和事件特效
```

当前有两个本地消费者入口：

```text
Source/Catfishing/Environment/Presentation/CatEnvironmentPresentationActor.h
Source/Catfishing/Environment/Presentation/CatEnvironmentPresentationActor.cpp
Source/Catfishing/Environment/Presentation/CatEnvironmentPresentationSubsystem.h
Source/Catfishing/Environment/Presentation/CatEnvironmentPresentationSubsystem.cpp
```

当前职责：

- `UCatEnvironmentPresentationSubsystem` 在游戏 World 开始时做保底检查：已有 `ACatEnvironmentPresentationActor` 就复用，没有才本地生成一个非复制 Actor；Dedicated Server 不生成。
- `ACatEnvironmentPresentationActor` 在客户端和 Listen Server 本地运行，Dedicated Server 不做表现。
- Actor BeginPlay 时定位本机 `ACatfishingGameState`，订阅 `OnRunPublicStateChanged`。
- 首次绑定时立即读取当前 `RunPublicState`，避免 OnRep 早于 Actor BeginPlay 时漏掉状态。
- Tick 中只根据最近的 `RunPublicState` 和 `GetServerWorldTimeSeconds()` 计算表现插值。
- C++ 默认驱动 UE 原生 `DirectionalLight`、`SkyLight`、`ExponentialHeightFog` 和 `PostProcessVolume`，把 Morning / Day / Dusk / Night / SettlementNight 映射到本机光照、天空光、雾和曝光。
- 太阳/月亮方向光会设置为 SkyAtmosphere 的 0/1 号大气光源；关卡如果已有 `SkyAtmosphere`，它会跟着同一套同步状态变化。
- 手动引用优先；没有引用时按 `Sun`/`CatSun`、`Moon`/`CatMoon`、`SkyLight`/`CatSkyLight`、`HeightFog`/`CatHeightFog`、`PostProcess`/`CatPostProcess` 标签查找，最后才退回同类第一个可用对象。
- Blueprint 事件仍然保留，用来让美术/关卡侧追加环境音、特效或正式资产表现。

当前不新增复杂 DataAsset。默认表现值先放在 Actor 上；只有当同一套表现曲线需要多个关卡、多套天气皮肤或资产版本时，再抽 `UCatEnvironmentPresentationSettings` 或 `UPrimaryDataAsset`。

表现层明确不做：

- 不决定能不能钓鱼。
- 不决定第几天。
- 不决定额度是否达成。
- 不决定玩家能不能 ready。
- 不复制给其他客户端。
- 不把本地插值结果写进 Save。

## HUD 和 UI 接入

HUD 要把 Run 快照当成正式读源订阅。

建议改法：

- `UCatHUDModel` 增加 `TWeakObjectPtr<ACatfishingGameState>` 和 `FDelegateHandle RunPublicStateChangedHandle`。
- `Bind()` 时从 World 找 GameState，并订阅 `OnRunPublicStateChanged`。
- `Unbind()` 时移除订阅。
- 回调只调用 `Refresh()`，不增量拼 UI 私有状态。
- `Refresh()` 继续从 `GetRunPublicState()` 读取 `DayIndex`，后续扩展阶段文本、白天剩余时间、夜晚 ready 状态。

这样优先从消费端闭合“天数不同步”风险。若 HUD 接订阅后仍不同步，再回查 GameState 复制条件和多客户端日志。

## Fishing 接入

Fishing 当前已经读取公共环境快照，方向正确。

保留规则：

- Fishing gate 继续通过 `CanAcceptFishingCommand()` 判断白天可钓。
- 鱼种选择继续读取 `GameState->GetRunPublicState().Environment.TimeOfDay` 和 `Weather`。
- Fishing 不直接调用 `UCatConfiguredEnvironmentProvider`。
- Fishing 不保存自己的天气、时段或夜晚状态。

只要服务器按 Morning/Dusk 边界刷新公共快照，鱼种选择就能自然吃到新的环境事实。

## 天气与自然事件

本轮收口的是环境公共合同和静态环境提供者，不把未实现的随机天气调度写成现行能力。

实施前问题：

```text
ConfiguredWeather=Clear
ActiveEventId=RainBloom
```

这表示“晴天”下仍激活了像雨后事件的 `RainBloom`。旧 provider 只要事件名非空就 `bHasActiveEvent=true`，没有校验天气、时段或阶段条件。

当前做法：

- `ConfiguredWeather` 继续保留，用作当前天气。
- `ActiveEventId` 继续保留，但 provider 已判断事件是否满足 Run 阶段、白天时段和天气条件。
- `ActiveEventRequiredWeather=Rain` 已写入当前配置，所以 `ConfiguredWeather=Clear` 时不会激活 `RainBloom`。
- 在事件条件表未敲定前，冲突事件 fail-closed：不激活事件，不提交自然聚鱼。
- `SubmitNaturalChumFieldIfConfigured()` 只消费 provider 已发布的 active event，不再自己解释事件条件。
- 自然聚鱼去重键已扩展为 `RunId|DayIndex|EventId|AnchorId`。

后续如需事件表，再新增小型内部配置：

```text
EventId
AllowedRunPhases
AllowedTimeOfDay
RequiredWeather
ChumDefinitionId
AnchorId
```

这张表属于 Environment 内部配置，不让 Run、Fishing、UI 或表现层直接解析。

历史决策记录中的天气权重、天气调度种子、自然事件优先级和环境印记提交链路已经按当前源码撤回为待裁口径。后续要补时，只能作为 Environment provider 的内部调度能力进入同一份快照。

## 表现型身体状态

`Wet` 的人话意思是“猫毛湿了”。它是表现型身体状态，不是环境后端状态，也不是会扣数值的惩罚。

本轮定稿口径：

- Environment 后端只表达全局环境事实：晴、雨、雾、白天时段和公共事件。
- Environment 发布 Rain 时不扫描角色，也不调用 `SetWetFromAuthority(true)`。
- `UCatConditionComponent` 仍然是 `Wet` 的已有写口，但谁在什么条件下写 Wet，不在本轮环境后端里裁决。
- 当前保留抖水相关入口，是因为它们属于已有 BodyAction/Condition 链路；本轮不扩展 Wet，也不把它算作环境系统验收内容。
- 后续如果要做“下雨猫会湿”“雨停自动抖水”“水体弄湿角色”等效果，应作为统一的表现或角色反馈消费层设计：它可以读取 `RunPublicState.Environment.Weather`，但不能让 Environment provider 或环境发布流程直接改角色身体状态。

这样做的意义是：天气是全局环境事实，`Wet` 是每只猫自己的身体/表现事实。两者未来可以有关联，但环境后端不直接承担这条关联。

## Save / Shop / Camp 等后续玩法接入

这个系统是全局底座，后续模块接入时按以下规则走：

- Save 保存 Run 事实，不保存表现派生值。白天保存剩余秒数或等价 deadline 事实；夜晚不补隐藏倒计时。
- Shop 刷新挂在 `DayIndex` 递增并进入新 `DayActive` 的服务器边界，不由商店 UI 或现实日期驱动。
- Camp 夜晚行为读 `Phase.Phase`，不读 `Environment.TimeOfDay`。
- Social 求助、保护、偷取边界继续走 GameMode/PlayerController 现有权限入口，不用环境表现状态授权。
- Profile/Album 若要记录环境印记，只记录已经由服务器裁决并提交的事件，不从本地画面特效生成永久事实。

## Debug 指令

人工 PIE、多客户端或 Development 包验收时，使用下面这些 Debug 指令看当前模块必要信息，并在房主端/服务器临时调整当前白天剩余时长，或按不同测试目的推进昼夜：

```text
cat.RunEnvironmentSocial.Debug 1
cat.RunEnvironmentSocial.Debug 0
cat.RunEnvironmentSocial.Dump
cat.RunEnvironmentSocial.DayLength 60
cat.RunEnvironmentSocial.SkipToNight
cat.RunEnvironmentSocial.SkipToNextDay
cat.RunEnvironmentSocial.ForceNextDay
```

`cat.RunEnvironmentSocial.Debug 1` 会在本机屏幕持续显示当前 World/NetMode、RunId、Revision、Environment SourceRevision、Day、Phase、Deadline、Quota、Weather、TimeOfDay、ActiveEvent、Ready 数量和公开 ChumField 数量。关掉用：

```text
cat.RunEnvironmentSocial.Debug 0
```

`cat.RunEnvironmentSocial.Dump` 会把同一份信息写入日志，事件名是：

```text
Event=run_environment_social_debug_snapshot
```

`cat.RunEnvironmentSocial.DayLength <秒数>` 是开发期服务器侧调试指令，用来把“当前白天从现在开始还持续多久”重设成指定秒数。例如：

```text
cat.RunEnvironmentSocial.DayLength 60
```

这不是改配置文件，也不是让 HUD 自己快进。它只在服务器、Listen Server 或 Standalone 上生效：GameMode 会重设当前 DayActive 的服务器锚点和截止时间，重新安排 Morning/Dusk/Deadline 计时，递增同一个 Run `Revision`，然后通过 `RunPublicState` 复制给客户端。客户端调试面板仍然只读 GameState；如果在纯客户端输入该指令，应看到 `AuthorityGameModeUnavailable` 日志，实际调整要在房主端或服务器执行。

`cat.RunEnvironmentSocial.SkipToNight` 是开发期服务器侧调试指令，用来只把当前开放白天推进到普通夜晚。它不提交夜晚 ready，不递增天数，也不把失败夜或结算夜改成普通夜晚：如果当前是 `DayActive`，命令会补足当日额度并让 `ST_RunFlow` 消费 `QuotaReached`；如果当前已经是 `NormalNight`，只返回“已经在夜晚”；其他阶段会拒绝。

`cat.RunEnvironmentSocial.SkipToNextDay` 是开发期服务器侧调试指令，用来把当前 Run 按正式成功链路推到下一天，便于人工快速看昼夜和天数同步。它不直接写 `DayIndex`、`Phase` 或客户端状态：如果当前是 `DayActive`，命令会先按当前 `Revision` 提交一条“补足当日额度”的 `SubmitQuotaContribution`，让 `ST_RunFlow` 消费 `QuotaReached` 进入 `NormalNight`；GameMode 只在 StateTree 已经正式进入 `NormalNight` 后，下一帧给当前服务器可见且属于夜晚资格集合的玩家逐个提交 `SubmitNextDayReady`。如果当前已经是 `NormalNight`，则直接走 ready 提交；如果 ready 已经全员完成但 StateTree 仍卡在普通夜晚，重复输入会重投同一个 `AllEligibleReady` 正式事件。新一天仍只会在 StateTree 进入下一次 `DayActive` 时递增，复制仍通过 `RunPublicState` 下发。

`cat.RunEnvironmentSocial.ForceNextDay` 是开发期服务器侧作弊救援指令，只处理两类情况：`FailureSettlementNight` 想继续人工测试后续天数，或者 `NormalNight` 已经全员 ready 但 StateTree 仍卡在普通夜晚。它和 `SkipToNextDay` 的意义不同：失败夜不能被普通 ready 流程翻成下一天，这是正式机制；`ForceNextDay` 明确绕过失败拓扑，先恢复失败结算夜关闭过的商店命令门，再停止当前服务器 StateTree，重新启动正式 `ST_RunFlow`，由下一次 `DayActive` 入口递增天数、重排 deadline、刷新 Environment、推进商店日状态并复制 `RunPublicState`。它不在客户端本地改 UI，不手写 `DayIndex++`，不处理 `HostExit` 拆局，也不改变正式成功结算规则。

该指令的关键日志事件是：

```text
Event=run_environment_social_debug_quota_completion_submitted
Event=run_environment_social_debug_quota_completion_rejected
Event=run_environment_social_debug_skip_to_next_day_ready_submitted
Event=run_environment_social_debug_skip_to_next_day_ready_summary
```

如果在纯客户端输入这些服务器指令，应看到 `AuthorityGameModeUnavailable`。如果补足额度后 StateTree 没有进入普通夜晚，不再由调试指令自己轮询和超时；服务器面板会显示“跳天加速=是”，健康判断会提示正在等待 StateTree 消费 `QuotaReached`。这说明正式状态机没有推进，而不是客户端 HUD 自己没刷新。若已经进入 `FailureSettlementNight`，`SkipToNextDay` 拒绝是正确的正式规则；测试需要继续看后续天数时，使用 `ForceNextDay`。若已经进入 `SuccessSettlementNight`、`Ending`、`Ended` 或 `HostExit` 拆局，`ForceNextDay` 也会拒绝，因为这些阶段属于正式局末或退出流程。

HUD 的天数显示按观察者口径工作：HUD 绑定时先从 `GameState.RunPublicState` 读取一次当前天数和阶段，随后订阅 `OnRunPublicStateChanged`。之后无论正常昼夜推进还是调试跳天，只要服务器发布了新的 `RunPublicState`，客户端都通过同一条复制通知刷新；HUD 不保存第二份天数。

人工验收时重点对比房主端和客户端：

- `Day`、`Phase`、`Revision` 是否一致。
- `EnvRevision` 是否等于 `Revision`，也就是 `EnvMatch=true`。
- `Weather`、`TimeOfDay`、`ActiveEvent` 是否一致。
- 进入夜晚后 `Deadline=false`，普通夜晚 ready 变化能在双方看到。
- 自然事件触发时 `NaturalChum` 不重复增长。

常驻面板和 Dump 入口只读 `GameState` 和本机已复制事实，不触发 StateTree、不改天气、不写角色状态。`DayLength` 只改当前白天时间窗口相关服务器事实和 timer，通过 `Revision`/`RunPublicState` 发布结果。`SkipToNight` 和 `SkipToNextDay` 只自动提交现有 quota/ready 写口，让 StateTree 自己进入夜晚和下一次白天。`ForceNextDay` 只作为非 Shipping 作弊救援，用显式命令从失败夜或普通夜 ready 卡住状态重新回到正式白天入口；它拒绝成功结算和 HostExit 拆局。它们都不改客户端本地天数、不改天气、不写角色状态，也不替代最终人工验收结论。
