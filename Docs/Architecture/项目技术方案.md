# Catfishing 项目技术方案

文档状态：架构方案，不是实现完成报告。**本文不描述工程实现进度**——实现到什么程度只能由真实源码、构建输出和新鲜 Automation 结果证明。
范围：把 active requirements lock、框架接线规则与架构讨论收敛为可实施、可审计的 UE 5.8 技术方案。它定义运行时宿主、领域边界、通信与持久化边界；不替代需求锁、数值表、美术资产规范或待裁策划项。

### 1.2 范围、非目标与模块化单体

目标是一个 1–8 人、单人同构的局制湖畔玩法：一次局在 `Lake` 中完成白天、夜晚、翻天与结算；跨局仅保留个人图鉴、印记和已裁的解锁。本方案采用一个 Runtime 模块内的模块化单体，保证同一局内的事务、复制与生命周期能有清晰的单一写入边界。

非目标同样是架构约束：不做 Lobby 地图、无缝旅行、主机迁移、持久房间/MMO、公会/排行、真实时间夜钓、强制任务、烹饪、营地建造，也不为了“通用”创建万能物品基类、全局事件总线或第二套状态机。成长机制已由 active requirements lock 固定：小/中/大/巨经验为 1/3/8/20、经验槽为 10、满槽三选一、溢出进入下一槽、同类 Buff 覆盖而异类共存、获得的 Buff 本局持续；具体 Buff 池、数值与文案仍为 **O**，必须 fail-closed。

统一执行链是：

```text
Enhanced Input / UMG View
  -> PlayerController 或 UI PageController 形成领域 Command
  -> 服务器校验身份、权限、阶段、RequestId 与 Revision
  -> StateTree 编排长流程，或领域服务完成短事务
  -> 唯一真相宿主提交 Result 与公开快照
  -> GameState / PlayerState / Character ASC / 领域 Actor 复制
  -> Cue、动画、音效与 MVC View 消费
-> CapturePlan 成像成功后，Collection/Imprint 才生成不可变 FProfileGrant
-> 所有者客户端按 GrantId Journal FProfileGrant，再 ACK Grant 投递记录并合并永久档案
```

场景交互与 UI 交互只能在命令入口汇合。例如叼鱼到祭坛与祭坛页面献鱼都只能提交 `SacrificeCommand`（P），由应用协调器进入 Items 与 Run 的可恢复提交协议；外部调用者不能直接调用底层 `ItemTransaction`。Widget、Ability、StateTree Task 与 FastArray 都不得直接改容器数组或额度。

## 2. 单 Runtime 目录与依赖方向

### 2.1 `Source/Catfishing` 的领域目录

不将模块重命名为 `CatfishingRuntime`。初期保持单个 `Catfishing` Runtime 模块，并在其下建立以下业务目录；目录不是子模块，也不引入跨 DLL 边界。

| 目录                 | 责任                                                | 可依赖                                                  | 禁止反向依赖                                          |
| -------------------- | --------------------------------------------------- | ------------------------------------------------------- | ----------------------------------------------------- |
| `Framework/Core`     | 共享 ID、错误码、Command/Result、日志、最小基础类型 | 无领域实现                                              | 不能知道 UI、Online、Run 具体对象                     |
| `Online`             | Steam/UE Session 适配、邀请、创建/加入/销毁         | Core、Framework                                         | 不能裁决局、物品或档案                                |
| `Run`                | 局规则、局时钟、额度、重连注册表、RunFlow、献祭协调 | Core、Data；Environment 契约放在 Core                   | 不能依赖 Environment 实现，也不能直接写 Profile 或 UI |
| `Data`               | Definition、查询、ID 解析、资产加载                 | Core                                                    | 不能依赖运行时 Actor                                  |
| `Environment`        | 水域区域、天气、自然聚鱼触发、环境快照              | Core、Data；只消费 Core 中的 Run 快照 DTO               | 不能依赖 Run 实现，也不能裁决钓获或容器               |
| `Fishing`            | 水域查询、鱼行为、钓鱼会话、捕获裁决                | Core、Data、Items；只消费 Core 中的 Run/Environment DTO | 不能依赖 Run/Environment 实现或持久化个人档案         |
| `Items`              | 鱼实例、容器 Aggregate、唯一事务                    | Core、Data                                              | 不能依赖 Fishing Actor、UI                            |
| `Character`          | 猫身体、GAS、输入命令转发、状态救援                 | Core、Data、Items、Fishing Result                       | 不持有局总流程或档案                                  |
| `Social`             | 权限查询、偷取意图、恶作剧策略                      | Core、Run 契约、Items 契约                              | 不裁决印记候选，不直接改 UI 或 SaveGame               |
| `Collection/Imprint` | 图鉴归约、印记候选去重、Capture Plan、Grant 语义    | Core、Data、Core 中不可变 Committed Result DTO          | 不依赖 Social/Fishing/Run 具体实现，也不拥有实物鱼    |
| `Profile`            | 本地档案、Pending Journal、Delivery ACK、SaveGame   | Core、Collection DTO                                    | 不能向服务器声称已持久化他人档案                      |
| `UI`                 | 按业务源划分的 Widget、Model、PageController、输入适配和只读显示数据 | Core、所有领域的 Query/Result DTO                       | 不能拥有玩法真相、不能替业务对象持有界面实例，也不能直接写领域状态 |
| `Debug/Tests`        | 命令重放、状态快照、自动化与网络诊断                | 可只读各领域公开契约                                    | 不成为生产依赖                                        |

依赖总体向内：`UI/Online` 是边缘适配层，`Framework/Core`、`Data`、`Items` 是稳定核；领域之间通过明确 Command、Result、Query 和小范围 Delegate 协作。Collection/Imprint 只消费放在 Core 的不可变 committed-result DTO，或显式的 Fishing/Run Result 契约，不回调这些领域的实现。任何因“方便”让 `Items` 调回 `Fishing`、让 `Profile` 读取 Lake Actor、让 Social 裁决印记，或让 UI 访问容器可写数组的写法都属于反向依赖。

### 2.2 最小公共契约

所有可重放的服务器入口使用 `RequestId`；所有读取后写入的对象带 `Revision`。`RequestId` 用于幂等，`Revision` 用于拒绝陈旧视图，二者不可互相替代。幂等键固定为 `StableNetId + CommandType + AggregateId + RequestId`（P），不能只凭客户端生成的 RequestId 去重。每个 Result 至少包含该作用域、结果码、提交后 Revision、受影响实体 ID 和可公开展示的数据；失败码至少区分 `PermissionDenied`、`InvalidPhase`、`NotFound`、`RevisionConflict`、`Cancelled`、`AlreadyResolved`、`NotEligible` 与 `TransportUnavailable`。

终态缓存由真正的 Aggregate 宿主持有。Run 命令由 GameMode/Run 服务缓存至 `EndRun` 完成并经过有界投递期，重连仍可得到首次终态，随后随局释放；Fishing 命令由 `AFishingSession`（P）缓存，会话结束后把必要的迟到请求终态摘要交给 Run 持有至局末，重连不能据此恢复旧会话；Container 命令由 Items Aggregate 缓存至容器/本局释放，普通玩家在同一局重连后仍可重放。缓存只回答同一作用域的首次完整终态，不允许跨局复用 RequestId，也不成为永久档案。

概念接口可用普通 C++ 服务、UObject、Actor Component 或直接领域入口表达，不要求为了形式全部做成 `UInterface`。候选入口如下：

| 概念接口                 | 输入与输出                                                                                                    | 写入者                                                |
| ------------------------ | ------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `Online`                 | Create/Find/Join/Destroy Command → Session Result                                                             | `UCatOnlineSubsystem`（P）                            |
| `WaterQuery`             | 位置、`FRunPhaseSnapshot`、天气、窝料快照 → 可钓区域/鱼候选；纯只读                                           | `WaterRegion`（P）/Environment                        |
| `Aggregation`            | `ContributeChumCommand` / `TriggerNaturalAggregationCommand` → 同类 `AggregationResult`（均 P）               | `WaterRegion` / ChumPool Aggregate（P）               |
| `Run`                    | 翻天、离局、重连 Command → Run Result                                                                         | GameMode / RunFlow                                    |
| `Fishing`                | 抛竿、提竿、协作、抢抄、取消 → Fishing Result                                                                 | `AFishingSession`（P）                                |
| `Sacrifice`              | 外部 `SacrificeCommand` → 完整终态；内部产生 `SacrificeCommittedResult`（均 P）                               | GameMode/Run-owned `USacrificeCoordinator`（拟定，P） |
| `ItemTransaction`        | 内部 Transfer/Steal/Consume + 期望 Revision → Transaction Result                                              | Items 容器 Aggregate                                  |
| `RequestHelp`            | 玩家主动求助 → Social Result；巨物系统提示走独立受控入口                                                      | Social（P）/Run 策略                                  |
| `SubmitImprintCandidate` | 事件、参与者、入镜上下文 → Capture Plan Result；CapturePlanId 状态只进入 `FImprintCaptureDeliveryRecord`（P） | Collection/Imprint 下的 `URunImprintService`（P）     |
| `FProfileGrant`          | GrantId 键控的不可变授予内容 → Pending Journal/Grant Delivery ACK Result                                      | `UCatProfileSubsystem`（P）                           |
| `UI Query`               | 只读快照、订阅、取消 Pending → 本模块显示数据                                                                | 对应业务 UI 模块的 Model/PageController；交互对象 UI 由该对象提供数据源 |

## 3. UE 宿主、真相与生命周期

### 3.1 世界与玩家宿主

`ACatfishingGameModeBase : AGameModeBase`（P）是服务器唯一局裁决者；它持有 Run 服务、`ST_RunFlow`（P）、局级社交策略及重连注册表。这里以 RunFlow 取代 Unreal 的 MatchState 作为项目流程语义，避免把白天/夜晚/额度/毕业强行压进通用比赛状态。额度失败的明确路径是 `QuotaFailed -> FailureSettlementNight -> 仍点火/看照片 -> EndRun`（P）：失败结算夜无计时、跨局记录不回滚，RunFlow 不能从 `QuotaFailed` 直接清理世界。`ACatfishingGameState`（P）复制当前天、昼夜、局内时间、天气、额度、公共事件与局级权限公开摘要；客户端只能读取。

`ACatfishingPlayerState`（P）只保存 Stable Net ID、在场、翻天确认与重连索引；它不持有身体 ASC、猫状态或物品真相。`ACatfishingPlayerController`（P）转发输入/界面意图、拥有镜头与本地 HUD 路由，但不裁决玩法。`ACatCharacter`（P）是唯一猫身体与 Character-owned ASC 的 Owner/Avatar，持有动作、Attribute、Effect、Tag、移动与表现宿主。

| 生命周期范围   | P 宿主                                                                      | 真相与限制                                                                                                                     |
| -------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 进程           | `UCatOnlineSubsystem`、`UCatProfileSubsystem`（均为 GameInstanceSubsystem） | 前者只适配 Session；后者仅写本机 SaveGame 与 Grant Journal。                                                                   |
| LocalPlayer    | `UCatLocalPlayerUISubsystem`（LocalPlayerSubsystem）                        | 本机 Viewport、焦点、输入适配和跨 World 清理；只承载本地玩家拥有的常驻 UI，不预建、不持有商店等交互对象 UI。                 |
| 服务器一局     | GameMode/Run、`USacrificeCoordinator`（拟定，P）、`FRunPlayerRecord`        | 权威规则、局级社交策略与重连；协调器持有献祭 pending/committed 和首次终态缓存。                                                |
| 服务器一局印记 | Collection/Imprint 下的 `URunImprintService`（P）                           | 候选去重、CapturePlan/Grant 裁决；分别持有本局 `FImprintCaptureDeliveryRecord` 与 `FGrantDeliveryRecord`，绝不直接写远端磁盘。 |
| 一局复制       | GameState                                                                   | 公开、只读的环境与局快照。                                                                                                     |
| 身体/连接      | Character、PlayerState、Controller                                          | 身体状态与动作随 Character；身份与连接事实随 PlayerState。                                                                     |
| 单次钓鱼       | `AFishingSession`                                                           | 钓手、目标鱼、协作者、阶段、终止原因、唯一结算键。                                                                             |
| 世界           | `WaterRegion`、`AFishActor`、Camp actors、`AProtectionSignActor`（P）       | 水域查询、活动鱼行为、固定营地/鱼护/共享鱼缸/祭坛舞台；牌子明确持有玩家/区域保护范围与 Revision。                              |

### 3.2 初始化、离局与回前端

启动时 GameInstance 建立 Online/Profile；Frontend 的独立 UI 模块建立组局入口和档案读取。Create 成功后 Host 以 Listen Server `OpenLevel(Lake, "listen")`；Join 成功后 Resolve Connect String，再由 Controller `ClientTravel` 到 `Lake`。二者完成前 UI 始终显示 Pending，而不是预先假定旅行成功。

进入 Lake 后，GameMode 先建立 Run 服务、启动 RunFlow 并发布初始 GameState；玩家先建立稳定身份与在场记录，再生成/占有 Character。Character 在 `PossessedBy` 初始化服务器 ASC；拥有客户端在 `OnRep_Controller` 与 `PawnClientRestart` 以可重入方式刷新 ActorInfo、输入绑定与 UI 订阅。

ASC 清理必须先分清临时失去控制和最终销毁。`UnPossessed` 可能只是等待重新占有：先收口或取消领域会话与 Ability、解除当前输入/Avatar 关联，再调用 `ClearActorInfo` 清理 ASC 缓存的 Owner/Avatar；重新占有时重新 `InitAbilityActorInfo`。`EndPlay`/最终销毁则还要结束 FishingSession 参与关系、完成或回滚预留事务、解绑 Delegate/Task 后再清 ActorInfo。`ClearActorInfo`（E）不替代 Ability 取消、FishingSession 终止或事务恢复协议，也不能被当作领域清理本身。

退出和局末先停止新命令，使每项进行中事务只走“一次提交”或“明确失败”之一。Run teardown 前，`USacrificeCoordinator`（P）必须取消未提交预留，并把 Items 已 committed 的记录补到 Run 终态；成功结算夜与失败结算夜都先完成篝火/相册归档，并分别收口 CapturePlan 成像投递与 Grant 投递，再清 World。UI 解绑旧 World/Controller/Model 并取消本地 Pending。没有 Lobby、Seamless Travel、Host Migration；房主退出即本局收口。普通玩家重连只按 Stable Net ID 恢复已经存在明确合同的白名单终态、CapturePlan 投递和未 ACK Grant；重连后身体、容器与装配分别恢复到什么状态仍为 **O**，必须保持 fail-closed，不能从旧 Character、Container 或 Loadout 快照自行拼接恢复策略。Host、Client 与网络异常的 Online 异步退出链见 §6.1。

## 4. 数据、资产、复制与隐私边界

### 4.1 最小数据模型与 ID

`FishDefinition`（P，Primary Data Asset）是鱼种数据 SSOT：分布、稀有度、体型、性格、偏好、毒性与用途；`FishInstance`（P）是局内唯一实物，记录 InstanceId、DefinitionId、重量、所有权/容器关系与创建来源。它们必须分离：实物鱼可被偷、吃、献和局末清空；图鉴记录由不可变 `FProfileGrant` 独立增加，不因实物后续变化回滚。

| 类型                                                                 | 归属与用途                                                                                                                        |
| -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `Container`（P）                                                     | 鱼护、共享鱼缸、祭坛输入等局内集合及其 Revision。                                                                                 |
| `RunPublicState` / `FishingPublicState` / `ChumPoolPublicState`（P） | 可复制的公共只读快照。                                                                                                            |
| `CaptureCommittedResult`（P）                                        | 嘴叼世界鱼首次入箱的已提交事实；携带结算键、鱼实例归属与必要候选上下文，供 Collection/Imprint 幂等归约，不是永久授予。            |
| `FProfileGrant`（P）                                                 | 不可变授予内容：Stable Grant ID、接收者、类型与 Payload；不包含可写 ACK 状态。                                                    |
| `FGrantDeliveryRecord`（P）                                          | 服务器本局 Grant 投递记录：以 GrantId 为键，仅保存 `FProfileGrant` 的接收者、投递尝试与 ACK 状态；ACK 只更新此记录。              |
| `FPendingGrantJournalEntry`（P）                                     | 拥有者客户端 local-only durable journal 条目：只以 GrantId 对应 `FProfileGrant`，保存本地 Pending/Complete 与图片恢复信息。       |
| `CapturePlan`（P）                                                   | 同一事件、同一帧/构图所需的可重放参数；不是已经写入的图片，也不是永久授予。                                                       |
| `FImprintCaptureDeliveryRecord`（P）                                 | 服务器本局 CapturePlan 投递记录：以 CapturePlanId 为键，保存计划投递、客户端捕获完成/失败与重试状态；不含 Grant ACK，随本局释放。 |
| `ReconnectRecord`（P）                                               | Stable Net ID、有效期、允许恢复的身体/容器关联、未完成 `FImprintCaptureDeliveryRecord` 索引和未 ACK `FGrantDeliveryRecord` 索引。 |
| `RunAlbumRecord`（P）                                                | 以 `RunAlbumId` / `RunId` 分组，保存 `CoverImprintId` 与印记索引；封面固定指向全员篝火合影。                                      |

不造万能 `Item` 基类。鱼、窝料、草药、竿/饵/漂等仅在确有共同交易与容器规则时共享小型 DTO 或事务语义；Definition 与实例的字段随领域各自演进。

### 4.2 权威、复制与隐私

服务器拥有所有 Run、Fishing、Fish、Container、权限、候选裁决和事务写权。`FFastArraySerializer`（E：NetCore 复制工具）只承担高效复制，不负责冲突裁决、幂等或持久化；任何 FastArray 条目都必须来自已提交的领域 Result。

`FishGuard` 是独立箱子式个人容器对象，不挂在 Character 上，也不由 Character 创建、注册或复制。角色交互命令只能解析到正式鱼护对象后再提交 Items 容器事务；共享 `FishTank` 是同一 Container Aggregate 的另一个适配者，二者可有不同 Actor/视觉表现，却共享 Items 事务规则。

| 可见性      | 例子                                                                                                                                                      | 规则                                                       |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| public      | 天/天气/额度、公共窝料、活动鱼、缸展示、可见事件                                                                                                          | GameState/世界 Actor 复制，只读。                          |
| owner-only  | 尚未完成投递的个人 `FProfileGrant`/CapturePlan、请求关联与 Pending 结果                                                                                   | 仅向对应拥有者投递；服务器不持有个人相册。                 |
| server-only | 完整容器写模型、CapturePlanId 键控的 `FImprintCaptureDeliveryRecord`、GrantId 键控的 `FGrantDeliveryRecord`、重连白名单、Session 操作细节、候选裁决中间态 | 不复制；由 Result 发布必要结果，两种投递记录不得共用 ACK。 |
| local-only  | 只对应 GrantId 的 `FPendingGrantJournalEntry`、相册索引、图片路径/字节、隐藏标记、页面焦点、输入映射                                                      | 全部属于拥有者本地档案，绝不复制为服务器或公共状态。       |

`ItemTransaction` 是容器实物写入的唯一门：先校验身份/权限/阶段/Revision，再单次提交源与目标，最后发 Result。偷取、吃和转移都不能“先删后加”。抄网本身不再是容器事务：首个合法 F 只把水中鱼交接为抄手嘴叼的 `ACatFishPickupActor`；玩家随后对具体地面鱼护交互，才以会话结算键与该容器 Revision Compare-and-Commit，产生鱼实例归属、不可变 `CaptureCommittedResult`（P）与印记候选。它不直接生成 `FProfileGrant`。Collection/Imprint 消费该已提交事实后再幂等归约授予；后续同键返回 `AlreadyResolved`，不会重复产生鱼、Committed Result、候选或授予。

献祭跨越 Items 与 Run 两个 Aggregate，不能伪装成数据库原子事务。外部只提交 `SacrificeCommand`（P）；GameMode/Run-owned `USacrificeCoordinator`（拟定，P）先校验身份、阶段、额度语义和期望 Revision，再让 Items 以 RequestId 预留鱼实例而不删除。Run 接受对应预留后，Items 原子消费该鱼并产出不可变 `SacrificeCommittedResult`（P），Run 只消费这条已提交事实、按同一幂等键增加额度。

协调器是一局服务器级对象：它不依附 PlayerController、Ability 或单次请求对象，玩家掉线后仍持有 pending/committed 与首次完整终态缓存。Run teardown 前必须完成或取消未提交预留；若 Items 已 committed，则鱼的唯一真相已经消费，只允许重试补 Run 额度，不允许“回滚鱼”。协调器只记录协议进度，不成为第二份鱼或额度真相。未消费预留可回滚/超时释放；首次完整终态只在两侧都完成后发布，同 RequestId 重放恢复或返回该终态，从合同上排除“鱼消失、额度未加”。如果 Host 进程直接消失，在没有外部后端的当前范围内无法恢复这段内存协议；这是明确证据边界，不能宣称跨 Host 恢复。

## 5. GAS、StateTree、输入与 UI 的职责切分

### 5.1 GAS：猫身体的动作与状态

GAS 只服务猫身体。AttributeSet 只表达 active requirements lock 已确认的身体属性；Gameplay Ability 表达抛竿、提竿、收放线、抄网、搬运、进食、偷取、救援等可取消动作；Gameplay Effect 改变状态；Gameplay Tag 表达稳定语义；Gameplay Cue 只消费 Result 做表现。Tag 不能代替 `FishInstance`、容器事务或重连快照。

当前工程阅读口径：Fishing 六输入仍是玩家输入 Ability 主链；吃鱼、偷取/追回、求助/恶作剧/保护牌、营地休息/篝火回看/转缸/救援/修竿、献祭和抖水等非 Fishing 身体动作，先经 `UCatGA_BodyActionCommand` 与 `UCatBodyActionPayload` 进入 GAS Gameplay Event 网关，BodyAction Ability 用 `UAbilityTask_WaitDelay` 保留短提交窗口，窗口结束后再由 `ACatfishingPlayerController::ExecuteBodyActionAbilityPayload` 回到原领域服务；Fishing Cancel 的服务器入口会先按 `Ability_Body_Command` 窄标签取消仍在窗口内的 BodyAction，再继续原 Fishing 取消/收竿语义。`PlayerController` RPC 仍是网络入口，但不能再被读成绕过 GAS 直接写领域；Items、Social、Camp、Condition、Equipment 和 Run 仍持有事务真相。

搏斗资源按真相拆开：猫的力量与搏斗体力由 Character ASC/AttributeSet（P）持有；鱼的力量与搏斗体力由 FishingSession 的鱼运行态（P）持有，FishDefinition 只提供初始数据；钓组强度与 Equipment Revision 来自装备快照，本场鱼线耐久则由 FishingSession/Runner 每场独立持有并重置。强度过载或线耐久耗尽产生 `LineBroken`，只终止当前会话，不写坏场景鱼竿或 Equipment；独立失败预算中的丢饵/伤竿事务仍保持互斥和幂等。资源公式、阈值与不同品质的预算分配仍为 **O**。

UE 5.8 源码可用事实（E）：GAS 位于 `Engine/Plugins/Runtime/GameplayAbilities/Source/GameplayAbilities`，`UAbilitySystemComponent` 的 ActorInfo 需要在 Owner/Avatar 可用时初始化。项目拟用 Character-owned 方式：服务器在 `ACatCharacter::PossessedBy` 初始化并授予基础 Ability Set；拥有客户端在 `OnRep_Controller` 与 `PawnClientRestart` 刷新。`Mixed` replication mode 是 **V**：需双客户端原型确认 Owner/Avatar 与 OwnerActor 链后才可启用；在验证前禁用 `Minimal`，不以其承载玩家身体状态。

### 5.2 StateTree：长流程而非短事务

`GameplayStateTreeModule`（E）提供 `UStateTreeComponent`；项目只在 GameMode、`AFishingSession` 和确有层级行为必要的 `AFishActor` 上使用。GameMode 的 `ST_RunFlow` 显式 Start/Stop，负责开局、白天、额度判定、入夜、翻天、失败/毕业结算；FishingSession 的 `ST_FishingSession` 负责抛竿、等待、试探、真咬、搏斗、近岸、抢抄和终止；FishActor 的行为树只在活动鱼行为需要时启用。

StateTree 与 GAS 的桥是项目层桥接：Task/Condition 只能发送 Gameplay Event 或调用领域 Command，并等待结构化 Result 决定转移；不会让 StateTree 直接改 Attribute、容器或档案。短事务、印记、物品写入均不放进树。鱼一旦 Hooked，最终阶段只由 FishingSession 推进，FishActor 不得与会话并行结算。

### 5.3 Enhanced Input 与 UMG MVC

Enhanced Input 的 Mapping Context 由 PlayerController/LocalPlayer 在正确的 Pawn、交互焦点和业务 UI 状态下装卸。项目只在正式 Input Context 资产里声明 Action 映射，C++ 不临时 `NewObject<UInputAction>` 或运行时硬写按键。HUD、背包/鱼容器、背包格子、商店、图鉴等业务 UI 必须按业务源分别形成自己的 Widget C++ 基类、WBP、Model、PageController、局部显示数据、输入/按钮意图和验证入口。

UI 实例的逻辑所有权跟随业务源，而不是一律归 LocalPlayer。HUD 属于本地玩家/Controller 的常驻显示；个人背包只读取本人 EquipmentComponent 中的鱼竿、鱼漂、鱼饵、窝料等随身道具。地面鱼护、共享鱼缸等世界容器只通过本次射线命中的交互对象把自己的只读容器复制源传入库存界面，不把容器 Actor 放进 UI，也不在 Character 上维护鱼容器。祭坛、修竿点、商店等界面由对应交互 Actor、组件或服务提供打开上下文、目录/可执行命令和关闭条件。LocalPlayerSubsystem 只在本机负责把可显示的 Widget 加到 Viewport、处理焦点与输入模式、并在 World 或拥有者失效时做清理；即使底层 `CreateWidget` 需要本地玩家，也不能把商店这类对象界面预创建成玩家自己的 UI 实例。

View 只收输入和渲染；PageController 将点击转换为领域 Command；Model 只持有本模块需要的 Query 快照、Result、Pending RequestId 和订阅。Controller 为 Pending 操作保留 RequestId，收到终态 Result 或超时失败后更新对应模块显示数据。不同 UI 模块之间不能共享一个大状态对象，也不能互相读取对方的控件或可写数据；需要协同时只能在领域 Command/Result 或只读 Query 层汇合。

不使用 Widget Tick 轮询领域状态。复制通知、领域 Result、页面事件和模型订阅驱动刷新；World 切换时，本地玩家拥有的 UI 解绑旧 World、Controller、Delegate 与 Mapping Context，交互对象提供的 UI 则在对象失效、距离/权限不满足或交互结束时关闭，防止 Frontend 或旧 Lake 对象的悬挂引用污染当前局。

## 6. Online、地图、插件与资产接线

### 6.1 两地图与 Steam 异步链

地图只有 `Frontend` 与 `Lake`。Frontend 承载档案、创建/加入；Lake 承载营地、河流、森林湖、昼夜和整个 Run。Session 是发现、邀请、加入与退出的在线对象，不是第三张地图。

`UCatOnlineSubsystem` 适配 UE OnlineSubsystem：Create 成功才 OpenLevel Lake listen；Find/Join 成功才 Resolve Connect String 并 ClientTravel；Join/Create/Destroy 失败均返回结构化 Result，UI 清除 Pending 并给可理解错误。所有退出链以退出 RequestId 去重，迟到回调不能触发第二次旅行。

Create 与 Join 共用一条 Session 兼容性硬约束（D）：目标 `FOnlineSessionSettings`（E）必须满足 `bUsesPresence == bUseLobbiesIfAvailable`。Create 在发起平台请求前拒绝不相等的配置；Join 在使用搜索结果前检查同一对设置，不匹配时返回结构化配置失败，不能靠旅行阶段兜底。二者是一组 Session/Lobby 选择合同，禁止由两个入口各自写成不同值。

- **Host exit**：GameMode 先拒绝新命令，按 Run 规则收口（包括失败/成功结算夜已开始时的归档），向远端发送 Return/断开原因；远端各自清 UI/Input、异步 Destroy 自己的 NamedSession 并回各自 Frontend。Host 有界等待远端确认或超时后 Destroy 自己的 NamedSession，最后本地回 Frontend。
- **Client leave**：服务器先终止该玩家的 FishingSession 参与和 Character/ASC 领域状态；是否为主动离局保留可重连白名单由离局策略决定（O），不能冒充网络异常自动恢复。离开的客户端清 UI/Input，Destroy 自己的 NamedSession，回本地 Frontend。Host Session 与其他玩家的 Run 不受影响。
- **网络异常**：客户端记录断开原因，幂等清理 UI/Input 与本地 NamedSession，回 Frontend；服务器按超时生成/保留 ReconnectRecord，不立刻摧毁 Host Session。若 Host 进程仍可执行收口，则走 Host exit 的有界路径，否则客户端只依赖 NetworkFailure 回退。

`DestroySession` 只销毁调用方的 NamedSession 状态，不等于关闭 NetDriver，也不能被当成驱动远端客户端旅行的机制。项目没有 Lobby、Seamless Travel、Host Migration；Steam 的真实回调顺序、邀请、中途加入和重连仍为 **V**。其中传输/身份外壳可以做原型验证，但身体、容器与装配的精确恢复 policy 仍为 **O**；没有新的需求裁决时必须保持关闭。

## 7. 领域链如何从需求落到运行时

### 7.1 Run、环境与钓鱼

Run 是局阶段与局时钟的唯一真相；它发布只读 `FRunPhaseSnapshot`（P），包含 RunId、天、阶段、局内时刻和可钓开关。RunFlow 把该快照传给 Environment 契约，Environment 只返回天气/事件 Result（P），不反向查询或依赖 Run 实现；RunFlow 再消费 Result 编排阶段与公开快照。由此消除 Run↔Environment 双向逻辑依赖，同时保留夜晚不钓鱼、天气与事件受局内时间驱动的规则。

RunFlow 将白天限时、献祭额度、夜晚无时限、在场者翻天与毕业结算串成唯一服务器流程。额度失败必须走 `QuotaFailed -> FailureSettlementNight -> 仍点火/看照片 -> EndRun`：失败夜没有倒计时，图鉴、印记与解锁等跨局记录不回滚；篝火回看和本地归档完成有界收口前，不能直接清理 Lake 世界。

`WaterQuery` 是纯只读查询：它读取位置、`FRunPhaseSnapshot`、天气与 ChumPool 快照，不得改变窝料、预算或冷却。玩家投窝只提交 `ContributeChumCommand`（P），自然事件只提交 `TriggerNaturalAggregationCommand`（P）；两者共同进入 `WaterRegion` / ChumPool Aggregate（P）的单一写口，使用同一 Revision、稀缺预算与冷却并产出同类 `AggregationResult`（P）。玩家叠窝与自然触发因此共享同一聚鱼机制，不能分别更新两套鱼群状态。

#### 7.1.1 窝料聚鱼账本改版记录（2026-08-28）

本节记录已确认的产品方向（**R**）与建议计算模型（**P**），不表示当前代码已经实现。每一片湖或河作为一个独立 `WaterRegion`，持有固定可钓面积 `A`、区域鱼总数 `N` 和各鱼种数量 `N_s`，并满足 `N = ΣN_s`。窝料仍以 `{腥, 香, 酵}` 三维向量表达，鱼种仍只保存一份三维偏好；所有鱼种共用同一条重叠收敛曲线，不为 16 种鱼分别制作 16 张曲线表。

详细版按以下模型实施（**P**）：

1. 把水域与当前所有窝料影响圆相交后划成互不重叠的面积单元 `c`；同一单元内覆盖它的窝料集合一致，面积比为 `r_c = A_c / A`。无窝区域也是单元，所有 `r_c` 之和为 1。实现时可用烘焙网格/规则 tile 近似并按“覆盖窝料 ID 集合”合并，不枚举理论上的 `2^窝点数` 排列组合。
2. 单元内的有效三维输入为 `V_c = Σ_j(窝料向量_j × 数量_j × 距离衰减_j × 时间衰减_j)`。鱼种 `s` 的有效剂量为 `x_s,c = dot(V_c, Preference_s)`；同一条 `ChumOverlapCurve(x)` 把它映射为 `M_s,c`。曲线需单调、有限且封顶，目标手感示例为一份标准窝料约 `1.1×`，大量重叠逐渐收敛到 `8×`，而不是线性无限增长；具体输入归一化、关键点和 `8×` 是否为终值仍属 **O**。
3. 各鱼种在所属水域内按面积平均分布（**R**），不制作鱼种专属栖息密度图。鱼种 `s` 在单元 `c` 的分配权重为 `W_s,c = r_c × M_s,c`，守恒分配为 `n_s,c = N_s × W_s,c / Σ_k W_s,k`。这样窝料只把鱼从同一水域的其他位置吸引过来，不凭空增加区域鱼总数，也不会改变各鱼种的水域总账。
4. 每个单元还受面积容量上限 `C_c = N × AreaCapacityCurve(r_c)` 约束；该曲线全项目/水域共享，单调且不超过 `N`。线性候选可写成 `AreaCapacityCurve(r)=min(1, LocalDensityCap×r)`。若 `Σ_s n_s,c > C_c`，用确定性的受限归一化/水位填充把溢出量重新分给尚未触顶的其他单元，直到所有单元满足容量且 `Σ_c n_s,c = N_s`。这同时满足“按面积比例限制聚鱼上限”和“水域鱼总量守恒”。
5. 运行时账本可保留双精度期望数量，只在生成/钓获提交边沿做整数化；需要整数时按稳定的 `WaterRegionId / CellId / FishDefinitionId` 顺序使用最大余数法，避免网络端或重放产生不同结果。捕获、逃逸、刷新或跨单元迁移只能通过水域账本单一写口改变 `N_s` / `n_s,c`。

该模型的成本与“鱼种数 × 当前空间单元数 × 单元附近窝点数”近似线性，不需要为鱼种组合建表。窝料种类的扩展仍围绕三维向量完成；鱼种增加时只新增该鱼自己的 `N_s` 和 `Preference_s` 数据。当前已确认平均分布，因此不增加芦苇区、深水区等鱼种专属栖息地表，也不得伪造 16 套空间曲线；将来若产品规则改变，再作为新的分布模型改版处理。

简化版（**P**）可以不维护全水域的显式迁移结果，而是在鱼钩所在局部区域即时计算：基础鱼种占比 `p_s=N_s/N`，局部加权占比 `p'_s = p_s×M_s / Σ_i(p_i×M_i)`，局部总量上限仍为 `C=N×AreaCapacityCurve(A_local/A)`。由于已确认所有鱼种按面积平均分布，`N_s×A_local/A` 中的面积因子会在鱼种比例归一化时约掉，所以这个简化成立；但面积只在比例里约掉，算局部总量/上限时不能删除。若系统既不维护局部总量也不做容量或库存扣减，那么总鱼数 `N` 也会从纯概率选择中约掉，该版本无法满足本次提出的鱼总量守恒与区域上限，只能作为无耗竭的选鱼近似。

建议先用简化版作为首个可玩实现，但保留 `WaterRegion` 的 `A / N / N_s` 权威账本、共享曲线和面积容量接口，使其之后能无数据迁移地升级到详细版。当前源码只完成“采样点三轴叠加 → 鱼偏好点积 → 选择权重饱和”，尚未持有水域面积、鱼总数、鱼种数量、互斥面积单元、守恒重分配或面积容量上限，因此不能把现有窝料实现视为本改版已完成。

FishDefinition 的稀有度与体型独立：稀有小鱼仍可单人遇到，巨大鱼受在场协作能力上限约束，单人局不刷新需要多人合力的体型。

FishingSession 保障三阶段咬钩、搏斗阶段合力、首个合法抢抄和明确中断。它读取 Character ASC 的猫力量/搏斗体力、鱼运行态的鱼力量/搏斗体力，以及装备快照的钓组强度与 Revision；本场鱼线耐久是 Session/Runner 的会话内真相，不是 Equipment 的永久鱼竿耐久镜像。咬钩前退出零损失；咬钩后放弃按规则损失鱼饵；`LineBroken` 只终止本场会话，显式失败预算中的丢饵/伤竿仍互斥。普通 `LineBroken` 保留已部署鱼竿和当前操作位，允许玩家直接再次抛竿；掉线、倒地、白天截止、配额达成、进入夜晚、局末或关键对象失效等会让玩家失去操作资格的边界，则必须在关闭 Fishing gate 前终止会话、释放鱼竿操作位并恢复 Fishing 持有的角色移动锁，不能要求已经被 gate 拒绝的 `LeaveRod` 再负责解锁。

### 7.2 鱼、营地、猫与社交

捕获成功后的实物链为：FishInstance → FishGuard → 共享 FishTank → 献祭/吃/观赏/偷取 → 局末清空。鱼护、缸与祭坛都是 Container 适配者，库存转移由 Items 事务负责。献祭的唯一外部入口是 Run-owned `SacrificeCommand`；`USacrificeCoordinator`（拟定，P）执行 §4.2 的预留/提交/恢复协议，Items 产出 `SacrificeCommittedResult` 后 Run 才推进额度，任何 UI、祭坛 Actor 或 Ability 都不能分别删鱼和加额度。营地是固定据点，不建造、不经营；它提供休息、鱼缸、祭坛动线和篝火回看。

猫没有死亡。现行身体状态只覆盖 Wet、Downed、恢复与搬运；伙伴可搬运回营。毒性数据与精确恢复 policy 仍为 **O**，没有裁决时生产入口必须保持关闭；没有烹饪。偷取仅限一条实物鱼，装备、图鉴与照片不可偷，追回窗口结束后才消失。装备/外观选择和已授予解锁跟人走，但装备在局内不允许被偷。

社交权限也只有一份服务器真相：局级默认策略由 GameMode/Run 持有，GameState 只复制公开摘要；玩家/区域保护牌由 `AProtectionSignActor`（P）持有 Owner StableNetId、WaterRegionId、保护范围与 Revision。恶作剧、偷取、求助等 Social Command 每次都统一查询局策略、牌子与当前阶段，UI 只显示摘要，不能缓存可写权限或本地放行。

普通鱼不会自动向全队广播求助。玩家必须主动提交 `RequestHelp`（P），Social 校验阶段与权限后才发布普通求助；只有系统判定为巨物时允许绕过玩家请求产生全体提示。普通求助的广播范围、冷却、重复抑制和表现仍为 **O**，但“普通鱼手动、巨物可系统全体提示”的边界已确定。

### 7.3 图鉴、印记与 FProfileGrant

钓获事务在服务器裁决后提交实物 FishInstance 进入容器，并发布不可变 `CaptureCommittedResult` 与印记候选；事务本身不创建永久授予。Collection/Imprint 消费该已提交事实后，才以幂等规则生成不可变 `FProfileGrant` 向拥有者客户端授予图鉴记录。实物、Committed Result 与 Grant 不能混为同一对象；图鉴有未知、剪影、已记录三态，剪影与实物同样独立。

剪影不是客户端根据动画自行猜出的记录。合格逃鱼终态先由 FishingSession 产生：重试次数耗尽是已确定的资格路径，断竿、脱钩、扑空或“看清程度”等其他资格仍为 **O**；Collection 对候选去重与裁决后生成带稳定 GrantId 的 `FProfileGrant`（P），再走本地 durable Journal/ACK。重复候选、重连补发或 ACK 丢失都只能归约到同一个剪影终态。

解锁同样走授予链，而不是由 UI 直接写档。图鉴节点、天数或额度里程碑的已提交 Result 产生 Unlock Candidate（P），Collection 裁决后生成不可变 `FProfileGrant`，再由客户端 Journal/ACK。成长机制固定为小/中/大/巨经验 1/3/8/20、槽 10、满槽三选一、溢出继承、同类 Buff 覆盖、异类共存且本局持续；具体 Buff 候选、数值、文案以及其他解锁内容仍为 **O/A5**。

`SubmitImprintCandidate` 在不打断操作的情况下提交候选。Collection/Imprint 下的 `URunImprintService`（P）只消费 Core 中不可变 committed-result DTO 或明确的 Fishing/Run Result，去重并产生 `CapturePlan`；共同印记按入镜分发。服务器以 CapturePlanId 在 `FImprintCaptureDeliveryRecord`（P）中记录计划投递、客户端捕获完成/失败与重试，本记录只活到本局结束，不写永久授予 ACK。只有捕获成功 Result 到达 Collection/Imprint 后，服务才生成带新 GrantId 的不可变 `FProfileGrant`，并建立独立 `FGrantDeliveryRecord`；捕获失败或仍待重试时不得伪装成已经授予。

每局本地相册以 `RunAlbumId` / `RunId` 分组，成功或失败结算夜都归档，固定的全员篝火合影写入 `CoverImprintId` 作为封面。断线重连按 CapturePlanId 查询 `FImprintCaptureDeliveryRecord` 以恢复本局成像投递，按 GrantId 查询 `FGrantDeliveryRecord` 以重投未 ACK 的 `FProfileGrant`；两类 ID、状态和回执不能互换。服务器只持本局两类投递记录，不持相册索引、图片路径或隐藏标记。局内相册私有，个人一键隐藏只改本地索引；图鉴可局内互看，公共回看唯一舞台是篝火。

Profile 的 durable 写盘协议（P）先落盘、后 ACK：客户端收到 `FProfileGrant` 后，先按 GrantId 生成 `FPendingGrantJournalEntry`，把 Grant 内容和 `Pending` 状态持久化；该 Journal 不接受 CapturePlanId。若含图片，使用稳定图片名写临时文件/临时状态，原子转为完成文件后再提交相册索引与 `Complete` 状态。只有 Pending Journal 确认持久化成功后才允许 Grant ACK；ACK 只更新同 GrantId 的服务器 `FGrantDeliveryRecord`，绝不修改 `FProfileGrant` 事实，也不更新 `FImprintCaptureDeliveryRecord`。启动恢复会重放 Pending、清理孤儿临时图片、修复“图片已完成但索引未提交”，并把“索引存在但图片缺失/损坏”标为可重取或损坏状态（P）。ACK 丢失时，同 GrantId 返回本地既有终态；磁盘失败不得 ACK，也不能假装永久记录已经完成。图片格式、容量、成像和具体原子文件策略仍为 **V/O**。
