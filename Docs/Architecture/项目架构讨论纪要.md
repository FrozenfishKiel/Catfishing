## 记录规则

本文件持续记录项目架构讨论过程。内容分为三类：

- **已确认口径**：开发工作必须遵守的项目事实和边界。
- **讨论中建议**：当前提出但尚未由项目负责人确认的技术方向。
- **待讨论事项**：后续需要继续分析和决定的问题。

讨论中建议不得直接当成已确认决策。稳定结论形成后，再整理进正式技术方案或项目知识库。

## 已确认口径

### 团队职责

当前团队负责开发，即把现有 GDD 落成完整、可运行、可交付的 Unreal Engine 项目。策划案是产品需求输入，开发团队负责工程架构、技术选型、系统实现和集成验证。

### 资源缺失与占位实现

项目目前缺少大量正式美术资源。开发不能因此停滞：在正式资源到位前，可以使用白盒场景、白模、基础几何体、临时材质、占位动画、简单音效和简单特效验证玩法。

项目架构需要允许占位资源在后续被正式资源替换，但不为尚未出现的资源工作流预建复杂框架。

### 渔获归属

鱼最终由实际取得它的玩家拥有。多人共同参与搏斗不会自动产生共同所有权；最终捕获、抱取或抢抄成功者取得该条鱼。

联机实现中，最终归属必须由服务器权威确认，客户端表现不能单方面决定结果。

### 平衡与非程序裁决

节奏、数值、状态压力、成长奖励以及类似体验取舍属于平衡或策划职责。开发阶段先把相关值做成可调整配置，并通过实际试玩提供证据，不在尚未可玩时替策划提前裁决。

“暂不裁决”不代表不实现相关能力；程序需要提供足够的调参入口和验证手段。

### 项目体量与架构尺度

Catfishing 是体量不大的独立项目。架构应服务于完整项目，并与实际规模和已知需求匹配。

“避免过度设计”不等于排斥抽象、扩展性、灵活性或前瞻性。真正需要避免的是：某项设计对完整项目没有明确价值，却需要投入大量时间搭建、接入和维护，最终没有降低风险，反而拖慢开发或增加复杂度。

架构目标不是追求最少代码或只让当前功能跑起来，而是让完整游戏能够被清楚地实现、调试、扩充和交付，同时避免后续系统接入时不断堆叠特判、重复逻辑和生命周期漏洞。

### 前瞻性、扩展性与灵活性

项目代码需要具备与完整需求相匹配的前瞻性、扩展性和灵活性。开发不能采用“当前能跑就算完成”的短视方案；如果当前实现会让后续已知系统难以接入、迫使代码反复推倒、制造大量回归风险，就属于需要避免的设计。

合理的前瞻性主要体现在：

- 为 GDD 中已经明确存在的完整系统预留稳定边界，而不是只覆盖眼前正在实现的一个用例。
- 把容易变化的内容、数值和资源表现从稳定玩法规则中分离。
- 明确状态所有者、写入入口、生命周期和网络权威，减少多人环境下的重复结算与状态分叉。
- 让新增同类内容主要通过数据、注册或能力声明接入，而不是不断复制流程或追加对象名单式判断。
- 对高风险链路提供可调试、可验证和可回归的入口，避免问题只能依赖人工猜测。

前瞻性也有边界：不能只因为“未来也许会用到”就建设与已知项目需求无关的基础设施。是否值得提前设计，应结合完整需求、后补代价、缺陷风险、实现成本和长期维护成本判断。

### 模块与接口的设计口径

前瞻性不依赖堆叠更多层级，而依赖把复杂度收进合适的模块。项目倾向设计“深模块”：调用者只需要学习较小、稳定的接口，模块内部承担完整规则、约束、错误处理和生命周期细节。

接口不仅指函数声明，还包括调用顺序、状态不变式、失败方式、网络权限和性能约束。接口同时是调用面和测试面；如果测试必须绕过接口钻进大量内部细节，通常说明模块切分或接口形状需要重新判断。

只有当行为确实需要变化或存在两个真实实现时，才建立适配接缝。纯粹为假想未来创建空接口和透传层，不会自动带来扩展性。判断一个模块是否有价值，可以反问：如果删除它，复杂度会消失，还是会重新散落到多个调用者中？只有后者说明该模块真正提供了复用收益和修改局部性。

### 当前讨论范围

当前讨论对象是这个独立项目**完整形态的项目架构蓝图**，不是 MVP、首个版本、第一阶段或垂直切片的范围设计。

后续可以讨论开发顺序和阶段验证，但开发顺序只表示如何逐步落地完整架构，不得把阶段性实现误写成项目最终范围。

### 目标平台与发行渠道

目标平台已确认为 **Windows PC**，发行渠道已确认为 **Steam**。当前架构不为主机、移动端、跨平台账号或跨平台联机预建兼容层。

Steam 身份、好友邀请、房间发现和加入对局需要被纳入完整工程方案，但平台接口不得直接渗入钓鱼、物品、局流程等领域规则。

### 本轮确认的框架取舍

- **不采用 CommonUI**。项目使用原生 UMG 和自有的小型 UI 组织层，不接入面向复杂多平台界面的 CommonUI 体系。
- **不采用 Steam Cloud**。跨局数据和印记照片保存在本机；更换电脑、清理本地数据或卸载后的恢复不属于当前架构保证。
- 其余总体骨架继续成立：房主 Listen Server、服务器权威、`OnlineSubsystemSteam`、项目级 GAS、`Enhanced Input`、数据资产、统一物品事务、C++ 规则与蓝图表现分层、单 Runtime 模块的模块化单体。
- 流程与行为框架采用 **GAS + StateTree**，不自研通用状态机框架。
- UI 内部设计采用 **MVC**。采用 MVC 的直接原因是大厅、背包、鱼护、鱼缸、图鉴、相册和设置等界面允许玩家操作；Controller 负责把 View 中的用户交互转换成游戏命令。

## 当前架构原则

以下原则已经与项目体量方向一致，但具体落地方式仍需继续讨论：

1. 优先设计后补代价高、且会影响完整项目的边界，例如联机权威、状态归属、稳定数据标识、跨局持久化和 C++ / 蓝图职责。
2. 抽象应覆盖 GDD 中已知的完整需求和可预见变化，但不建设与项目无明确关系的万能系统。
3. 核心玩法和网络规则使用 C++，资源接线、表现、UI、动画、音效、特效和快速调参优先使用蓝图与数据资产。
4. 联机是产品基本形态，应从系统设计起点考虑服务器权威、复制和掉线边界，不能把完整单机实现直接当作联机架构。
5. 只有确实会批量增长的内容才采用数据驱动；避免把所有逻辑都包装成配置资产。
6. 技术方案以解决完整项目问题为准。GAS、Mass、消息总线、服务定位器或通用框架等方案不是天然错误，也不是天然正确；只有收益明确高于接入、学习、调试和维护成本时才采用。
7. 系统边界首先在同一 Runtime 模块内通过业务目录和清晰职责表达；是否拆模块或插件必须由真实依赖和独立交付需求证明。
8. 占位表现和正式表现应消费同一份玩法状态，防止正式资源到位时反向修改核心规则。
9. 不以减少初期代码量为唯一目标；如果一个清晰的公共入口能够显著减少后续重复逻辑、对象特判和网络缺陷，应当在合适层级提前建立。
10. 模块应尽量保持小而稳定的接口，把复杂规则收进实现内部；避免只有转发作用、接口复杂度接近实现复杂度的浅模块。

## GAS 技术选型讨论

### 讨论起因

此前曾把 Gameplay Ability System（GAS）和其他重型方案一起列为默认谨慎项，但没有先完成 Catfishing 完整需求与 GAS 能力的正式映射。该表述不能视为“项目已决定弃用 GAS”，也不能作为成熟技术选型结论。

### 当时倾向不用 GAS 的原因

当时的直觉主要来自以下判断：

- 项目体量较小，担心 Ability System Component、Attribute Set、Gameplay Ability、Gameplay Effect、Gameplay Tag、Gameplay Cue 和自定义 Ability Task 带来较高的接入与调试成本。
- 项目不是传统战斗、RPG 或 MOBA，没有大量攻击技能、伤害公式、Buff / Debuff 叠层、技能等级和冷却循环。
- 局与天、鱼缸、祭坛、聚鱼时刻、渔获归属、图鉴和印记等核心状态并不天然属于某个角色的 Ability System Component。
- 钓鱼是玩家、鱼、鱼竿、鱼线和其他参与者共同构成的服务器权威交互，担心把完整钓鱼流程硬塞进单个角色 Ability 会使状态所有权和多人生命周期变得不清楚。
- 游戏节奏并非高强度战斗，初步认为普通服务器 RPC、属性复制和显式状态机可能已经足够，不一定需要完整预测框架。

这些理由可以作为评估成本的输入，但不足以直接推出“GAS 不适合本项目”。

### GAS 与完整项目需求的真实匹配点

Catfishing 仍然存在一组 GAS 擅长解决的真实问题：

- 玩家拥有多种可激活、可取消、会互相阻塞的动作：抛竿、提竿、收线、松线、抄鱼、偷鱼、扑倒、救援、进食、休息和使用道具。
- 许多动作是持续、异步、分阶段并依赖动画或事件回调的流程，需要可靠地结束和取消。
- 饥饿、疲惫、中毒、搏斗体力、力量以及部分装备修正具有 Attribute / Effect 特征。
- 玩家状态会影响动作许可，例如倒地不能钓鱼、搏斗中限制其他交互、受保护钓点阻止恶作剧。
- 项目从起点就是联机游戏，需要处理服务器确认、客户端响应、动作复制、取消回滚和表现同步。
- Gameplay Cue 可以为占位表现与正式音效、特效、动画之间提供稳定接缝。

因此，GAS 不是只对战斗游戏有价值。它可能成为“玩家动作与角色状态”模块的成熟实现基础。

### GAS 采用后的项目级影响

GAS 属于项目基础技术选型，不能作为局部试用项。如果采用，它会贯穿项目的玩法动作、状态表达、Gameplay Tag 语言、效果、表现触发、网络执行、调试方式和团队开发规范；所有相关系统都需要按统一口径与它集成。

“贯穿项目”不等于所有状态都由同一个 Ability System Component 持有。项目仍需保持清晰的运行时真相所有者：

- 局与天的生命周期属于游戏流程状态。
- 天气、自然事件和聚鱼时刻属于世界状态。
- 鱼护、共用鱼缸、祭坛与渔获归属属于服务器权威的物资和规则状态。
- 图鉴、印记和解锁属于持久化状态。
- 单次钓鱼中玩家、鱼、鱼竿和协作者共享的会话真相，需要明确的服务器权威所有者，并与 GAS 的动作、Tag、Effect 和事件体系形成统一执行链。

采用 GAS 后，上述模块不能各自绕开 GAS 再发明一套互斥状态、效果语言和动作执行规范；同时也不能因为使用 GAS 就放弃原本应有的状态所有权和生命周期划分。

### 最终选择：GAS + StateTree

项目正式采用 GAS，并同时采用 StateTree：

- GAS 成为项目级玩法基础设施，相关模块统一采用其 Ability、Tag、Attribute、Effect、Cue、Gameplay Event 和网络执行口径。
- StateTree 成为项目级流程与行为编排框架，负责局流程、钓鱼会话、鱼行为和环境事件等多阶段逻辑。
- 各领域仍保持自己的状态所有权，但不再自研通用状态机或在 GAS 外建立另一套动作互斥、效果和取消协议。

本次在“GAS 独自承担流程”和“GAS + StateTree”之间选择后者。原因是 Gameplay Ability 与 Ability Task 适合一个 Actor 动作的异步执行，但局流程、鱼 AI 和多参与者会话并不都属于某个 Actor 的 ASC；StateTree 能承担这些流程的层级状态、条件、Task 和转换，使 GAS 保持在动作与效果职责上。

该选择属于项目基础架构，不采用局部试用或后续再决定是否接入的方案。

### 采用 StateTree 的项目理由

采用 StateTree 不能只因为它是 Unreal 自带、支持可视化或比自研状态机省事。它必须在本项目中持续替代一类会反复出现的复杂度。

本项目采用它的主要依据是：

1. **鱼行为具有可复用的层级与组合条件。**鱼会在巡游、受窝料吸引、观察鱼饵、试探、真咬、挣扎、乏力、逃脱等行为之间变化；鱼种还采用“性格模板 + 程序化微调”，不同模板会改变咬钩与挣扎节奏。若只使用 GAS，这些 AI 决策会散落在 Ability、Ability Task、鱼 Actor Tick 和大量 Tag 判断中。
2. **钓鱼是多参与者共享的长生命周期会话。**钓手、目标鱼、协作者、钓具和抢抄者会在同一个流程中加入、退出、中断、重试和竞争。该流程没有一个天然的玩家 ASC 可以独占；如果建立一个长生命周期总 Ability 统筹全部参与者，会让 Ability 所有权、取消和掉线清理变得别扭。
3. **GDD 已明确要求先定义中断回退与多人兜底。**咬钩前后退出损失不同，搏斗存在协作者加入、体力切换、重试、断竿、落水、鱼逃和抢抄判序。StateTree 的 State、Transition、Condition、Task 和 Evaluator 能把这些路径集中在一个可检查的流程资产中。
4. **至少两个核心领域会复用同一编排能力。**鱼行为和 FishingSession 都需要层级状态、条件选择、异步 Task 与事件驱动转换；局流程和环境事件也可以在同一基础上表达。删除 StateTree 后，这些复杂度不会消失，只会重新散回 C++ 分支、Ability Task 和 Gameplay Tag 组合，因此它不是只有转发作用的额外层。

单独的日夜切换、简单计时或几个顺序步骤并不足以证明 StateTree。如果项目只有线性的抛竿 Ability 和很简单的鱼移动，应该只采用 GAS。当前选择 GAS + StateTree，是因为完整 GDD 同时存在鱼行为模板、多参与者钓鱼会话和中断/重试/掉线分支。

### StateTree 不负责什么

- 不负责力量、体力、饥饿、中毒等 Attribute 与 Gameplay Effect。
- 不负责玩家动作预测、Ability 激活、互斥、取消和 Cue。
- 不负责捕获归属、物品事务、容量计算、祭坛额度和存档规则。
- 不负责 Steam 会话、UI MVC、资源加载或数据表查询本身。

这些规则仍由 GAS 或对应领域模块持有。StateTree 只编排“在什么条件下执行哪个 Task，以及根据结果转向哪里”，避免它膨胀成第二套 Gameplay Framework。

### 采用成本与控制办法

采用 StateTree 会增加 StateTree 资产、项目专用 Task/Condition/Evaluator、GAS 事件接线、服务器调试和公开阶段复制的成本。控制办法是：

- 领域计算保留在可测试的 C++ 函数或 GAS 规则中，StateTree 节点只调用并消费结果。
- 只在服务器运行影响玩法真相的 StateTree，客户端不复制执行树，只消费权威结果。
- 共用节点必须来自至少两个真实流程；只服务单个状态的逻辑直接留在该领域 Task 内。
- 不把每个短动画、一次按钮点击或简单布尔开关建成 StateTree。

### 本轮口径纠正

此前提出的“限定范围采用 GAS”已撤回。GAS 是否采用属于会影响整个项目的基础技术选择：要么作为项目共同基础正式采用，要么完全不采用。职责划分仍然存在，但不能把技术选型降级成局部试验。

## 讨论组织方式纠正

项目技术选型不能拆成平台、网络、GAS、输入、UI、存档等互不相干的话题逐项散聊，也不能因为存在依赖关系就长期停留在上游条件讨论。当前目标是形成一张能够直接指导工程骨架搭建的完整架构图，再在同一张图上确认技术选择。

从本轮开始，每一项讨论都必须回答下面五个问题：

1. 它位于哪一条实际游戏运行链路中？
2. 它拥有什么状态，状态生命周期是什么？
3. 谁可以写入，服务器与客户端各自负责什么？
4. 它通过什么小而稳定的接口连接相邻模块？
5. 它如何被调试、测试和替换？

如果某项技术无法挂到完整运行链、无法说明状态所有者或只是孤立地增加一个框架，就不进入项目骨架。技术选型记录仍需包含采用结论、淘汰原因、项目级影响、接入与维护成本和验证方式，但不再把技术名词本身当成讨论主线。

## 项目框架总体骨架（讨论中建议）

### 总体形态

建议采用 **模块化单体**：一个游戏工程、一个主要 Runtime 模块，在模块内部按领域形成清楚的深模块；仅为编辑器数据校验和开发工具保留一个 Editor 模块。当前项目不按钓鱼、背包、营地等系统拆成大量插件，也不引入微服务式抽象、全局服务定位器或通用消息中台。

这套框架的主干是：

```text
Steam 身份/房间
    -> GameInstance 会话入口
    -> GameMode / GameState 对局生命周期
    -> Enhanced Input 输入
    -> GAS 玩法动作与权限
    -> 服务器领域会话（钓鱼、交互、抢夺、救援）
    -> 复制后的权威状态
    -> Gameplay Cue / 动画 / 音效 / UI
    -> 物品事务与渔获归属
    -> 局进度、共享鱼缸、祭坛或玩家物品
    -> 跨局图鉴、印记与解锁存档
```

任何完整玩法都沿这条链路落地。输入层不直接修改物品，表现层不直接裁决捕获，存档层不反向持有局内对象，Steam 接口也不进入领域规则。

### 运行时状态所有者

| 状态或职责 | 建议所有者 | 写入边界 |
|---|---|---|
| Steam 登录、邀请、建房、加入和退出 | `UGameInstanceSubsystem` 会话适配器 | 只负责平台与 UE 会话之间的转换，不写玩法状态 |
| 对局规则、天数推进、日夜切换和结算命令 | `AGameMode` 与普通 C++ 规则对象 | 仅服务器执行 |
| 当前天、阶段、天气、配额、公共事件等对局快照 | `AGameState` | 服务器写入并复制，客户端只读 |
| 玩家稳定身份、连接/在场状态、翻天确认和重连索引 | `APlayerState` | 服务器权威并复制；不持有猫身体属性、Effect 或物品真相 |
| 玩家输入、镜头、本地 HUD 和菜单路由 | `APlayerController` | 只发出意图并消费复制结果，不裁决玩法 |
| 猫的移动、碰撞、动画宿主、GAS ASC 与局内身体状态 | `ACharacter` | 服务器权威；饥饿、疲惫、中毒、淋湿、倒地和动作许可跟随这具唯一猫身体 |
| 单次抛竿到捕获结束的共享真相 | 服务器生成的 `AFishingSession` 类领域 Actor | 会话对象统一推进阶段、校验参与者、生成捕获结果 |
| 世界鱼实体、鱼群和环境交互 | 对应服务器 Actor 与生成器 | 服务器模拟，客户端消费必要的复制状态和表现事件 |
| 玩家鱼护、共享鱼缸、祭坛等物品集合 | 各自明确的复制状态拥有者 | 所有转移统一通过物品事务入口，不允许多个系统直接改数组 |
| 图鉴、印记、永久解锁和设置 | 本地档案 `USaveGame`，由档案 Subsystem 管理 | 在 Steam 身份就绪后加载；只保存跨局事实 |

状态所有者表是架构约束，不是类名最终定稿。后续可以调整具体命名，但不能重新把同一份真相分散给多个对象共同修改。

### 一次钓鱼的端到端链路

1. `Enhanced Input` 把玩家输入翻译成项目输入动作。
2. `APlayerController` 或 Pawn 将输入交给对应的 GAS Ability，Ability 根据 Tag、Attribute 和阻塞规则判断能否开始。
3. Ability 向服务器请求创建或加入 `FishingSession`；客户端预测只负责即时反馈，不产生最终渔获。
4. `FishingSession` 持有钓手、目标鱼、鱼竿/鱼线快照、协作者、当前阶段和结束原因，服务器统一推进抛竿、咬钩、搏斗、抄取和失败状态。
5. 会话复制最小必要快照；客户端动画、音效、特效和 UI 通过 Gameplay Cue、复制通知或范围明确的 Delegate 消费它。
6. 捕获成功后，会话生成唯一的捕获结果，交给物品事务入口。事务一次性校验来源、目标容器、容量和最终所有者，然后原子地移交鱼实例。
7. 物品变化再驱动玩家鱼护、共享鱼缸、祭坛配额和局进度；服务器只在明确的跨局事件发生时生成规范化授予结果，拥有者客户端收到后再由本地 Profile 幂等持久化。

这条链同时约束“独自钓鱼、协作抄鱼、抢鱼、偷鱼、鱼缸转移和祭坛献祭”，避免每种玩法分别实现一套归属与复制逻辑。

### 技术选型与其在骨架中的用法

| 技术 | 当前建议 | 在项目中的具体职责 |
|---|---|---|
| 联机拓扑 | 房主 Listen Server，1–8 人 Steam 房间 | 房主同时承担服务器权威；独立服务器和主机迁移不作为默认架构 |
| Steam 接入 | `OnlineSubsystemSteam`，外包一层 GameInstance 会话适配器 | 登录身份、邀请、房间、加入/退出；领域代码只认识项目自己的会话结果 |
| GAS | 全项目正式采用 | 统一玩法动作、互斥与取消、Tag、Attribute、Effect、Cue、网络执行和调试语言；领域会话仍持有自己的共享真相 |
| StateTree | 与 GAS 一并采用 | 编排局流程、钓鱼会话、鱼和环境行为等多阶段流程；使用引擎已有 State、Transition、Task、Condition 和 Evaluator，不自研状态机运行框架 |
| 输入 | `Enhanced Input` | 管理键鼠/手柄映射、上下文切换和重绑定；输入只产生意图 |
| UI | 原生 UMG + 项目自有 MVC | Model 向 View 提供事件驱动的只读展示状态，Controller 处理用户意图；不接入 CommonUI 或 UMG MVVM 插件 |
| 数据定义 | `UPrimaryDataAsset` + Asset Manager | 鱼种、装备、道具等有独立身份和资源引用的内容定义 |
| 数值配置 | Data Table / Curve Table | 批量平衡数值、成长曲线、天气或鱼种参数；不承载流程逻辑 |
| 项目标识 | `FPrimaryAssetId` + Gameplay Tag | 前者标识内容实体，后者表达状态、类别、能力要求和效果语义，二者不互相替代 |
| 列表复制 | `FFastArraySerializer` | 玩家鱼护、共享鱼缸等会增长且频繁增量变化的复制集合 |
| 持久化 | 本地 `USaveGame` 与本地印记文件 | 图鉴、印记索引、永久解锁和设置；不接入 Steam Cloud，局内权威状态不以客户端存档为真相 |
| 表现接缝 | Gameplay Cue、复制通知和局部 Delegate | 白盒与正式动画、音效、特效、UI 消费同一玩法状态，不能回写规则 |
| 自动化与调试 | 规则单测、联机功能测试图、数据校验、分类日志和调试命令 | 验证状态转换、物品事务、归属唯一性、复制结果和错误恢复 |

### 设计模式的实际使用位置

- **GAS + StateTree**：GAS 执行玩家或 Actor 的动作，StateTree 编排跨时间、跨参与者的流程与行为；两者通过 Gameplay Tag、Gameplay Event 和结构化结果连接。
- **事务入口**：用于捕获、偷取、抢夺、鱼护转移、鱼缸存取和祭坛献祭。所有权改变必须一次校验、一次提交、一次广播，避免复制过程中出现重复鱼或双重归属。
- **命令式入口**：玩家操作通过 Ability 或服务器请求表达“想做什么”，领域模块决定“是否成功以及结果是什么”。
- **观察者**：Gameplay Cue、复制通知和局部 Delegate 只把已发生的状态变化交给表现层；不建立任何系统都能发布和订阅的全局消息总线。
- **适配器**：仅放在确有外部差异的边界，例如 Steam 会话、档案文件与正式/占位表现资源。项目内部不为每个类机械增加接口。
- **数据驱动**：用于会批量增加的鱼种、装备、道具和数值；规则流程仍保留在 C++ / GAS 中，不把代码控制流搬进表格。
- **组合优先**：只有能力具备独立生命周期或需要跨宿主复用时才成为 Actor Component；不执行“一种概念一个组件”。

### GAS 与 StateTree 的分工

项目不从 `enum + Transition` 开始自研通用状态机。流程和行为统一建立在 Unreal 已有的 GAS 与 StateTree 之上。

**GAS 负责“执行什么动作”**：

- 玩家输入触发抛竿、收线、松线、抄鱼、协助、偷取、扑倒、救援、进食和道具使用等 Ability。
- Gameplay Tag 处理动作许可、互斥、阻塞和取消。
- Attribute / Gameplay Effect 处理力量、体力、饥饿、疲惫、中毒和装备修正。
- Ability Task 处理单个动作内部的动画等待、目标选择、输入等待和异步回调。
- Gameplay Cue 处理联机下的动画、声音和特效反馈。

**StateTree 负责“整个流程现在走到哪一步”**：

- 局与天：准备、白天、额度达成/截止、入夜、篝火、翻天和局结算。
- 钓鱼会话：准备、抛竿、等待、试探、真咬、搏斗、抄取、捕获和失败清理。
- 鱼行为：巡游、受窝料吸引、观察鱼饵、试探、咬钩、挣扎、乏力、逃脱和被捕获。
- 环境事件：未激活、预告、持续、收尾和冷却等有明确生命周期的事件。

两者的接线方式是：StateTree 的 Task 或转换发出 Gameplay Event / 请求激活 Ability；GAS 执行动作后返回成功、失败、取消或结构化结果；StateTree 根据结果继续转换。StateTree 不重复实现体力、效果、动作互斥和网络预测，GAS 也不承担整局、鱼 AI 或多人钓鱼会话的总流程图。

所有影响玩法真相的 StateTree 只在服务器运行。客户端不并行裁决同一棵树，只接收公开阶段、必要状态以及 GAS/Gameplay Cue 表现。这样仍然维持服务器权威，避免服务端与客户端分别走出不同流程。

只采用 GAS 的候选方案被否决：Gameplay Ability 确实可以通过 Ability Task 编写多阶段异步动作，但把局流程、鱼行为和多参与者钓鱼会话全部塞进长生命周期 Ability，会产生大量项目专用 Ability Task，并让非角色流程依赖某个 ASC。采用 GAS + StateTree 能直接复用引擎已有的层级状态、转换、条件、Task 和调试视图，避免在 GAS 内部重新发明流程运行器。

## MVC 问题暴露出的项目框架缺口

提出“UMG 使用 MVC 还是 MVVM”，真正关注的不是一个 UI 名词，而是此前总体骨架只说明了**用了什么技术、系统由谁持有**，还没有完整说明**每个领域内部如何组织职责与数据流**。

完整项目框架必须同时回答三个层次：

1. **宿主架构**：Unreal 的 `GameInstance`、`World`、`GameMode`、`GameState`、`PlayerState`、`PlayerController`、Pawn 和 Subsystem 分别承载什么生命周期。
2. **领域架构**：钓鱼、物品、局流程、鱼行为、印记和存档内部采用什么模型，命令如何进入、真相如何变化、结果如何产生。
3. **表现架构**：UI、动画、音效和特效如何读取领域结果、如何提交用户意图，以及如何保证它们不成为第二套玩法规则。

因此，后续不只记录“UI 用 MVC”，而要给每个主要领域确定内部架构、入口模式、状态模型、输出形式和禁止依赖。

## 项目级职责层次

Catfishing 不采用完整 Clean Architecture 或洋葱架构的多层工程模板，但保留其中真正有价值的依赖方向。各层是职责概念，主要通过同一 Runtime 模块中的目录和类型表达，不机械拆成多个 UE 模块。

```text
表现层       UMG、AnimBP、Gameplay Cue、音效与特效
    ↓ 意图 / ↑ 展示状态
应用协调层   UI Controller、GAS Ability、流程 Coordinator
    ↓ 命令 / ↑ 结果
领域层       局状态机、FishingSession、物品事务、鱼行为、印记规则
    ↓ 持久化请求 / ↑ 加载结果
基础设施层   OnlineSubsystemSteam、SaveGame、资产管理、文件与引擎适配
```

依赖规则如下：

- 表现层可以认识展示结构和应用入口，不能直接修改领域状态。
- 应用协调层负责串联一个完整用例，不复制领域规则。
- 领域层产生权威结果，不依赖 UMG、Widget Blueprint、Steam 接口或具体美术资产。
- 基础设施层只在真实外部接缝处提供实现；Steam、文件和资源加载失败通过项目结果类型返回，不向领域层泄漏平台细节。
- 网络权威贯穿应用协调层和领域层：客户端提交意图，服务器执行领域命令并复制结果。

## UMG 的 MVC 架构

### 为什么采用 MVC

项目采用 MVC 的直接原因是玩家会操作 UI。大厅建房与加入、背包选择、鱼护和鱼缸转移、祭坛献祭、图鉴翻阅、相册隐藏和设置修改，都需要把“玩家在界面上做了什么”转换成明确的游戏命令。

MVC 在这里解决的是交互链路：View 接收鼠标、键盘或手柄操作，Controller 解释操作意图并调用游戏入口，Model 发生变化后再由 View 显示结果。项目不再引入 Passive View/MVP 作为设计依据。

#### Model

Model 是界面对应的游戏数据与规则入口，例如会话信息、玩家物品容器、共享鱼缸、图鉴档案、印记相册和设置数据。运行时真相仍由 `GameState`、`PlayerState`、Character ASC、领域 Actor、GAS 或本地档案持有。

View 通过 Model 的只读查询和变化事件取得显示数据。只有实际出现复杂展示转换或需要组合多个来源时，才增加专用 UI 读取结构；不默认给每个页面再造一套 UI Model / ViewModel 对象。

#### View

View 是 `UUserWidget` / Widget Blueprint，负责布局、样式、局部动画和控件反馈。

View 只能做三件事：

1. 通过 Model 的只读入口显示数据，并在 Model 发出变化通知时刷新对应区域。
2. 播放纯表现动画和本地交互反馈。
3. 把按钮、选择、拖放、确认和取消转换成语义化 UI 事件发给 Controller。

View 不允许：

- 为了显示一个字段就在蓝图里到处查找世界 Actor，或者绕过领域 Model 的正式读取入口。
- 直接调用服务器 RPC、GAS Ability、物品事务或存档写入。
- 在 Widget Blueprint 中计算配额、容量、归属、解锁或其他玩法规则。
- 使用 Tick 轮询玩法数据，或大量使用每帧执行的传统 UMG Property Binding。

可复用的小型叶子控件只需要“接收数据并抛事件”，不为每个按钮、列表项和进度条创建独立 Controller。

#### Controller

MVC Controller 是按页面或完整 UI 功能建立的 `UObject`，例如组局、HUD、鱼护、共享鱼缸、图鉴、印记相册和设置 Controller。它不是 `APlayerController` 的同义词。

Controller 负责：

1. 接收 View 的语义事件，判断这是页面导航、纯本地设置还是玩法命令。
2. 调用应用入口、GAS Ability 或服务器命令，不直接修改领域 Model。
3. 管理确认、取消、页面切换和请求中的交互流程。
4. 把结构化命令失败转换成界面可显示的提示，不让 View 猜测失败原因。
5. 不负责逐字段刷新 View，不保存权威玩法状态，也不重复实现领域校验。

Controller 按“一个完整页面或功能”划分，而不是按 Widget 数量划分。HUD 可以由少量功能 Controller 组合，但禁止出现持有全项目引用的万能 `UIController`。

### 无 CommonUI 的 UI 宿主

项目建立一个小型本地 UI 宿主，负责 CommonUI 被砍掉后仍然确实需要的生命周期能力：

- 每个本地玩家一个 `ULocalPlayerSubsystem` 类型的 UI Manager。
- 一个根 Widget，固定提供 `HUD`、`Screen`、`Modal` 和 `Notification` 四个层。
- UI Manager 只负责创建根节点、打开/关闭页面、Modal 栈、输入模式、鼠标与焦点恢复，以及页面 MVC 三者的装配和生命周期。
- UI Manager 不认识背包容量、图鉴解锁或祭坛规则；这些属于相应 Model，交互请求由对应 Controller 提交。
- 地图旅行或 PlayerController 替换时，UI Manager 先释放旧世界绑定，再为新世界重新装配页面 Controller，禁止保留悬空 Actor 引用。

这是针对本项目界面数量建立的最小导航层，不扩写成通用 UI 框架。

### UI 数据流

```text
服务器领域状态
  -> 复制到 GameState / PlayerState / 领域 Actor
  -> Model 的只读入口与变化通知
  -> View 读取并刷新

View 用户操作
  -> 语义事件
  -> 页面 Controller
  -> Ability / 应用命令 / 服务器请求
  -> 领域校验与状态变化
  -> 沿上面的读取链刷新 View
```

UI 不做“先本地改 Model，失败再猜着回滚”。需要即时响应的操作由 GAS 预测或明确的本地 Pending 状态提供反馈，最终仍以服务器复制结果收敛。

## 各领域的内部设计架构

| 领域 | 内部架构 | 命令入口 | 真相与输出 | 主要禁止项 |
|---|---|---|---|---|
| Steam 会话 | Adapter + OnlineSubsystem 既有会话状态 | Host、Find、Join、Leave、Invite | GameInstance 生命周期的会话状态与结构化结果 | 玩法代码直接调用 Steam 接口；Delegate 到处注册 |
| 局与天流程 | 服务器 StateTree + GAS 事件接线 | StartRun、SubmitDayReady、ResolveQuota | StateTree 编排流程，`GameState` 复制公开阶段和对局快照 | 客户端运行权威流程；UI 直接推动天数 |
| 玩家动作 | GAS 的 Command + Tag/Effect 模型 | 输入激活 Ability 或领域事件触发 Ability | ASC 持有动作许可、属性、效果与表现触发 | 每个系统再造自己的互斥、Buff 和取消协议 |
| 钓鱼 | `FishingSession` + StateTree + GAS | Start、Join、Respond、Withdraw、AttemptCapture、Cancel | StateTree 持有会话阶段，GAS 执行动作，最终输出唯一 `CaptureResult` | Ability、鱼 Actor、钓手和 UI 分别推进同一阶段 |
| 物品与渔获 | Container Aggregate + Transaction | Capture、Transfer、Steal、Consume、Sacrifice | 唯一 Item Instance、所有者与容器版本；输出事务结果 | 直接改数组；先删后加；多个容器同时拥有同一鱼 |
| 鱼与鱼群 | StateTree + 数据化性格参数 | 环境刺激、窝料、鱼饵、咬钩和会话释放 | 服务器 StateTree 持有行为状态；Hooked 后多人流程交给 FishingSession | AnimBP 决定鱼行为；每个鱼种复制一套蓝图流程 |
| 世界与天气 | StateTree + Modifier 查询 | 时间推进、天气切换、自然事件触发 | 服务器 StateTree 编排事件，`GameState` 复制世界快照 | 天气系统直接修改每条鱼和每个玩家的内部字段 |
| 印记 | Trigger → Adjudication → Capture Plan → Local Render → Archive 管线 | 各领域提交语义化印记候选 | 服务器决定事件与参与者；客户端执行本地成像并写本地相册 | 各系统自行截图和分发；无上限保存；UI 持有图片真相 |
| 图鉴与解锁 | 规则归约 + 本地档案 | 捕获结果、里程碑结果 | 档案持有跨局事实，返回新增记录/解锁结果 | Widget 直接解锁；鱼被偷后回滚已记录图鉴 |
| 本地存档 | 深模块 + 原子保存 | LoadProfile、CommitProfile、LoadImprintIndex | `USaveGame` 与本地印记文件；结构化成功/失败结果 | Steam Cloud 依赖；任意系统直接调用文件读写 |
| UI | UMG MVC | View 交互进入 Controller，再转为 Ability、本地命令或服务器请求 | 领域 Model 是真相，View 通过正式只读入口和事件显示结果 | Widget 直接写 Model 或网络；Tick 轮询；万能 Controller |
| 动画/VFX/音频 | 状态驱动的表现 Adapter | Gameplay Cue、复制通知、会话表现事件 | AnimBP/Cue 只消费已确认状态并播放表现 | AnimNotify 直接判定捕获或归属；表现层写规则状态 |

这张表是后续框架类设计的索引。搭建项目框架时，每个目录先建立表中必要的真相类型、命令入口和结果类型，不先批量生成空 Manager、Interface、Component 或 Blueprint 基类。

### 源码与资产组织

建议先保持一个 `Catfishing` Runtime 模块，并按真实领域组织目录：

```text
Source/Catfishing/
  Core/          项目标识、Tag、日志、通用结果类型
  Online/        Steam 会话适配与房间流程
  GameFlow/      局、天、日夜、配额和公共事件

  World/         天气、自然事件、交互点和营地世界逻辑
```

编辑器校验、批量资产创建或专用调试面板确实出现时，放入独立的 `CatfishingEditor` 模块。目录边界先表达职责，不为目录逐一创建插件、Subsystem、接口和 Component。

### 当前框架建议的核心结论

当前建议不是十项彼此独立的技术选择，而是一套组合：

> Windows PC + Steam、房主 Listen Server、服务器权威、OnlineSubsystemSteam、项目级 GAS + StateTree、Enhanced Input、原生 UMG/MVC、Primary Data Asset/Asset Manager、统一物品事务、本地 SaveGame、C++ 规则与蓝图表现分层，以及单 Runtime 模块的模块化单体。

如果其中一个基础选择被否决，需要沿上述运行链检查它影响的相邻边界并整体修订，不能只替换名词而保留冲突的下游设计。

## 整体框架闭环检查（基于 GDD，2026-08-11）

### 复核结论与事实等级

重新按 GDD 的实际玩法链检查后，框架接线需要同时标明三类信息，防止把产品事实、开发判断和尚未验证的引擎细节混为一谈：

1. **GDD / 用户确认事实**：1–8 人且单人可玩；房主 Listen Server、服务器权威；河流、森林湖和营地同属湖畔主场景；白天、夜晚与翻天发生在同一局内；猫状态与物资跟局走，鱼类图鉴、印记和解锁跟人走；近岸抢抄由第一个合法成功者取得鱼；实物鱼与图鉴记录必须分离。
2. **当前架构决定**：Character 持有 ASC；PlayerState 只承担稳定身份和连接期事实；只设 Frontend 与 Lake 两类地图；组局后直接进入 Lake；使用服务器 StateTree 编排长流程，短事务由领域模块直接提交；所有物品变化和捕获结算都必须幂等。
3. **待 UE 5.8 实装验证**：Character-owned ASC 的服务端/客户端初始化与销毁回调、StateTree 与 GAS 的事件接缝、容器增量复制和并发 Compare-and-Commit、Steam 身份与重连回调、共同印记成像、UMG 与 Enhanced Input 的焦点切换。

本节撤回上一轮两个没有得到 GDD 支持的推断：**不再把 ASC 放在 PlayerState，也不再建立 Lobby Map 和 Lobby → Lake 无缝旅行。**旧方案仅保留在文末纠偏历史中，不能作为现行实现依据。

### 从 GDD 得到的项目专属边界

- `局与进程.md` 明确一局在同一个天循环中经历白天、入夜、篝火和翻天，局末才清空物资；`环境与氛围.md` 明确河流与森林湖同属湖畔主场景。这要求 Lake 在一局内保持同一个 Gameplay World，而不是按天或区域旅行。
- `联机社交.md` 只要求创建、邀请、中途加入和退出足够轻量，没有准备房或准备阶段需求。因此 Online Session 是会话状态，不是一张 Lobby 地图。
- `猫咪与状态.md` 只描述一具持续活动的猫身体，并明确饥饿、疲惫、中毒、淋湿和倒地都跟局走；GDD 没有换 Pawn、死亡重生或载具附体需求。因此身体状态与动作框架跟随 Character 比跨 Pawn 的 PlayerState ASC 更贴合项目。
- `钓鱼系统.md` 把钓鱼定义为从抛竿、咬钩、搏斗到近岸抢抄的多人长流程，并明确抢抄先到先得；它需要 `FishingSession` 持有共享阶段，但最终归属必须由一次服务器事务提交。
- `鱼类图鉴.md` 明确实物鱼会流转和消失，图鉴记录只增不减；捕获结果必须同时产生“局内鱼实例归属”和“永久记录事件”，但二者不能共用同一对象。
- `印记图鉴.md` 要求所有玩法只抛候选，由印记系统统一接收、裁决、成像和分发；共同印记还要求同一张照片、同一帧，并在掉线重连后补发。

### 当前 UE 对象承载关系

以下类名均为**拟定名**。工程仍是空模板，当前确定的是职责和生命周期，不代表这些类型已经存在。

| 生命周期 | 拟定宿主 | 当前职责与可写真相 |
|---|---|---|
| 进程级 | `UCatOnlineSubsystem`、`UCatProfileSubsystem`（`UGameInstanceSubsystem`） | 前者适配 Steam 身份、建房、邀请、加入和退出；后者只在各拥有者客户端加载本地档案、持久化待处理授予并合并图鉴/印记/解锁。二者不裁决局内玩法 |
| 本地玩家级 | `UCatUIManagerSubsystem`（`ULocalPlayerSubsystem`） | 创建 UMG 根节点和页面 MVC，管理输入模式、焦点、页面与弹窗；不持有玩法真相 |
| 一局服务器级 | `ACatfishingGameMode` | 创建本局服务和 `ST_RunFlow`，裁决加入、白天截止、额度、入夜、翻天与结算；持有断线记录注册表，只存在于服务器 |
| 一局复制级 | `ACatfishingGameState` | 复制当前天、日夜阶段、局内时间、天气、额度、公共事件和共享状态；客户端只读 |
| 连接级 | `ACatfishingPlayerState` | 持有稳定网络身份、连接/在场状态、翻天确认和重连索引；不持有 ASC、猫身体属性或物品容器 |
| 身体级 | `ACatCharacter` | 同时作为 ASC Owner 与 Avatar；持有 Ability、Attribute、Effect 和身体 Tag，承担移动、碰撞、动画宿主与世界交互 |
| 输入级 | `ACatfishingPlayerController` | 把 Enhanced Input 与 UI Controller 产生的意图送入 Character Ability 或应用命令；不直接裁决玩法 |
| 单次钓鱼级 | `AFishingSession` | 服务器创建并运行 `ST_FishingSession`；持有钓手、鱼、协作者、阶段、唯一结算键和终止原因 |
| 活动鱼级 | `AFishActor` | 服务器运行必要的 `ST_FishBehavior`；进入 Hooked 后把多人会话阶段交给 `FishingSession` |
| 容器级 | 拟定的容器 Aggregate / `AItemContainerActor` | 分别持有鱼护、共享鱼缸、祭坛输入等局内集合；只能由 Inventory 事务改写 |
| 一局印记级 | 拟定的 `URunImprintService`，由 GameMode 创建 | 对印记候选去重、裁决参与者、生成 Capture Plan 并记录待分发项；不直接写客户端文件 |
| 断线间隙级 | 拟定的 `FRunPlayerRecord` 注册表，由 GameMode 持有 | 以稳定网络身份索引允许恢复的身体快照、容器关联和待补发结果；在线时不能与现存对象同时成为真相 |

ASC 改为 Character-owned 的理由不是个人偏好，而是本项目只有一具猫身体，动作和饥饿、疲惫、中毒、淋湿、倒地都属于这具身体。PlayerState 保留的是连接身份，不再为了不存在的换 Pawn / 无缝旅行需求承接身体状态。

### 项目专属领域模块与统一执行链

项目仍保持一个 `Catfishing` Runtime 模块，内部按业务目录形成模块化单体：Online/Profile 处理平台与本地档案，GameFlow 处理局与天，Player/Ability 处理猫身体动作，Fishing 处理鱼与钓鱼会话，Inventory 处理物品与容器事务，Imprint/Progression 处理印记与永久记录，UI 处理 UMG MVC。它们不是各做各的系统，统一进入下面一条执行链：

```text
Enhanced Input / UMG View 产生玩家意图
  -> PlayerController / MVC Controller 转成 Ability 或应用命令
  -> 服务器校验身份、权限、阶段和输入上下文
  -> StateTree 编排长流程，或领域模块直接执行短事务
  -> 领域模块生成结构化 Result，并由唯一真相持有者一次提交
  -> GameState / PlayerState / Character ASC / 领域 Actor 复制公开结果
  -> Gameplay Cue、AnimBP、音效和 MVC View 消费结果
  -> 服务器向拥有者客户端投递带稳定 ID 的 `ProfileGrant`（拟定）和印记计划
  -> 客户端 ProfileSubsystem 先幂等落入本地待处理队列/日志，再回执并合并图鉴、印记与解锁
```

世界交互和 UI 不能建立第二条业务路径。例如把鱼叼到祭坛和在祭坛界面选择献祭，最终都调用同一个 `Sacrifice` 事务；Widget、Ability 和 StateTree Task 都不能直接改容器数组。

### GAS 与 StateTree 的项目分工

**GAS 贯穿猫的动作与身体状态**：抛竿、提竿、收线、松线、抄网、搬运、进食、偷取、扑倒和救援等动作使用 Ability；动作许可、互斥、取消和局内身体状态使用 Tag、Attribute 与 Gameplay Effect；Gameplay Cue 只消费结果并播放表现。

**StateTree 贯穿确有长生命周期的服务器流程**：`ST_RunFlow` 编排白天、截止、入夜、篝火、翻天和局结算；`ST_FishingSession` 编排抛竿、等待、试探、真咬、搏斗、近岸、抢抄和终止；`ST_FishBehavior` 只在活动鱼确实需要层级行为时使用。客户端不运行权威流程树。

短事务不为“统一技术”硬塞进 StateTree。捕获提交、容器转移、偷取、进食、献祭、图鉴归约和印记管线使用普通领域命令与 Result；StateTree Task 和 Ability 只能调用这些入口。项目不自研第二套状态机，也不建立全局事件总线。

Gameplay Tag 只表达稳定语义，业务数据使用明确的 `USTRUCT`：`Ability.*` 表示动作，`State.*` 表示身体或会话状态，`Event.*` 表示跨模块事件，`Cue.*` 表示表现，`Failure.*` 表示结构化失败类别。Tag 不能代替鱼实例、物品事务、捕获结果或重连快照。

### 两地图与 Online Session 模型

```text
Frontend Map：本地主菜单、档案和创建/加入入口
  -> 创建或加入 Steam Session 后直接进入 Lake Map
Lake Map：营地、河流、森林湖、白天、夜晚和整局结算
```

- Online Session 负责房间发现、邀请、加入和退出，不对应独立地图。
- Lake 是 Listen Server 的 Gameplay World。中途加入直接进入当前 Lake，并从 GameState 与各领域复制状态补齐现场。
- 白天到夜晚、篝火到翻天、河流到森林湖都不旅行；它们只改变 RunFlow、位置和世界表现。
- 局结束或房主退出后销毁 Session 并返回 Frontend。房主退出即结束本局，不实现主机迁移。
- 当前体量不默认采用 World Partition；只有实际地图规模证明普通关卡不足时再评估。

### 捕获、物品与永久记录的幂等链

`AFishingSession` 在服务器创建唯一结算键。任何近岸抄取请求都携带该键和请求键，事务按下面顺序执行：

1. 校验会话仍可结算、请求者合法、目标鱼与抄取窗口一致。
2. 对会话终态和目标容器版本执行 Compare-and-Commit；只有第一个合法请求能够提交。
3. 服务器 Compare-and-Commit 一次提交关闭 FishingSession、确定最终持有者、把唯一鱼实例放入目标容器，并生成规范化的 `ProfileGrant`（拟定）与印记候选事件；该原子边界不包含任何远端磁盘写入。
4. 每个 `ProfileGrant` 都有稳定唯一的 Grant ID，表达“授予一条不可因实物鱼后续去向而撤销的图鉴记录”；拥有者客户端持久化后，它才成为本地永久记录。实物鱼、授予结果与照片记录仍是三种不同对象。
5. 重复或迟到请求返回 `AlreadyResolved`，不能再次给鱼、刷新最佳记录或抛第二个印记候选。

图鉴和印记最终落在各拥有者客户端的本地档案，服务器不能完成或原子包含远端 `USaveGame` 写入。服务器在本局存活期间按 Grant ID 保留未回执授予，玩家重连时重发。客户端 `ProfileSubsystem` 收到授予后，先按 Grant ID 幂等写入本地持久化待处理队列/日志，再发送回执，并把授予合并到图鉴、印记或解锁；重复投递只读取既有结果。

捕获以外的 Transfer、Steal、Consume、Sacrifice 也必须携带唯一事务键和期望容器版本。事务只能产生成功、明确失败或 `AlreadyResolved`，不能先从来源删除、再异步尝试加入目标而留下半完成状态。

### 初始化、重连与清理顺序

**启动与入局：**

1. GameInstance 创建 Online 与 Profile Subsystem；本地 Profile 完成版本检查和加载。
2. Frontend 的 LocalPlayer UI Manager 创建根 UI，组局 Controller 调用 Online Subsystem 创建或加入 Session。
3. 房主以 Listen Server 打开 Lake；`ACatfishingGameMode` 创建本局服务并启动 `ST_RunFlow`，`ACatfishingGameState` 发布初始快照。
4. 玩家加入后先建立 `ACatfishingPlayerState` 的稳定身份与在场记录，再生成并占有 `ACatCharacter`。
5. Character 在服务端和拥有客户端完成 Character-owned ASC 初始化、授予基础 Ability Set，随后 PlayerController 绑定 Enhanced Input，UI Model 订阅复制状态。

**普通玩家重连：**

1. 服务器按 Steam Stable Net ID 查找限时 `FRunPlayerRecord`，拒绝同一身份同时占用两份在线真相。
2. 依次重建 PlayerState 身份、Character/ASC、允许恢复的局内身体状态和容器关联，再按 Grant ID 重发服务器仍保留的未回执 `ProfileGrant` 与印记投递结果。
3. 掉线时正在进行的 FishingSession 不原地续接；服务器按中断规则结束旧会话，释放鱼和参与者引用，避免半场搏斗复活成重复结算。

**离局与局末：**

1. UI Manager 先解绑旧 World、Controller、Model 与 Delegate，取消本地 Pending 交互。
2. 服务器停止接收新命令；进行中的领域请求要么一次提交，要么以终态失败返回，不能留下半事务。
3. 局结束前，服务器对在线玩家执行有界的 `ProfileGrant` 最终重发与回执收集；这只提高送达概率，不代表服务器完成远端本地存档。
4. FishingSession、鱼行为和 RunFlow 依次终止，容器与猫状态随局清空；随后销毁 Online Session 并返回 Frontend，所有 Lake Actor 引用和本局未回执授予随本局释放。

身体状态恢复的白名单、断线记录保留时长和钓鱼中断的具体回退属于待实现设计，但“FishingSession 不原地续接、不可重复结算、猫状态不能跨局保存”是现行边界。若授予尚未送达或尚未写入客户端待处理日志，远端玩家掉线后房主又结束本局，在没有 Steam Cloud 或外部后端的当前范围内无法保证恢复；这是已接受的本地存档边界，不引入跨主机授权账本补偿。

### 待 UE 5.8 实装验证

以下接线不能只凭文档认定通过，进入框架实现时必须用最小纵向原型验证：

1. Character 同时作为 ASC Owner/Avatar 时，服务端与拥有客户端应在哪些 UE 5.8 生命周期回调中初始化、授予 Ability、刷新 ActorInfo 和释放绑定。
2. StateTree Task 通过 Gameplay Event 激活 Ability、等待成功/失败/取消 Result，再驱动转换的线程与生命周期边界。
3. Fast Array 或等价容器复制在两名玩家同帧抢抄、偷取和献祭时的版本校验、去重与客户端收敛。
4. OnlineSubsystemSteam 的 Stable Net ID、邀请、中途加入、掉线与重连回调在 Listen Server 下的真实顺序。
5. 共同印记如何保证同一张照片、同一帧，以及掉线玩家补发时是分发宿主成像结果还是可重复的 Capture Plan。
6. UMG MVC 页面打开/关闭时与 Enhanced Input Mapping Context、鼠标捕获和焦点恢复的实际配对。

### 工程接线基线

当前工程仍是空模板，以上全部是待实现的架构蓝图：

- `.uproject` 的 EngineAssociation 是 5.8，目前只启用编辑器建模工具；没有启用 GameplayAbilities、StateTree、GameplayStateTree 或 OnlineSubsystemSteam。
- Runtime 模块只依赖 `Core`、`CoreUObject`、`Engine`、`InputCore`；尚未接入 GAS、Gameplay Tags/Tasks、StateTree、Enhanced Input、UMG、OnlineSubsystem 和 Steam 模块。
- `Source/Catfishing` 只有默认模块入口和空 `MyClass`，`Content` 没有项目地图与玩法资产。
- 默认地图仍指向引擎 OpenWorld 模板，配置中仍有已砍掉的 CommonUI 痕迹。这些只能说明尚未搭建，不能反推最终设计。

### 框架搭建完成的判定

项目框架不是创建一批空基类和目录。只有下面纵向链路实际跑通，才算当前蓝图完成接线：

1. Win64 客户端能够创建/加入 Steam 或测试 OSS Session，并直接进入 Lake。
2. Character-owned ASC 在服务端与拥有客户端正确初始化，Enhanced Input 能激活项目 Ability，身体 Attribute/Tag 正确复制。
3. 服务器 `ST_RunFlow` 与 `ST_FishingSession` 能通过 Gameplay Event/Result 和 Ability 协作，不产生第二套状态。
4. 两名玩家竞争同一个占位捕获时，只有一个服务器事务成功；重复请求返回 `AlreadyResolved`，鱼实例、带稳定 ID 的 `ProfileGrant` 和印记候选各产生一次，且事务不包含远端磁盘写入。
5. UMG MVC View 能通过 Controller 调用同一条领域命令并显示复制结果，场景交互与 UI 交互不会走两套规则。
6. 普通玩家掉线重连后恢复允许状态并重发本局仍保留的未回执授予，旧 FishingSession 不续接；房主退出时本局结束，未送达或未在客户端落盘的授予不保证跨房主恢复。
7. 一项跨局图鉴或印记索引能写入版本化本地 SaveGame，重新启动后读取；局内物资和猫状态不跨局残留。

这些是框架纵向闭环，不要求先完成正式钓鱼数值、鱼表、美术或全部 UI。

## 仍需细化的实现设计

以下内容不改变总体骨架，但在进入对应代码前还需落成具体类型和数据结构：

- 初期保留单一 `Catfishing` Runtime 模块，按 `Game`、`Player`、`Fishing`、`Inventory`、`Camp`、`Data`、`Save`、`UI` 等业务目录组织源码。
- 不自研通用状态机框架；玩家与 Actor 动作使用 GAS，多阶段流程和行为使用 StateTree，两者通过 Gameplay Tag、Gameplay Event 和结果接线。
- 系统之间优先使用直接调用或范围明确的 Delegate；没有真实生产者和消费者时，不建立全局事件总线。
- 只有具备独立生命周期、会被多个宿主复用的能力才拆为 Actor Component，避免一个概念对应一个组件。
- 鱼种、装备和道具 Definition 使用 Primary Data Asset；批量数值使用 Data Table / Curve Table。各领域的具体字段和引用关系仍需细化。
- 当前完整框架组合以“项目框架总体骨架”章节为统一讨论底稿，后续单项结论必须回写到该骨架，不能形成互相独立的技术孤岛。

## 过度设计的判断标准

此前曾将若干具体技术形态直接列为“过度设计”，该口径过于武断，现予以撤回。模块、插件、接口、组件、事件系统或通用框架本身不能决定是否过度；需要根据它们在完整项目中的实际收益判断。

评估一项架构设计时，应回答：

1. 它是否服务于 GDD 已知需求、完整项目范围或已经识别出的工程风险？
2. 如果现在不建立这条边界，后续是否大概率出现推倒重写、重复实现、对象特判、网络分叉或生命周期缺陷？
3. 是否存在明显更简单、但仍能提供相同稳定性和扩展能力的实现？
4. 它节省的后续开发与排错成本，是否值得当前的搭建、学习和维护成本？
5. 团队能否清楚说明它的使用规则、所有者和调试路径？

如果一项设计没有明确项目收益，主要依赖遥远假设，却持续增加接入步骤和维护负担，它属于应避免的过度设计。如果一项设计能够覆盖完整需求、稳定关键边界并显著降低后续缺陷，即使当前需要额外投入，也可能是必要的前瞻性设计。

## 本轮纠偏记录

此前提出的“先定义第一个可玩版本”只适合作为未来的实现与验证方法，不能代表当前架构讨论的目标。当前目标是先设计与独立项目体量匹配的完整架构，再决定它的落地顺序。

此前还曾把“避免过度设计”偏向解释为“少抽象、等多个用例出现后再设计”。该解释已撤回。当前正式口径是：既避免建设对完整项目没有必要的复杂设施，也避免只顾眼前可运行、缺乏前瞻性而导致后续大量缺陷和返工。

此前采用按技术主题从上游到下游逐项讨论的方式，导致话题分散且难以直接指导项目框架搭建。该方式已停止。后续以完整运行链、状态所有者和模块接口为主线，技术选型、架构模式和设计模式都必须放回同一张项目骨架中讨论。

此前框架只列出系统边界和技术组合，没有为每个领域说明内部职责模型。MVC 问题证明这种粒度不足：知道“使用 UMG”并不能指导 Widget、状态和用户操作如何组织。后续框架必须同时记录宿主架构、领域架构与表现架构，并为各领域明确命令入口、真相、输出和禁止依赖。

上一轮使用“Passive View MVC”指代 UMG 方案，命名不严谨。Passive View 不是本项目发明，但通常被讨论为 MVP 变体；本项目不再使用该组合名称，统一写作 UMG MVC，并以本纪要定义的 Model、View、Controller 职责为准。

上一轮把 MVC 的讨论重心放到了表现分层和测试性，没有抓住项目采用 MVC 的直接原因是玩家会操作 UI。当前口径已改为：View 接收玩家界面交互，Controller 把交互转换成游戏命令，Model 提供结果并驱动 View 更新。

上一轮还建议为简单流程自研 `enum + Transition` 状态机，该方案已撤回。项目在候选“只用 GAS”与“GAS + StateTree”之间选择 **GAS + StateTree**：GAS 负责动作生命周期与效果，StateTree 负责流程和行为编排，不再从零实现通用状态机运行器。

整体闭环检查发现此前只确定了技术选型，却没有明确这些技术由哪些 UE 对象承载、按什么调用链协作、谁有最终写权限，以及地图旅行和重连时如何保持或释放状态。此前用“缺少装配规则”概括这件事过于抽象，也容易被误解成空项目缺文件，现统一改称“框架接线规则”。框架现按“意图 → Ability/命令 → 服务器校验 → StateTree/领域事务 → 复制结果 → MVC/Cue → 本地持久化”连接，并补齐各层生命周期和框架成立的纵向验收条件。

随后按 GDD 重新复核发现，上一轮把 ASC 放在 PlayerState、增加 Lobby Map 并使用 Lobby → Lake 无缝旅行，是从通用 UE 联机经验推导出的方案，不是项目需求。两项均已撤回：现行规则改为 Character 持有 ASC，PlayerState 只承载稳定身份和连接事实；地图只保留 Frontend 与 Lake，组局直接进入 Lake。旧方案只作为纠偏历史保留，禁止继续用于工程接线。

此前还把服务器捕获裁决与远端玩家的本地 Profile 写档描述成同一原子事务，并在局末暗示服务器能够完成图鉴、印记和解锁持久化；该表述已撤回。现行边界是服务器原子生成带稳定 ID 的授予结果并在本局内重发，拥有者客户端先持久化待处理记录再回执和合并，服务器不承诺远端 `USaveGame` 已完成。
