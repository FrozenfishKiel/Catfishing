## 二、先看这一节：会绊到你的三件事

### 1. 有东西被整条删掉了，不是挪位置

找不到以下符号是**预期**的，不是漏改。删除处都留了墓碑注释写明何时为何删：

| 删掉的 | 为什么 |
|---|---|
| `ServerBeginTheft` / `ServerCatchTheft` / `FCatTheftCommand` / `FCatTheftResult` 及整条偷鱼协议 | 09-11 裁决②：偷鱼不是机制，偷是玩家的主观叙述；机制层只做客观的「拿鱼」。这套本来也零调用点、玩家发不起 |
| `CatFishContainerService` 的 `BeginFishTheft` / `ReturnStolenFish` / `TheftEscrows` | 上一条删净后零调用点。拆它时同步检查了 `ExportPersistedWorldFishContainers` 的导出前置 |
| `InitializeFishingStaminaForSession` / `RequestFishingStaminaReset` | 09-11 裁决④删「每次进搏斗把主控体力补满」。同语义的初始播种入口改名 `SeedFightStaminaToMaximumFromAuthority`，只服务角色初始化与测试夹具 |
| 商店的「待交付」中间态 | 09-09 晚按 bug 定性（代码超前 #15），购买成功即进营地公共仓库 |
| 草药恢复链、`Herb` 装备类别 | 设计早已删除，但代码里是**开启状态**，是真在跑的死机制 |

### 2. 字段改名了，已有资产靠 CoreRedirects 保值

`Config/DefaultEngine.ini` 里加了 PropertyRedirects / EnumRedirects。**改名清单**：

- `CatFishDefinition::EatingExperience` → `EatingExperiencePerKilogram`（语义从定额变系数）
- `CatFishDefinition::FishFightStamina` → `FishFightStaminaPerKilogram`（同上）
- `ECatFishFoodSafety::Toxic` → `SevereToxic`，并新增 `Inedible` 档

改名不是洁癖：这两个字段的**语义**从「定额」变成了「每公斤系数」，名字不改会让下一个人按旧含义填值。

### 3. 存档新增字段但**没有抬 schema 版本**

`FCatSaveSlotSummary::bRunCompleted` / `UCatRunSaveGame::bRunCompleted` 是纯加法字段。
抬版本会让已有 v6 档整批读不出来，与 09-11 裁决③「游戏永不删档」相悖。

**代价**：同一个 `FormatVersion=6` 现在对应两种字段集，**旧构建读新档会静默丢掉终局标记、
把打完的局当成可继续**。发布前只有一套构建所以暂时安全——这是个有保质期的安全，别忘了它。

## 四、行为变化（不是重构，是玩起来不一样）

按裁决改的，**核口径请找对应分册属主**：

1. **落水即结场**（此前只播表现、会话转入无人值守放线继续跑）。无人值守放线只留给主位主动离竿
2. **响应窗超时＝鱼逃终局并扣饵**（此前回等待、重新派种子、不扣饵）
3. **竿强瞬断报废鱼竿**，与耐久归零共用同一结局与表现。**前置未落地，见第六节**
4. **碾压沿钓线朝持竿猫身后甩 2.5 米**（此前落在猫脚下）
5. **祭坛任一人发起＋3 秒可打断倒计时**（此前每人各按一次、走出 8 米圈即撤销全部确认）
6. **终局后的存档槽标记已完结、不再提供「继续」**。**代码不删档**，只标记＋开新局写新槽
7. **图鉴收集层收件人从拾取者改回上钩者**——此前合作钓鱼里「A 上钩、B 跑过去叼走」会记到 B 头上
8. **选鱼时点从「提竿成功后」提前到「咬钩计时到点」**，并在那一刻生成鱼影。见下条警告
9. **倒地只挡涉及他人容器的转移**，不挡整理自己的背包

## 五、⚠️ 一个反复踩到的坑，请合并时留意

**四次**同样的错误：新增一个必填字段 → 对它 fail-closed → 而没有任何资产配过它 → 功能静默死掉。

- 竿强度 `0` 被当成「强度极低必断」（写代码时拦下）
- 倒地拒绝扩到了自己的背包（代码审查时拦下）
- 试探期时长只认逐鱼资产 → **试探期永远进不去**（跑测试才发现）
- 逐鱼力量系数 K 未配置就跳过候选 → **候选跳光、选鱼失败**（跑测试才发现）

后两条已修，修法都是**回退到迁移前的事实源并记警告**，而不是把功能判死。

**给新增必填字段的人一条经验**：先问「现有资产配了吗」。没配就得有迁移路径，
fail-closed 只适用于「配错了比不配更危险」的场合。

## 七、怎么验

**编译**（增量约 10~40 秒）：
```
Build.bat CatfishingEditor Win64 Development -Project="<repo>/Catfishing.uproject" -WaitMutex
```

**自动化测试**：
```
UnrealEditor-Cmd.exe "<repo>/Catfishing.uproject" -ExecCmds="Automation RunTests Catfishing.Unit; Quit" ^
  -unattended -nopause -nosplash -NullRHI -log
```
结果在 `Saved/Logs/Catfishing.log`，数 `Result={Success}` / `Result={Fail}`。

**当前：81 通过 / 7 失败，失败清单与本分支分出前的基线同名，本分支新增失败 0。**

那 7 条红项（`WorldFieldsDriveFormalStateTreeAndBobber`、Effort 三条、Runner 两条、
`EquipmentItemPickup`）在分支分出前就是红的。其中 BiteTiming 那条覆盖的正是本轮的演出时序，
它的失败与测试自建水域里没有匹配鱼种有关（夹具问题），**真机验证过可以正常钓到鱼**。

**改代码前请先建基线**：`git stash -u` 回到对比点跑一遍，回来再跑一遍，比差集。
不然分不清「你弄红的」和「本来就红的」——本轮就是靠这个方法确认新增失败为零的。
