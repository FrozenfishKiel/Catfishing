# Catfishing 开发与测试职责隔离协作协议

更新时间：2026-08-20  
文档状态：现行协作协议。  
适用范围：一个或多个 Agent 参与开发、测试编写和验证时的职责分离、工作区隔离、候选版本交接与证据回传。本文不定义产品规则，不替代 `AGENTS.md`、项目 Harness 或 `Docs/Development/自动化测试方案.md`。

## 一句话规则

**测试职责只验证固定的 Commit SHA；开发职责只在开发工作树继续修改。任何两个并发 Agent 都不得操作或运行同一个项目目录。**

Commit 在本文中首先是本地候选快照，不等于合入主分支、推送远端或正式发布。没有通过验证和独立 Review 的候选 Commit 不得进入最终提交。

## 1. 职责与工作区

本文只有两类职责，不限制 Agent 数量：

- **开发职责**：修改生产实现、测试、配置和资产，整合并生成候选 Commit。
- **测试职责**：编写独立测试，或对固定候选执行构建、自动化、冒烟和只读 Review。

下文使用“开发 Agent”和“测试 Agent”表示当前承担对应职责的执行者，不表示项目只能安排两个 Agent。同一 Agent 在一个候选周期内只能承担一种职责；需要换职责时必须先结束当前工作、交接状态并切换到另一独立工作树。

| 职责 | 工作目录约定 | Git 状态 | 主要职责 |
| --- | --- | --- | --- |
| 开发职责 | 集成工作树使用 `D:\UnreaProjects\Catfishing`；其他并发开发 Agent 使用 `D:\UnreaProjects\Catfishing-dev-<编号>` | `codex/dev-*` 开发分支 | 修改任务范围内文件；把各开发分支整合成候选 Commit |
| 测试职责 | 每个并发测试 Agent 使用独立的 `D:\UnreaProjects\Catfishing-verify-<编号>` | 正式验证时使用 detached HEAD，固定在候选 SHA | 按验证维度检查同一个候选，并输出带 SHA 的证据 |

多个工作树可以共享 Git 对象库，但必须分别持有项目级 `Binaries/`、`Intermediate/`、`Saved/`、日志和自动化产物。任一开发工作树重新编译或链接 DLL 时，不得覆盖验证工作树正在测试的产物。

并发分配规则：

- 多个开发 Agent 可以按互不重叠的文件或系统并行工作；承担集成职责的开发 Agent 负责处理冲突并生成唯一候选 SHA。
- 多个测试 Agent 可以针对同一个候选 SHA 分别执行构建、Unit/Boundary/Slice/Functional、双进程冒烟、注释审查或代码 Review。
- 不同测试 Agent 的结果必须各自记录 `tested_sha`；证据汇总者只合并 SHA 完全一致的结果。
- 两个 Agent 需要写同一个文件时不得并行落盘，应重新分片或由一个 Agent 负责写入、另一个 Agent 只读审查。

每个测试 Agent 开工前必须打印并记录：

```powershell
git rev-parse HEAD
git status --short
```

如果实际 SHA 与交接 SHA 不一致，或者验证工作树不是干净状态，测试必须停止并报告，不得自行猜测应该测哪个版本。

## 2. 首次建立职责工作树

承担集成职责的开发 Agent 先在开发工作树生成一个自洽的本地候选 Commit，并记录 SHA：

```powershell
git add <本候选版本明确包含的文件>
git commit -m "wip: verification candidate 001"
git rev-parse HEAD
```

不得顺手暂存或提交不属于候选范围的用户改动。候选必须包含构建和运行所需的全部新增源码、配置、脚本与资产；遗漏未跟踪文件会让测试对象与开发者实际看到的工程不一致。

为第一个测试 Agent 创建验证工作树：

```powershell
git worktree add --detach D:\UnreaProjects\Catfishing-verify-01 <候选SHA>
```

其他并发测试 Agent 使用 `Catfishing-verify-02`、`Catfishing-verify-03` 等独立目录，不得共用 `verify-01`。验证工作树已存在时不得重复创建。切换到新候选前先确认对应工作树干净：

```powershell
git -C D:\UnreaProjects\Catfishing-verify-01 status --short
git -C D:\UnreaProjects\Catfishing-verify-01 switch --detach <新候选SHA>
```

验证工作树存在未提交改动时禁止使用 `reset --hard`、强制切换或删除文件。应先确认这些改动的所有者和用途。

## 3. 标准交接循环

### 3.1 开发职责生成候选

各开发 Agent 完成各自的最小、可独立审查改动后，由承担集成职责的开发 Agent：

1. 检查完整 diff 和未跟踪文件。
2. 确认候选没有混入无关用户改动。
3. 运行最低成本的本地构建或聚焦检查，排除明显不可测状态。
4. 创建本地候选 Commit。
5. 向承担测试职责的 Agent 发送同一份候选交接包。
6. 按风险把构建、自动化、冒烟、注释审查和代码 Review 分配给一个或多个测试 Agent。
7. 交接后开发 Agent 可以继续编辑下一版，但不得改动任何验证工作树。

### 3.2 测试职责冻结并验证

每个测试 Agent 收到候选和自己的验证维度后：

1. 将验证工作树切换到交接 SHA。
2. 记录实际 SHA 和干净状态。
3. 根据改动风险先运行聚焦测试。
4. 最终候选按项目统一入口运行完整验证：

```powershell
powershell -ExecutionPolicy Bypass -File Tools\ci_check.ps1
```

统一验证顺序为：

```text
build -> catalog -> statetree -> automation -> smoke
```

5. 只报告该 SHA 和本 Agent 负责的验证维度，不得把旧 SHA 的绿灯继承给新 SHA。
6. 输出测试结果交接包，并保留日志和报告路径。
7. 证据汇总者确认所有结果使用同一 SHA，再形成候选级结论。

### 3.3 失败回路

测试失败时：

1. 测试 Agent 保留失败候选的 SHA、命令、退出码和日志。
2. 将最后一个已成立状态、第一个失败状态和最小复现步骤交给开发集成 Agent。
3. 开发 Agent 只在开发工作树修复，不得直接修改验证工作树。
4. 修复后创建新的候选 Commit 和新的 SHA。
5. 测试 Agent 对新 SHA 重新运行受影响测试；最终候选仍需运行完整验证。

禁止在原候选上偷偷改一两行后继续沿用原测试结果。只要源码、测试、配置或资产发生变化，被测版本就已经改变。

### 3.4 通过回路

验证通过只表示交接包声明的检查在该 SHA 上通过，不表示“项目绝对没有缺陷”。候选进入最终提交前还必须满足：

- 当前任务要求的构建、Automation、多人或人工验证均有新鲜证据；
- 独立代码 Review 没有未关闭 finding；
- `comment-review` 通过；
- 已确认未遗漏未跟踪源码、配置和资产；
- 用户明确同意最终提交、合并或推送。

## 4. 测试职责需要编写测试时

测试职责中的“写测试”和“正式验证”是两个不同阶段，不能混在同一个未冻结工作区里。同一候选可以由不同测试 Agent 分别承担测试编写和只读验证，但两者仍需使用各自工作树。

需要新增回归测试时：

1. 从候选 SHA 创建测试分支：

```powershell
git -C D:\UnreaProjects\Catfishing-verify-01 switch -c codex/test-<主题> <候选SHA>
```

2. 测试 Agent 只修改与问题直接相关的测试和必要测试支持，不顺手修改生产实现。
3. 测试 Agent 提交测试 Commit，并把测试 SHA、失败基线和预期行为交给开发集成 Agent。
4. 开发集成 Agent 将测试改动纳入开发分支，再完成实现修复。
5. 开发集成 Agent 生成包含“生产实现 + 测试”的新候选 SHA。
6. 测试 Agent 将验证工作树切回该候选的 detached HEAD，进入只读验证模式。

测试分支上的通过结果不能证明开发分支已经通过；只有测试代码和生产实现同时存在于同一个候选 SHA 时，结果才有效。

## 5. UE 专用隔离规则

### 5.1 项目与构建产物

- 每个并发 Agent 必须从自己的工作树内启动 `.uproject`，不得让多个 Agent 共用同一个 Editor 进程。
- 测试 Agent 不得复用任何开发工作树的 `Binaries/`、`Intermediate/` 或 `Saved/`。
- 测试期间禁用 Live Coding 和 Hot Reload，保证运行代码对应磁盘上的候选 SHA。
- UE Engine 安装和 Derived Data Cache 可以共享；项目构建输出和测试报告不能共享。

### 5.2 重型任务租约

Worktree 能隔离文件，不能隔离同一台机器的 CPU、内存、GPU、端口和在线账号。

任一测试 Agent 开始重型验证时发送：

```text
VERIFY_START <候选SHA>
```

收到该信号后，本机上的开发 Agent 可以继续阅读和编辑，但暂停以下动作：

- 启动 Unreal Editor；
- 运行 UBT 构建；
- 运行 Automation、Commandlet 或多人冒烟；
- 占用相同端口、Session 名或在线账号。

该测试 Agent 结束后发送：

```text
VERIFY_END <候选SHA> <PASS|FAIL|BLOCKED>
```

如果必须并行执行重型任务，应迁移到独立机器或 CI Runner，而不是在同一台机器上竞争资源。

### 5.3 多进程与日志

- 双进程冒烟只由明确获分配的测试 Agent 执行，同一台机器同一时间只能运行一组。
- 服务器端口、Session 名、日志路径和进程清理必须由测试脚本统一管理。
- 测试结论必须引用验证工作树的 `Saved/CI/**` 或对应日志，不得引用开发工作树日志。
- Smart App Control 报 `GetLastError=4551` 时按 `.harness/CODING_LESSONS.md` 判断环境阻塞，不得把模块未加载冒充代码测试失败或通过。

## 6. 开发职责的权限与禁止事项

开发 Agent 可以：

- 在开发工作树修改当前任务范围内的源码、测试、配置和资产；
- 创建本地候选 Commit；
- 在测试 Agent 验证旧候选时继续编辑下一版；
- 根据带 SHA 的 finding 修复并生成新候选。

开发 Agent 禁止：

- 修改任何 `D:\UnreaProjects\Catfishing-verify-*` 验证工作树；
- 要求测试 Agent 验证开发工作树中的未提交内容；
- 用新 SHA 的局部检查继承旧 SHA 的全量绿灯；
- 在 `VERIFY_START` 到 `VERIFY_END` 期间争用本机重型 UE 资源；
- 未经用户确认将候选 Commit 合入主分支、推送或发布。

## 7. 测试职责的权限与禁止事项

测试 Agent 可以：

- 读取指定候选的源码、配置、测试和日志；
- 在验证工作树运行项目正式验证入口；
- 为复现缺陷建立独立测试分支并提交测试 Commit；
- 输出带证据的 `PASS`、`FAIL` 或 `BLOCKED`。

测试 Agent 禁止：

- 在 detached 验证模式修改生产源码；
- 自动跟随开发分支最新状态；
- 测试一个 SHA，却引用另一个 SHA 的构建或日志；
- 为制造绿灯修改验收、降低测试数量下限或隐藏失败；
- 把“测试文件存在”“构建通过”或“局部测试通过”写成完整验证通过。

## 8. 开发候选交接模板

承担集成职责的开发 Agent 每次向全部测试 Agent 发送：

```text
candidate_id: CANDIDATE-001
candidate_sha: <完整Commit SHA>
source_worktree: D:\UnreaProjects\Catfishing
goal: <本候选要实现或修复什么>
changed_surface:
  - <文件或系统范围>
expected_observable_result:
  - <用户或测试能够观察到什么>
required_verification:
  - <聚焦测试>
  - Tools\ci_check.ps1
known_risks:
  - <生命周期、网络、资产或环境风险>
known_failures:
  - <当前仍存在的失败；没有则写 none>
unverified:
  - <尚未验证的范围>
```

缺少 `candidate_sha` 的交接无效，任何测试 Agent 都不得开工。

## 9. 测试结果交接模板

每个测试 Agent 向开发集成 Agent、证据汇总者和用户发送：

```text
candidate_id: CANDIDATE-001
tested_sha: <完整Commit SHA>
worktree: <本测试Agent独占的验证工作树绝对路径>
verification_dimension: <build|catalog|statetree|automation|smoke|comment_review|code_review>
result: PASS | FAIL | BLOCKED
workspace_clean: true | false
commands:
  - command: <真实命令>
    exit_code: <退出码>
    evidence: <日志或报告路径>
acceptance_results:
  - item: <可观察结果>
    status: pass | fail | blocked
    evidence: <证据>
findings:
  - <问题、最小复现和关键文件位置>
environment_gaps:
  - <SAC、账号、端口、资产或工具缺口>
unverified:
  - <本轮没有覆盖的范围>
```

只有 `tested_sha` 与开发交接的 `candidate_sha` 完全一致，结果才属于该候选。候选级 `PASS` 还要求所有必需验证维度都已返回，并且没有任一 Agent 报告 `FAIL` 或未解决的 `BLOCKED`。

## 10. 冲突处理

遇到以下情况立即停止当前动作并交回用户或协调者：

- 任意两个并发 Agent 发现自己正在操作同一个物理目录；
- 验证工作树存在来源不明的修改；
- 候选 Commit 遗漏运行必需的未跟踪文件；
- 测试结果对应的 SHA 与候选 SHA 不一致；
- 需要删除、移动或覆盖用户已有改动；
- 需要变更产品规则、持久化、权限、安全或外部接口；
- 同一测试在固定 SHA 和固定环境下仍出现无法解释的漂移。

不要通过强制切换、清空目录、降低验收或让承担正式验证职责的 Agent 直接修生产代码来绕过冲突。
