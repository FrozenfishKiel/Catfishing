## 这次写了什么

左上角那块现在不是完整主菜单，也不是背包。它是 Lake 场景 HUD，用来告诉玩家当前猫状态、钓鱼反馈，并提示按 `Tab` 打开个人背包。

项目里的“背包”是局内物品总览：它要同时展示鱼护里的鱼、当前手上的鱼竿槽、随身鱼饵/窝料等耗材，以及商店买到但还没装到自己身上的待取装备。普通 `Tab` 打开只显示玩家自己的背包，玩家可以在个人容器内拖拽整理格子；与世界容器交互时，交互对象把自己的容器复制源传进同一个背包，玩家通过同一套格子拖拽完成跨容器移动。商店是世界摊位交互对象打开的页面，不和个人背包塞在同一个菜单里。

## 功能怎么用

1. 打开项目后，默认进入 `Frontend`。
2. 点击运行，先走 Frontend 的在线入口。
3. 单人本地验收时点 `Host Session`，游戏会旅行到 `/Game/Catfishing/Maps/Lake?listen`。
4. 进入 Lake 后，左上角 `猫钓鱼湖` 面板是 HUD。
5. HUD 里的状态应该显示为 `中毒值`、`钓鱼力量`、`搏斗体力`，不应再是裸的 `0 / 50 / 100`。
6. 在 Lake 中按 `Tab`，打开个人背包；再按 `Tab` 或点 `关闭` 收起。
7. 背包需要能看到鱼护格子、当前鱼竿槽、随身耗材和待取装备。没有鱼时鱼护仍应显示空格；有鱼时可以点非空格子查看详情。
8. 选中个人鱼护里的鱼后，`吃鱼` 和 `献祭` 只发 UI 意图，真实结果由服务器事务返回后刷新。
9. 与共享鱼缸交互后应打开同一个背包，并额外显示鱼缸提供的外部容器；把鱼从一个容器格拖到另一个容器格会提交同容器整理或跨容器移动。
10. 与商店摊位交互后才打开商店页面，商店页面显示队伍资金和按钮：`买二级竿`、`买窝料`、`领鱼饵`、`领保底竿`。

## 按键绑定在哪里

`Tab` 不是 WBP 蓝图按钮图标里的硬编码，也不再由 C++ 临时 `NewObject<UInputAction>` / `MapKey` 写死。当前绑定在正式 Enhanced Input 资产里：

- 输入动作：`/Game/Input/InputAction/IA_LakeMenu`
- 输入映射：`/Game/Input/InputContext/IMC_InputContext`
- 默认显示键名：C++ 从 `IMC_InputContext` 里找到 `IA_LakeMenu` 的映射后解析出来。

所以人工验收时，要看“背包键为什么是 Tab”，应检查 `IA_LakeMenu` 是否在 `IMC_InputContext` 里绑定到 Tab；要看“按钮点了做什么”，才检查对应拆分 WBP 的按钮绑定和 `Request...` 函数。

## 给蓝图/前端开发的对接口径

WBP 只负责展示和发意图：

- HUD 只读展示猫状态和钓鱼反馈。
- Inventory 只调用：`RequestCloseInventory`、`RequestSelectSlot`、`RequestConsumeSelectedFish`、`RequestSacrificeSelectedFish`；鱼的跨容器移动来自 `WBP_CatInventorySlot` 的拖拽和 Drop，不再有单独入鱼缸按钮入口。
- 每个 `SlotView` 都必须保留容器 ID、容器类型、容器内 index 和对象 ID；Drop 请求提交源容器/index 与目标容器/index，不能只提交对象 ID 或 UI 数组下标。
- Shop 只调用：`RequestPurchaseEntry(FName EntryId)`、`RequestFreeClaimEntry(FName EntryId)` 等商店页面意图，按钮预设项也从这两个入口转发。
- 世界交互对象只提供打开上下文：`ACatShopKioskActor` 打开 Shop，`UCatFishTankInteractionComponent::Interact_Implementation` 把鱼缸容器复制组件传给 Inventory。
- 蓝图不能直接删鱼、改容器、写献祭额度、改队伍资金或绕过 PageController/PlayerController。

后端负责真正改状态：

- 鱼护吃鱼走 Items 消费事务。
- 格子拖拽从 `UCatInventorySlotWidget::NativeOnDrop` 进入，`UCatInventoryPageController::HandleViewSlotDropRequested` 提交源/目标容器与槽位；PlayerController 的 `ServerTransferObjectBetweenContainers` 在服务端重读容器、源槽位对象和 Revision，Items 的 `TransferContainedObject` 再按 `FCatContainerSnapshot::Fish` 槽位数组裁决。空槽以无效 `FishInstanceId` 占位；同容器按槽位交换/移动，跨容器按目标槽位移动；复制项携带 `SlotIndex`，客户端按后端槽位还原，不依赖 FastArray 条目顺序。
- 献祭走 Sacrifice/Run 事务。
- 商店购买和免费领取走 Shop 服务端事务。
- 离局走 Online 子系统。

## 人工验收步骤

### A. 默认入口

操作：打开 `Catfishing.uproject`，不手动切图，直接运行。

期望：进入 `Frontend`，能看到可点击的进局入口，不应只看到黑屏或不明状态板。

### B. Frontend 进 Lake

操作：点击 `Host Session`。

期望：进入 `Lake`，日志出现类似 `ProcessServerTravel: /Game/Catfishing/Maps/Lake?listen`，Lake 内不再显示 Host/Find/Join 那套前端按钮。

### C. HUD 可读性

操作：进入 Lake 后观察左上角 HUD。

期望：标题为中文 `猫钓鱼湖`，状态有清楚标签，能看出 `Tab` 用来打开个人背包。

失败判定：仍显示 `CATFISHING LAKE / Current Cat / 0 / 50 / 100` 这种旧英文裸数字，失败。

### D. 个人背包

操作：在 Lake 连续做两组打开/关闭检查：第一组按 `Tab` 打开背包，再按 `Tab` 关闭；随后再次按 `Tab` 打开第二轮背包，并再次按 `Tab` 关闭。第二组按 `Tab` 打开背包，点击 `关闭` 按钮关闭；随后再次按 `Tab` 打开第二轮背包，并再次点击 `关闭` 按钮关闭。

期望：每一轮背包都能展开；第二轮打开后，`Tab` 和 `关闭` 按钮仍能正常收起背包。背包展开时能看到鱼护格子、当前鱼竿槽、当前装备摘要、随身耗材、待取装备、选中项、吃鱼/献祭动作按钮和结果反馈。

失败判定：按 `Tab` 没反应；第二轮打开后 `Tab` 或 `关闭` 按钮无法收起背包；没有当前鱼竿槽；没有鱼护区域；没有鱼时没有空状态提示。

### E. 商店交互

操作：靠近商店摊位，按交互键打开商店页面。

期望：显示队伍资金和商店按钮：买二级竿、买窝料、领鱼饵、领保底竿。按钮点击后不应在蓝图里直接改钱或物品，而应由后端结果刷新。

失败判定：找不到商店区；按钮可点但没有任何意图或后端日志；UI 自己改状态。

### F. 鱼动作与格子拖拽

前置：鱼护里至少有一条鱼；非 Shipping 构建可在控制台执行 `cat.Fishing.Debug.GiveFish` 给本地玩家一条可运行的正式鱼，也可执行 `cat.Fishing.Debug.GiveFish Fish_Pike 1 0 1.5` 指定资产名、数量、玩家索引和重量。跨容器验收时需要靠近共享鱼缸。

操作：按 `Tab` 打开个人背包，先把鱼从当前鱼护格拖到另一个鱼护空格，确认空槽移动；再把另一条鱼拖到已有鱼格，确认两格按槽位交换。记录拖动前后的源格、目标格和容器名称。选中个人鱼护内的鱼后分别点击 `吃鱼`、`献祭`。靠近共享鱼缸按交互键打开带外部容器的同一个背包，把鱼从个人鱼护拖到鱼缸空格，再把鱼缸内本人拥有的鱼拖回个人鱼护；双客户端时由另一客户端观察共享鱼缸视图是否同步。每次 Drop 后等待服务器结果和两个容器视图刷新，再检查两端槽位内容。

期望：同容器空槽移动后源槽变为空槽、目标槽出现原鱼；同容器有物拖拽后源/目标槽内容交换。跨容器移动后源容器槽位变为空槽、目标容器对应槽位出现原鱼，服务器复制刷新后两端仍保持一致，双客户端观察到的共享鱼缸内容也一致，且不会因网络复制条目顺序变化打乱槽位；吃鱼/献祭按钮只在选中个人鱼护内鱼且可提交时启用；每次操作都有等待或结果反馈，失败时前端不能伪造成功。

失败判定：按钮可点但没有反馈；UI 显示成功但后端状态没变；蓝图绕过服务器命令。

程序员阅读顺序：先读 `Source/Catfishing/UI/Inventory/CatInventoryTypes.h` 的 `FCatInventorySlotView`，确认每个 UI 格子的容器与槽位身份；再读 `Source/Catfishing/UI/InventorySlot/CatInventorySlotWidget.cpp` 的 `NativeOnDrop` 和 `Source/Catfishing/UI/Inventory/CatInventoryPageController.cpp` 的 `HandleViewSlotDropRequested`，确认请求参数；最后读 `Source/Catfishing/Framework/Game/CatGameplayTypes.cpp` 的 `ServerTransferObjectBetweenContainers_Implementation`、`Source/Catfishing/Items/CatItemsService.cpp` 的 `TransferContainedObject`、`Source/Catfishing/Items/CatItemTypes.h` 的 `FCatContainerSnapshot` 和 `Source/Catfishing/Items/CatContainerReplicationComponent.cpp` 的 `RebuildSnapshotFromReplication`，确认服务端槽位数组交换与客户端按 `SlotIndex` 还原。

关联代码位置：给鱼指令看 `Source/Catfishing/Fishing/Debug/CatFishingDebugSubsystem.cpp` 的 `cat.Fishing.Debug.GiveFish`；鱼缸打开背包看 `Source/Catfishing/Items/CatFishTankInteractionComponent.cpp` 的 `Interact_Implementation`；SlotView 字段和 Drop 事件看 `Source/Catfishing/UI/Inventory/CatInventoryTypes.h`、`Source/Catfishing/UI/InventorySlot/CatInventorySlotWidget.cpp` 的 `NativeOnDrop`；跨容器提交看 `Source/Catfishing/UI/Inventory/CatInventoryPageController.cpp` 的 `HandleViewSlotDropRequested`、`Source/Catfishing/Framework/Game/CatGameplayTypes.cpp` 的 `ServerTransferObjectBetweenContainers_Implementation`、`Source/Catfishing/Items/CatItemsService.cpp` 的 `TransferContainedObject`，槽位数组定义看 `Source/Catfishing/Items/CatItemTypes.h` 的 `FCatContainerSnapshot`，复制还原看 `Source/Catfishing/Items/CatContainerReplicationComponent.cpp` 的 `RebuildSnapshotFromReplication`。

### G. 离局边界

操作：按当前 Online/离局入口执行离局；个人背包不承载离局按钮。

期望：进入正式离局流程，回到 Frontend 或进入明确收口状态；背包打开或关闭都不应影响离局入口的正式裁决。

失败判定：黑屏、卡死、留在 Lake 没反馈，或用旁路 `OpenLevel` 代替正式离局。
