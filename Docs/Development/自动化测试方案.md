# 自动化测试方案

- 文档状态：现行有效（2026-08-20 重建，替代已删除的旧版）
- 事实来源：`Source/Catfishing/**/Tests/*.cpp`（59 个测试文件）、`Tools/ci_check.ps1`、`Tools/run_multiplayer_smoke.ps1`、`.github/workflows/ci.yml`、`.harness/CODING_LESSONS.md`
- 适用范围：本仓库全部自动化验证。Cook/打包验证明确不在本方案内（用户拍定排除）。

## 一句话总则

**所有验证从同一个入口跑：`Tools/ci_check.ps1`。本地改完代码跑它，CI 也跑它，两边口径一字不差。**

```powershell
powershell -ExecutionPolicy Bypass -File Tools\ci_check.ps1                     # 全部阶段
powershell -ExecutionPolicy Bypass -File Tools\ci_check.ps1 -Stage automation   # 只跑某一阶段
```

阶段与顺序：`build → catalog → statetree → automation → smoke`。退出码 0 = 全通过，非 0 = 第一个失败阶段的序号。

## 测试分层

自动化测试按验证目标分四层，加一个跨进程冒烟。**新写测试前先判断它属于哪一层，按层的约束写，不要混层。**

### 第 1 层：Unit（单元）

- 验证对象：单个类型的纯逻辑——配置校验、DTO 不变式、算法、分派表、状态机单步。
- 环境约束：不建 World，或只建不 BeginPlay 的裸 World；不 Tick；不依赖其它系统的实例。
- 配置获取：需要 `GetDefault<T>()` 配置时使用 **CDO 覆盖守卫**（构造保存原值、析构还原），守卫结构写在测试文件内部，不跨文件共享（项目惯例，防止测试间隐性耦合）。
- 绝大多数 `*Tests.cpp` 属于这一层。

### 第 2 层：Boundary（边界契约）

- 验证对象：两个系统之间的接口契约——调用方传什么、被调方保证什么、错误形态长什么样。
- 代表：`Integration/Fishing/Tests/CatFishingBoundaryContractTests.cpp`。
- 约束：只验证契约本身，不重复验证双方内部逻辑（那是各自第 1 层的事）。

### 第 3 层：Slice（纵切片）

- 验证对象：一条业务链在单 World 里的多系统协作，例如"抄鱼提交 → 印记记录 → 容器入库"。
- 代表：`CatFishingCaptureSliceTests.cpp`、`CatItemsCollectionSliceTests.cpp`。
- 环境约束：可以建 Game World 并 BeginPlay，可以手工驱动少量步骤，但**不做长时间真实 Tick**、不覆盖完整局流程——那是第 4 层的事。

### 第 4 层：Functional（功能全链路）

- 验证对象：一整局的核心循环在**真实 Tick 的 World**里从头跑到尾。
- 代表（目前唯一）：`Framework/Game/Tests/CatCoreLoopFunctionalTests.cpp` —
  `Catfishing.Functional.CoreLoop.RealTickedWorldRunsDayCatchCampSacrificeAndSettlement`。
  覆盖：真实 PreLogin/PostLogin 准入 → 领饵/购窝料/投窝 → 两次完整钓鱼战斗与抄鱼 → Grant ACK 闭环 → 营地转缸/休息 → 90 秒白天计时器自然入夜 → 献祭达标 → ready → 成功结算夜 → 结算完成归档。
- 关键手法（新增功能测试照抄这些，不要另起炉灶）：
  - `FTestWorldWrapper` + `TickTestWorld`：计时器、StateTree 组件、衰减全走真实路径；
  - 先 `SetGameMode(?game=...)` 再 `BeginPlayInTestWorld()`（Wrapper 内部的 SetGameMode 对已有 GameMode 是空操作）；
  - 缩短局参数用 CDO 覆盖守卫（如 DayLengthSeconds=90、QuotaTarget=1），析构还原；
  - 鱼表替换成单条固定弱鱼，含完整 SourceStamp 让 StartPlay 目录校验通过；
  - 用 `TickUntil(最大模拟秒数, 条件)` 等事件，**不用固定 sleep**。
- 数量约束：功能测试很贵（单条约 2~3 分钟），只为"核心循环"级别的链路写，一条链路一条测试。

### 冒烟层：双进程真实联机（不属于 automation，单独阶段）

- 脚本：`Tools/run_multiplayer_smoke.ps1`；验证复制层——快照网络序列化、真实 PreLogin 准入、客户端 Pawn 生成与占有、客户端 UI 装配。
- 判据是双方日志里的结构化事件（`Event=xxx`），必需标记与禁止标记见脚本头注释。
- 已知边界：走 NULL 在线子系统（`-nosteam`），Steam 真实会话/邀请仍需人工验收；客户端进程没有可脚本化输入，不从客户端驱动玩法命令。
- 2026-08-20 价值证明：第一次跑就抓到"联机局里非房主玩家 HUD 永不装配"的真缺陷（单进程测试在结构上不可能发现它）。

## 分层选择规则（写测试前自查）

1. 能在第 1 层证明的，不上第 2 层；能在单 World 证明的，不开双进程。
2. 涉及"两个系统的约定"→ 第 2 层；涉及"一条链多系统协作"→ 第 3 层；涉及"计时器/相位/整局节奏"→ 第 4 层；涉及"复制/准入/多进程"→ 冒烟。
3. 修 Bug 时防复发测试落在**能复现该 Bug 的最低层**。
4. 测试直写私有状态只允许沿用既有反射手法（如 `FindFProperty` 挂共享鱼缸），且必须是"生产路径无法在测试环境构造"时的最后手段。

## 条数下限约定（防测试悄悄消失）

`ci_check.ps1 -MinimumTestCount`（当前 200）是全量 automation 的条数下限。测试文件编译失败不会进入运行集、不会报 failed——条数下限是唯一能兜住"整文件消失"的检查。

- 新增测试后**上调**下限到接近当前实际条数；
- **下调必须在提交说明里写明**哪些测试为什么消失。

## 环境已知风险

- Smart App Control 强制模式下，新链接出的 DLL 可能被按哈希拒绝加载（日志特征 `GetLastError=4551`）。这是环境问题不是代码失败，`ci_check.ps1` 会明确标注；处置见 `.harness/CODING_LESSONS.md`。
- 无窗口自动化统一带 `-nullrhi -unattended -DDC-ForceMemoryCache`；冒烟额外带 `-ForceLogFlush`（否则进程被杀时丢日志尾巴）。

## CI

`.github/workflows/ci.yml`：自托管 Runner（windows + ue5 标签）调用 `ci_check.ps1`，工件上传 `Saved/CI/**`。CI 没有任何本地跑不了的私有步骤。

## 明确不覆盖的范围

- Cook/打包（用户拍定排除）；
- Steam 真实会话、邀请、双账号（人工验收）;
- 渲染/画面表现（全部测试跑在 NullRHI 上）。
