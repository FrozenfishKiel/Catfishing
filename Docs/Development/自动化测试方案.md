## 1. 这套测试要解决什么问题

当前框架会交给后续程序员或其他 Agent 继续补充实际玩法、资产、数值和表现。因此测试的目标不只是发现某一行代码有没有写错，还要持续证明以下事情：

- 后续功能仍然通过当前正式入口进入系统，没有绕开权威校验、事务、生命周期和唯一真相宿主。
- 模块公开接口足以承载真实需求，而不是只能编译、不能组合、无法验证。
- 重复请求、迟到回调、过期 Revision、错误所有者、缺少配置和生命周期结束不会污染长期状态。
- 一个系统内部重构后，只要公开行为不变，对应测试就不应因为私有实现变化而失效。
- 单个模块正确之后，Fishing、Items、Collection、Profile、Run、Online 等模块仍能组成完整纵向链路。
- 自动化能够证明的范围与必须交给真实 Steam、多客户端、PIE、资产和人工体验验证的范围保持清楚。

这里的核心判断是：**测试面对的应当是模块的正式接口和可观察结果，而不是私有辅助方法、字段形状或调用次数。** 如果一个关键行为只能靠读取私有字段或增加测试后门才能验证，先把它记录为模块接口或可观察性问题，再决定是否调整正式设计。

## 2. 测试方案的强制写作合同

以后新增的每一个测试项，都必须写清以下字段。缺少其中任何一项，不能视为完整测试方案，也不能仅以“已经写了测试文件”作为交付结论。

| 字段 | 必须回答的问题 |
|---|---|
| 测试目标 | 究竟要证明哪一条需求、架构约束、失败边界或生命周期合同？ |
| 测试对象 | 哪个模块、正式类型和公开入口承担该行为？ |
| 测试层级 | 它属于合同测试、生命周期测试、跨模块切片，还是环境验收？ |
| 前置条件 | 需要什么 World、Authority、Controller、配置、资产、OSS 或初始状态？ |
| 驱动方式 | 测试通过哪个正式入口发出什么命令；按什么顺序操作？ |
| 可观察结果 | 从公开 Result、Snapshot、复制状态、Delegate、World 状态或正式日志观察什么？ |
| 通过标准 | 哪些精确断言必须同时成立，才能判定通过？ |
| 负面与副作用 | 哪些状态必须保持不变，哪些重复写入、残留引用或多余副作用必须为零？ |
| 证据 | 使用什么命令运行，退出码、Automation 结果、报告和日志保存在哪里？ |
| 不能证明什么 | 本测试没有覆盖哪些平台、网络、资产、交互或人工体验风险？ |

测试名称也必须描述行为，而不是实现。例如：

```text
Catfishing.Unit.Items.CommitCapture.ReplayDoesNotDuplicateFish
Catfishing.Lifecycle.Character.UnPossessClearsAbilityActorInfo
Catfishing.Slice.Fishing.FirstLegalNearShoreScooperOwnsFish
```

禁止使用 `TestHelper1`、`CallsInternalFunction`、`SetsMemberValue` 这类无法说明产品或架构能力的名称。

## 3. 测试代码的目录与编译规则

测试文件跟随其测试对象所属的系统放置。目录归类继续遵守项目规则：按类型本身隶属的系统分类，不按它服务谁或挂在哪个 Actor 上分类。

```text
Source/Catfishing/Fishing/
├─ CatFishingService.cpp
├─ CatFishingService.h
├─ CatFishingSession.cpp
├─ CatFishingSession.h
└─ Tests/
   ├─ CatFishingServiceTests.cpp
   └─ CatFishingSessionTests.cpp
```

具体规则如下：

- 不建立一套与业务目录平行的全局 `CatfishingTests` 镜像树。
- 不要求每一个生产 `.h/.cpp` 机械对应一个测试文件；只有具备独立行为、状态、事务、权限、配置判断或生命周期责任的类型才单独建测试文件。
- 纯枚举、DTO、反射类型声明、日志分类、模块入口和 Build 配置通常由使用它们的模块测试或构建测试覆盖。
- 具有 `IsRuntimeReady()`、`TryGet...()`、合法性判断或产品 gate 的 Settings/Definition 类型需要合同测试。
- 模块内重复的 fixture 先留在本系统 `Tests/` 中；只有至少两个系统出现相同且稳定的测试基础设施需求，才考虑建立 `Source/Catfishing/Tests/Support/`。
- C++ 测试使用 UE Automation Framework，并由 `WITH_DEV_AUTOMATION_TESTS` 隔离；不得让测试逻辑进入 Shipping 行为。
- Runtime 模块不得为了测试依赖 `UnrealEd`、`LevelEditor` 等 Editor-only 模块。
- 不向生产类型增加测试专用 public setter、状态注入方法、测试模式分支或绕过权限的控制台命令。
- 随机数、时间、OSS、文件系统等真正的系统接缝只有在出现第二种真实 adapter 或当前行为无法稳定验证时才建立；不能为了方便 mock 预先制造一层通用包装。

## 4. 四层验证体系

### 4.1 L1 合同测试

合同测试覆盖不依赖真实地图、Steam 或多进程的领域行为。它主要验证配置 gate、输入校验、RequestId 幂等、Revision、容量、所有权、状态转移和事务结果。

运行时使用尽量小的真实 UObject、Actor、Component 和 Subsystem，不 mock 项目内部模块。测试从正式 public 接口提交命令，从 Result、Snapshot 或正式查询入口断言结果。

L1 通过只能证明该模块在受控进程中的领域合同成立，不能证明网络复制、资产装配或真实平台回调成立。

### 4.2 L2 生命周期测试

生命周期测试使用最小测试 World 和真实 UE 生命周期，覆盖 Authority、BeginPlay/EndPlay、Possess/UnPossess、ASC 初始化和清理、组件注册、Delegate 绑定解绑、Widget/Pawn 重建等行为。

这类测试的关键不是“函数被调用过”，而是生命周期前后的公开事实。例如 UnPossess 后 Ability ActorInfo 不再指向旧 Pawn，EndPlay 后 Items 中不再能查询到已销毁容器，Controller 更换后只存在一个有效 View。

L2 通过不能替代真实多客户端复制和可见 PIE，但能够提前抓住大量旧 World、旧 Controller、重复委托和 teardown 污染。

### 4.3 L3 跨模块纵向切片

纵向切片使用真实模块组合验证一条完整业务链，避免所有模块各自通过却无法协作。第一批固定切片如下：

```text
Fishing → Items → Collection → Profile
Run → Sacrifice → Items → Settlement
Camp / Social → Items / Condition / Collection
Online → Run Teardown → Session Destroy → Frontend
Character → AbilitySystem → Condition → UI ViewState
```

切片测试只从最外层正式入口驱动，内部模块使用真实实现。只有 Steam、文件系统、时间或平台等系统接缝允许使用专用 adapter 或安全副本。

L3 通过证明模块能够按当前架构组成实际链路，但如果使用 Null OSS、无窗口渲染或临时配置，结论必须明确保留这些边界。

### 4.4 L4 运行环境与人工验收

以下内容不能由单元测试或普通模块测试替代：

- Steam Create/Find/Join/Invite 的真实回调顺序和双账号行为。
- Listen Server 的实际复制、断线、延迟、丢包和迟到 RPC。
- StateTree 资产里的真实拓扑、任务接线和事件转移。
- UMG/Slate 的真实鼠标、键盘、焦点、分辨率和可读性。
- Frontend/Lake 地图资产、PlayerStart、GameMode Override 和场景 Actor 装配。
- Cook、Package、Shipping、性能和长时间运行。

L4 的结果继续进入验收报告；不得因为 L1～L3 全绿就宣称这些项目已经通过。

## 5. 所有领域命令共用的测试矩阵

凡是接受领域命令、RequestId 或 ExpectedRevision 的正式入口，应按实际能力覆盖以下测试。某项确实不适用时，必须在对应测试文件或方案条目中写明原因。

1. 合法请求成功，并产生预期公开结果。
2. 缺少必要配置、资产、身份或运行阶段时 fail-closed。
3. 非权威端、错误所有者、无效 StableNetId 或错误 Controller 被拒绝。
4. 过期 Revision 被拒绝，并且原状态不变。
5. 相同 RequestId 重放返回相同终态，不重复生成鱼、奖励、印记、消耗品或副作用。
6. 不同请求在已有操作 Pending 时得到稳定、明确的拒绝。
7. 事务中途失败后，预约、Pending、委托和临时索引被清理或保留为可恢复记录，不能落入半提交状态。
8. 失败终态后，下一次新的合法 RequestId 可以按合同重新受理。
9. 迟到回调、旧 epoch、旧 Controller 或旧 World 不能覆盖当前状态。
10. teardown 后不残留 Actor、Widget、Delegate、Timer、Mapping Context、预约或旧对象强引用。

每个正向测试至少配一个最有价值的负向测试。不能只证明“能成功”，还必须证明错误输入不会悄悄修改状态。

## 7. 首个 tracer test 与实施顺序

第一条测试固定为：

```text
Catfishing.Unit.Items.CommitCapture.ReplayDoesNotDuplicateFish
```

测试文件为：

```text
Source/Catfishing/Items/Tests/CatItemsServiceTests.cpp
```

它要证明的完整行为是：

```text
创建最小 Authority World
→ 创建并注册真实个人鱼护容器
→ 通过 UCatItemsService::CommitCapture 提交一次合法捕获
→ 从 TryGetContainerSnapshot 观察到一条鱼和一次 Revision 前进
→ 使用完全相同的 RequestId 重放
→ Result 返回原终态，Snapshot 中仍只有同一条鱼，Revision 不再前进
```

这条 tracer test 通过的证据必须同时包括：

- 测试被 UE Automation 正确发现，完整测试名唯一。
- 第一次提交成功，公开 Snapshot 含预期 FishInstanceId。
- 第二次提交没有新增鱼、没有改变 owner、没有再次推进 Revision。
- Automation 个案状态为 Success，进程正常退出，日志没有 Fatal、Ensure 或测试 Error。
- 测试结束后 World 和对象正常清理，没有残留 Timer、Delegate 或后台进程。

实施采用逐条纵向循环：先写这一个测试并看到它因缺少测试装配或真实缺陷而失败，再做最小修正使其通过；随后才增加下一条行为。禁止先批量创建所有 `Tests/` 空壳，再批量补实现。

建议顺序为：

```text
Items
→ Fishing
→ Collection / Profile
→ Run / Framework
→ AbilitySystem / Character / Condition
→ Environment / Equipment
→ Camp / Social
→ Online / UI
→ 跨模块纵向切片
```

## 8. 怎么运行，怎样形成通过证据

第一条 tracer test 落地时，要先用真实 UE 5.8 Automation 发现机制冻结最终命令。预期采用无窗口 Editor 命令行运行，测试名称分层如下：

```text
Catfishing.Unit.*
Catfishing.Lifecycle.*
Catfishing.Slice.*
```

一次测试批次只有同时满足以下条件，才能记为通过：

1. 对应 `CatfishingEditor Win64 Development` 新鲜构建成功，UHT、编译和链接退出码为 0。
2. Automation 实际发现的测试数量等于计划执行数量，不能出现过滤器写错导致的“0 tests”。
3. 每个测试个案状态均为 Success；批次失败数、跳过数和未完成数均为 0，除非方案提前列明允许跳过的外部环境项。
4. `UnrealEditor-Cmd` 测试进程正常退出；不能以强制结束进程冒充完成。
5. 日志中没有 Fatal、Ensure、Automation Error、崩溃或超时。
6. 测试报告、完整日志、执行命令、退出码、开始/结束时间和源码提交哈希保存到本次 `Saved/Automation/<run-id>/` 证据目录。
7. 测试前后检查工作区，证明测试没有修改正式 Config、Content、Source 或用户文件；需要临时配置和故障注入时只能操作安全副本。
8. `.codex/docs/testing-report.md` 按测试 ID 记录实际结果、失败—修复—重跑链、证据路径、覆盖范围和未覆盖范围。

某个批次只有构建通过、测试没有真正被发现，结论是 **未执行**；测试执行失败但其他测试通过，结论仍是 **该批次失败**；只通过 L1/L2 时，不能把 L3/L4 写成通过。

## 9. 完成标准与后续维护

测试体系的阶段性完成口径是：

```text
关键模块 L1 合同测试通过
+ 高风险生命周期 L2 测试通过
+ 固定跨模块 L3 切片通过
+ Editor/Game 构建通过
+ L4 中适用于本次交付的运行环境和人工验收通过
```

后续每次实现真实功能时，应先判断它改变了哪个公开行为，再在所属系统 `Tests/` 中以一条新的红灯测试开始。修复 bug 时，先用正式入口重现 bug，再写最小回归测试；不能只修改实现后补一个永远不会失败的形状测试。

本方案不冻结每个系统最终有多少测试，也不提前冻结尚未出现的 mock、fixture 或 adapter。测试数量由真实行为和风险决定；测试基础设施只有在 tracer test 证明需要后才增加。
