# Catfishing 问题分析 Harness

更新时间：2026-08-14  
文档状态：当前项目强制 Harness 合同。  
范围：约束 Bug、行为异常、性能或兼容性回归、失败测试以及修改既有行为的代码任务。纯新增且不改变既有行为的任务仍需读取本文，但只执行与本题风险相关的部分。

## 目的

错误本身允许发生，但不能只留下“已经修复”或“下次注意”。每次错误都必须暴露当时错误的事实假设、推理断点和证据缺口，并把可复用结论升级为说明、测试、工具或 Hook，使同类错误更难再次发生。

本文不是 Bug 黑名单，也不规定固定代码结构、生命周期接缝或测试矩阵。历史问题只提供分析样本；新问题必须重新读取当前产品规则、项目源码、引擎或平台实现和运行证据。

## 修改前诊断合同

进入实现前，负责 `context`、`architect` 和 `implementation` 的 Agent 必须形成一份可交接的诊断记录。记录可以进入 Context Pack、Harness 状态或节点 handoff，但至少回答：

1. `target_and_non_goals`：本轮要恢复的可观察行为、当前阶段、明确非目标和允许修改的边界。
2. `observed_facts`：已经由源码、日志、测试、界面或人工复现确认的事实。
3. `inferences`：从事实推导但尚未直接证明的判断，不能与事实混写。
4. `unknowns`：权限、环境、资产、平台、账号或运行拓扑造成的信息缺口。
5. `symptom_owners`：同时出现的现象分别由哪个状态所有者和生命周期负责；没有证据时不得假定它们互为因果。
6. `runtime_chain`：从真实入口追到状态所有者、权威写入、消费节点、玩法或事务终态以及 Cleanup；项目 override 依赖 UE 或平台隐含行为时继续追到真实上游实现。
7. `breakpoint_evidence`：链路最后一个已成立状态和第一个未成立状态，以及证明断点的源码或运行证据。
8. `rejected_hypotheses`：已被证据排除的候选原因，以及排除依据。
9. `minimal_change`：只修复已确认断点的最小充分改动，并说明它如何保持现有 SSOT、权威写入者、正常入口和生命周期合同。
10. `verification_dimensions`：从本题风险推导的验证组合，以及每种证据能证明和不能证明的范围。

无法确定真实断点时可以继续调查，但不得进入实现；必须把状态记录为 `blocked` 或保留为调查任务，不能用扩大架构、增加旁路或创建替身来掩盖缺口。

## 分析与方案收敛门禁

- 不得用“联机问题”“UI 问题”“初始化问题”等宽泛标签替代对多个现象的独立归属判断。
- 不得在读取真实入口、状态所有者和生命周期之前提出 Manager、Policy、替代 GameMode、第二套状态或完整重构。
- 不得用隐藏 UI、跳过权限、绕过状态机、测试专用宿主或 Fake 下的成功结果证明正式产品链已经修复。
- 修复必须落在真实链路的已证实断点上；需要新边界时，必须对应当前存在的所有权、生命周期、副作用、平台隔离或验证收益。
- 实现完成前必须做删减审查。删除、内联或合并新增结构后仍满足相同验收与验证的，采用更少结构的方案。
- 历史问题中的接缝和测试维度只能作为候选线索，不能成为新问题的默认修法或固定矩阵。

## 验证与结论门禁

- 修改既有行为必须先取得可复核基线；不能真实复现时，记录缺失条件和降级证据。
- 验证维度从本题风险产生，可包括生命周期入口、权限方、NetMode、进程拓扑、并发顺序、断线重试、持久化、资源加载或真实平台环境。
- 源码静态检查、构建、Automation、单进程 PIE、多进程运行、打包目标和真实平台分别属于不同强度证据，不得相互冒充。
- Review 必须检查改动是否只压制表面症状、是否引入第二条真相或旁路、是否保留真实产品入口、是否存在强于证据的完成声明。
- 交付必须分别列出代码事实、运行证据、工程推断、未验证范围和剩余风险。没有新鲜证据时只能说明代码或合同存在，不能说明行为已经完成。

## 失败防复发门禁

每次真实失败或用户纠正都要在交付前完成一次防复发判断：

1. 一次性问题：说明为什么没有跨任务复用价值。
2. 说明约束：把推理边界写入 Harness、项目规则或稳定知识入口，并给出适用范围。
3. 测试：行为能够自动观察时，新增或强化覆盖真实失败模式的回归测试。
4. 工具或 Hook：同类错误重复出现，或文字约束仍容易被绕过时，升级为机械检查。

防复发不能只复述具体 Bug。记录必须说明原始错误假设、改进后的分析动作、回归检查和最后验证时间。若已有单一权威文档，只增加引用或门禁，不复制整段正文。

## 本次经验的适用边界

本 Harness 的直接来源是“直达 Lake 的联机 UI 与 Character 生成被误当成同一问题”。该案例证明需要拆分现象、核对真实 UE 生命周期、定位断点并保持正式准入链；它不证明以后都应修改 `InitNewPlayer`，也不证明 Standalone、Listen、Dedicated 是所有问题的固定测试矩阵。

案例事实见 `Knowledge/Framework/KNOWN_ISSUES.md` 的“直达 Lake 时隐藏联机 UI 不等于角色能够生成”。本文是问题分析与方案收敛原则的唯一正文，并把这些经验升级为每轮代码任务可执行、可审查的 Harness 合同。
